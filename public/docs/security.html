Security Best Practices

Essential security guidelines for production deployments

Authentication & Authorization

  • Role-Based Access Control (RBAC): Built-in roles (admin, operator, viewer) with granular permission levels
  • Scoped API Keys: Create API keys with allowed_domains patterns and expiration dates for fine-grained access control; scope is enforced on every per-domain endpoint (create, renew, download, deployment status, DNS alias check, settings GET’s domains[] array)
  • Local Authentication: Setup wizard for first-run user creation with secure session management
  • OIDC / SSO (v2.7.0+): Authorization Code + PKCE via Authlib; IdP-claim-based role mapping (case-insensitive, first-match-wins); JIT or link-by-email provisioning with mandatory email_verified gate (default require_verified_email=true) to defend against self-service-signup IdPs leaking admin@target.com claims; dedicated audit-logged settings endpoint kept separate from the bulk settings POST. Tested against Keycloak, Authentik, Okta.
  • HTTPS Only: Always use HTTPS in production

OIDC / SSO configuration

OIDC is disabled by default. Local users, API keys and the legacy bearer token keep working when it’s off — OIDC is purely additive.

  • Issuer URL must be HTTPS in production. http://localhost* is permitted for development.
  • Role mapping uses an admin-configurable claim (default groups) plus a {claim_value → role} table; first match wins. Configurable default role for callers that match no rule (default viewer).
  • Provisioning paths: JIT writes a new users row with password_hash='', so a JIT identity cannot fall back to local password login. link_by_email attaches an OIDC subject to an existing local user, preserving their existing password_hash (admin can flip link_by_email off for a hard cutover).
  • End-session URL carries id_token_hint + client_id + post_logout_redirect_uri so Keycloak / Okta / Authentik terminate the IdP-side session on logout.
  • Audit: client_secret rotations are detected from the raw request payload (the masked sentinel from GET does not trigger a false-positive); refused link_by_email attempts (missing email_verified) emit oidc_user_link_refused.

Rate Limiting & Protection

  • Built-in Rate Limiting: Configurable rate limits to prevent API abuse
  • CSRF Protection: Cross-site request forgery protection on all state-changing endpoints
  • Content Security Policy: Strict CSP headers to prevent XSS attacks
  • Secure Cookies: HttpOnly, Secure, SameSite=Strict session cookies

File Permissions

  • Private keys: 600 permissions
  • Certificate directories: 700 permissions
  • Unified backup ZIPs are written as 0600 and mask secrets by default (see “Backup safety” below)

Backup safety (v2.6.10+)

  • Default mode: secrets_masked. POST /api/web/backups/create produces a share-safe archive where every credential field (DNS provider tokens, storage-backend secrets, api_bearer_token, smtp_password, OIDC client_secret) is replaced with the canonical mask sentinel before serialisation. Restoring this backup onto an existing install preserves the on-disk credentials via the same deep-merge pipeline the settings POST uses; restoring onto a fresh install keeps the sentinels and logs a warning so the operator knows to re-enter secrets.
  • Opt-in plaintext: include_secrets=true. Admin-only and audit-logged. Produces a full disaster-recovery archive that does carry every credential in plaintext — the audit-log entry records the opt-in so a SIEM can flag the resulting file-on-disk credential dump.
  • Restore re-validates deploy hooks against the current DeployManager validator. A backup containing a hook command that today’s validator rejects (e.g. saved under an older permissive version, or a tampered archive) is refused before settings.json is written; the caller’s pre_restore_backup remains as the rollback target.

Defense in depth (2026 audit hardening)

Internal four-angle audit on main closed 11 findings (3 CRITICAL, 6 HIGH, 5 MEDIUM) in a single day. The hardening is now baked into the runtime and pinned by ~115 regression tests; the contracts callers should rely on:

  • Domain validation at the write boundary. POST /api/certificates/create validates the primary domain field structurally (RFC label rules, length, no traversal characters) before any side effect — directory creation, settings persistence, certbot invocation. Same gate on the web blueprint and on the batch endpoint, so a poisoned domain cannot survive into background renewals via check_renewals.
  • Path-style download routes (/api/certificates/<domain>/download/<cert|chain|fullchain|privkey|combined>) carry the same role gating as the legacy ?file= form: viewers pull public material; privkey and combined require operator+, with the denial audit-logged.
  • Client-cert API stratified: viewer reads list / detail / stats / public-material download; operator mints, renews, batches; admin revokes; key file download is operator-floor regardless of route.
  • Settings-mutating routes preserve masked secrets. POST /api/storage/config, POST /api/notifications/config and the central settings POST all run _strip_masked_values + deep-merge against the on-disk subtree, so a UI round-trip that re-POSTs masked sentinels does not destroy the on-disk credential. Toggling a non-secret field (e.g. storage_mode or notifications enabled) is safe.
  • Certbot error responses are sanitised. When the DNS plugin echoes the offending credentials INI line on parse error, the API response strips credential-bearing name = value lines and replaces credential file paths with a generic marker; the unredacted output remains in the application log for operator debugging.
  • Mask coverage extended. ACME-DNS username + subdomain (UUID + delegation FQDN — together they are the shared secret) and the notifications GET subtree are now masked through the same central helper the settings GET path uses.
  • Cross-tenant filtering on settings GET. Scoped API keys (allowed_domains set) see only their in-scope domains[] on GET /api/web/settings. POST /api/certificates/check-dns-alias scope-gates the body-style domain + every SAN, matching the path-param sibling.

Network Security

  • Implement firewall rules to restrict API access
  • Use reverse proxy (nginx/haproxy) for production
  • Enable structured JSON audit logging for compliance
  • Prometheus metrics endpoint for monitoring (/metrics)
