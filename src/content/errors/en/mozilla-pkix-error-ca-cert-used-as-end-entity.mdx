## What it means

Firefox reports `MOZILLA_PKIX_ERROR_CA_CERT_USED_AS_END_ENTITY`: *"The server
uses a certificate with a basic constraints extension identifying it as a
certificate authority. For a properly-issued certificate, this should not be
the case."*

The condition is one bit. The server's own certificate carries a
basicConstraints extension with `cA` set to true, and mozilla::pkix refuses any
end-entity certificate that makes that claim. A leaf with `CA:FALSE`, or with
no basicConstraints extension at all, passes this check.

When the check fires decides which error you see. For an ordinary leaf,
Firefox holds the problem back and first builds a chain to a trusted root; only
if that succeeds does it report the CA flag. If the chain fails, you get the
chain's error, which is why a self-signed certificate with `CA:TRUE` normally
shows `MOZILLA_PKIX_ERROR_SELF_SIGNED_CERT`. The exception is a certificate
Firefox itself treats as a trust anchor, such as one imported as an authority:
there this error is raised at once.

## Common causes

- **A self-signed certificate that was then trusted as an authority.**
  `openssl req -x509` with the example `openssl.cnf` that ships with OpenSSL
  takes its extensions from the `[ v3_ca ]` section, which sets
  `basicConstraints = critical,CA:true`. Served as it is, Firefox calls it
  self-signed. Import it into Firefox as a trusted authority to silence that
  warning, and it becomes a trust anchor: the next visit fails with this code
  instead.
- **An internal CA signing leaves with the CA profile.** An `-extfile` or
  `-extensions` section copied from the root's. The chain to your internal
  root builds fine; the leaf's own flag is what fails.
- **One certificate doing two jobs.** A certificate generated once as "the CA"
  for a lab or an appliance, distributed as a root, and also installed as the
  server certificate of the host that made it.

## How to fix it

**1. Read the flag on the certificate being served:**

```bash
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -text | grep -E 'Issuer:|Subject:|CA:'
```

`CA:TRUE` confirms the diagnosis. If issuer and subject are also identical, the
certificate is a self-signed root being served as a leaf.

**2. Keep the CA and the leaf separate.** The CA certificate stays where it is,
distributed as a root and never configured on a server. Issue the server its
own leaf, with an explicit end-entity profile:

```bash
openssl req -new -newkey rsa:2048 -nodes -keyout server.key -out server.csr \
  -subj "/CN=intranet.example.com"

openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -days 365 -out server.crt -extfile <(printf '%s\n' \
    'basicConstraints=critical,CA:FALSE' \
    'keyUsage=critical,digitalSignature,keyEncipherment' \
    'extendedKeyUsage=serverAuth' \
    'subjectAltName=DNS:intranet.example.com')
```

**3. If the name is public, skip the internal CA entirely.** A publicly trusted
CA issues end-entity certificates, and a DNS-01 challenge works for hosts that
are not reachable from the internet.

**4. Deploy, reload, and check the flag again:**

```bash
systemctl reload nginx
echo | openssl s_client -connect intranet.example.com:443 -servername intranet.example.com 2>/dev/null \
  | openssl x509 -noout -text | grep -A1 'Basic Constraints'
```

The answer should now be `CA:FALSE`. If a self-signed certificate had been
imported into Firefox as an authority, remove it from the certificate manager.

## Prevent it from recurring

This error does not come from time passing. It comes from how a certificate
was made, so it returns whenever someone makes one by hand.

CertMate does not mint server certificates from openssl commands. It requests
them over ACME from the CA you configure, public or your own internal ACME
server, so the leaf's profile, basicConstraints included, is set by that CA
rather than by a pasted `-extfile`. Where CertMate signs certificates itself,
with the built-in CA it uses for client certificates, it pins `CA:FALSE`,
marked critical, and ignores whatever basicConstraints and keyUsage the CSR
asked for. It does not inspect this flag on a certificate a server is already
serving, so for certificates made elsewhere, step 1 above is the check to run.
