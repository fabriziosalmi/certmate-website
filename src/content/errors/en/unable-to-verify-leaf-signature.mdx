## What it means

Node.js raises an `Error` whose `code` is `UNABLE_TO_VERIFY_LEAF_SIGNATURE` and
whose message is OpenSSL's text for that condition, *"unable to verify the
first certificate"*. Node.js 24 and later append a hint: *"; if the root CA is
installed locally, try running Node.js with --use-system-ca"*.

The name is precise. OpenSSL tried to build a chain upwards from the server's
certificate and could not take a single step: the chain it ended up with is
the leaf alone, and the leaf is not self-signed. The certificate that signed
it was not among the certificates the server sent, and not in the trust store
Node.js was using. There is nothing to check the leaf's signature against.

OpenSSL builds the chain only from those two sources. Some browsers recover
from a missing intermediate on their own, which is why a site can look fine in
a browser and fail from a Node.js script against the same URL.

Node.js lets OpenSSL finish the handshake and decides afterwards: its
verification callback always accepts, and the client checks the stored result
once the connection is up. That is why the error arrives as an `error` event on
the socket rather than during the handshake itself.

## Common causes

- **The server sends the leaf without the intermediate.** By far the most
  common case. The server is configured with `cert.pem` where it should have
  `fullchain.pem`, or with a certificate file someone assembled by hand.
  Trust stores hold roots, not intermediates, so the gap cannot be filled on
  the client side.
- **The leaf was signed directly by a CA Node.js does not trust**, and the
  server does not send that CA. Typical of small internal CAs that issue
  straight from the root. If the server does send the root, Node.js reports
  `SELF_SIGNED_CERT_IN_CHAIN` instead.
- **The CA is in the operating system's store, not in Node.js's.** Node.js
  normally uses its own snapshot of the Mozilla CA store, fixed when that
  Node.js version was released (the default is chosen at build time). A
  corporate root installed on the machine is not consulted unless you ask for
  it.

If the server sends the intermediate and only the root is missing, the error
is `UNABLE_TO_GET_ISSUER_CERT_LOCALLY` (*"unable to get local issuer
certificate"*). That one is usually fixed on the client.

## How to fix it

**1. Count what the server sends.** This separates a server problem from a
client problem:

```bash
echo | openssl s_client -connect example.com:443 -servername example.com -showcerts 2>/dev/null \
  | grep -c 'BEGIN CERTIFICATE'
```

A result of `1` for a publicly issued certificate means the intermediate is
missing, and the fix belongs on the server.

**2. Serve the full chain.** Point the server at the file that contains the
leaf followed by its intermediate, not at the bare leaf:

```nginx
ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
```

Reload, then repeat step 1: the count should be `2` or more. This also fixes
every other client that does not fill gaps, not just Node.js.

**3. If the CA is private, add it to the client.** For a root that belongs to
your organisation, give Node.js the certificate in PEM form when the process
starts:

```bash
NODE_EXTRA_CA_CERTS=/etc/ssl/internal-root.pem node app.js
```

The variable extends the bundled roots rather than replacing them. It is read
once at startup, so setting `process.env.NODE_EXTRA_CA_CERTS` from inside the
program has no effect. It is also ignored for any request that passes an
explicit `ca` option, because `ca` replaces the defaults entirely.

If the root is already installed in the operating system's store, start
Node.js with `--use-system-ca` (Node.js 23.8 and later) or set
`NODE_USE_SYSTEM_CA=1` (22.19 and 24.6 and later) so it reads that store in
addition to its own. This is what the hint in the error message
suggests.

**Do not set `NODE_TLS_REJECT_UNAUTHORIZED=0`.** It does not fix the chain; it
switches off certificate validation for every TLS connection the process
makes, and the Node.js documentation describes the result as insecure. The
same goes for `rejectUnauthorized: false`. Both turn a visible error into an
invisible exposure.

## Prevent it from recurring

A missing intermediate is almost always a deployment choice that picked the
wrong file, and it tends to come back whenever a certificate is copied by
hand.

CertMate writes `fullchain.pem` alongside `cert.pem` and `chain.pem` for
every certificate it issues. A deploy hook receives the path of the
full chain as `CERTMATE_FULLCHAIN_PATH`, and the intermediates alone as
`CERTMATE_CHAIN_PATH` for servers that want them in a separate file. Typed
deploy targets read `fullchain.pem`. A hook that copies
`$CERTMATE_FULLCHAIN_PATH` into place ships the intermediate every time.

For a private ACME CA, CertMate trusts the CA certificate you give it by
passing it to certbot as `REQUESTS_CA_BUNDLE`. It is the same principle as
`NODE_EXTRA_CA_CERTS`: trust the root explicitly instead of turning
verification off.

## Related errors

- `x509: certificate signed by unknown authority`: the same failure in Go.
- `PKIX path building failed`: the same failure in Java.
- `NET::ERR_CERT_AUTHORITY_INVALID`: what Chromium shows when it cannot reach a trusted root.
- `SEC_ERROR_UNKNOWN_ISSUER`: the Firefox equivalent.
