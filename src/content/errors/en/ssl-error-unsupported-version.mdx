## What it means

Firefox reports `SSL_ERROR_UNSUPPORTED_VERSION` with the message *"Peer using
unsupported version of security protocol."* The error page adds: *"This website
might not support the TLS 1.2 protocol, which is the minimum version supported
by Firefox."*

The server did answer. Its ServerHello named a protocol version, and that
version lies outside the range Firefox has enabled. Firefox is the side that
says no: it sends a `protocol_version` alert to the server and closes the
connection. By default that range is TLS 1.2 to TLS 1.3, set by the preferences
`security.tls.version.min` (default `3`, TLS 1.2) and `security.tls.version.max`
(default `4`, TLS 1.3). A server whose best offer is TLS 1.0 or 1.1 negotiates
down to it, as the protocol allows, and lands below the floor.

This is not the same failure as `SSL_ERROR_NO_CYPHER_OVERLAP`, where a version
may be agreed and no cipher suite is. Nor is it `SSL_ERROR_PROTOCOL_VERSION_ALERT`:
there, the server is the one refusing and Firefox is reporting the server's
alert. Chrome and the other Chromium browsers report version and cipher
mismatches under one code, `ERR_SSL_VERSION_OR_CIPHER_MISMATCH`.

## Common causes

- **The server tops out at TLS 1.0 or 1.1.** An appliance, an embedded admin
  interface, an old load balancer policy, or a server built against a TLS
  library that predates TLS 1.2. This is the usual case, and every current
  Firefox user sees the same error.
- **One vhost or one listener was left behind.** The main site speaks TLS 1.2
  and 1.3; a second name, a second port, or a second backend behind the same
  balancer still carries the old profile.
- **This Firefox has a raised minimum.** Someone set `security.tls.version.min`
  to `4` in `about:config`, or an enterprise policy (`SSLVersionMin`) did. A
  server that is fine for everyone else, and tops out at TLS 1.2, now falls
  below this browser's floor. If only one machine sees the error, look here
  first.

Firefox does not step down and retry by default. Its version fallback limit,
`security.tls.version.fallback-limit`, defaults to `4`, which leaves no lower
version to fall back to.

## How to fix it

**1. Ask the server which versions it will complete a handshake with:**

```bash
for v in tls1 tls1_1 tls1_2 tls1_3; do
  printf '%-9s ' "$v"
  echo | openssl s_client -connect example.com:443 -servername example.com -"$v" 2>&1 \
    | grep -q 'Cipher is [A-Z]' && echo accepted || echo refused
done
```

If `tls1_2` and `tls1_3` are both refused, the server is the cause.

Read `refused` next to `tls1` and `tls1_1` with care: many current OpenSSL
builds will not offer TLS 1.0 or 1.1 at all, so the handshake fails on your
own machine before anything reaches the server. That result tells you nothing
about the server.

**2. Enable TLS 1.2 and 1.3 on the server.** On nginx:

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
```

On a managed load balancer or CDN, pick a current TLS policy rather than a
legacy one. If the software cannot do TLS 1.2 at all, it needs upgrading or a
TLS-terminating proxy in front of it; no setting will add a protocol version
the library does not implement.

**3. If only one browser is affected, check its settings.** Open
`about:config` and search for `security.tls.version`. A value shown as modified
is the likely cause. When any `security.tls.version.*`, `security.ssl3.*` or
`security.tls13.*` preference has been changed, the error page itself offers
**Restore default settings**. A value set by enterprise policy is locked and
has to be changed in the policy.

Setting `security.tls.version.enable-deprecated` to `true` lowers Firefox's
minimum to TLS 1.0. It applies to every site the browser visits, so treat it
as a stopgap for a device you cannot yet upgrade, not a fix.

## Prevent it from recurring

A server that can speak only TLS 1.0 or 1.1 is already unreachable for every
Firefox on default settings, so the useful moment to find the old protocol is
while the host still speaks something newer as well.

CertMate's own probes require TLS 1.2, so a host that cannot negotiate it is
recorded in the inventory as `unreachable` with a `tls_error`, not as a
certificate.
Since v2.34.0 it can also ask the question the probes cannot: the opt-in
`weak_tls` check offers each tracked host TLS 1.0 and then TLS 1.1, and reports
the host as `failing` when it accepts either. That finds the vhost or balancer
still carrying the old profile while it also speaks TLS 1.2. If CertMate's own
runtime cannot offer those versions, the answer is `unknown`, never "refuses
old TLS". The check is off by default; see
[Domain health](/docs/domain-health.html) for how to turn it on.

## Related errors

- `SSL_ERROR_PROTOCOL_VERSION_ALERT`: the server refused Firefox's versions, rather than the reverse.
- `SSL_ERROR_NO_CYPHER_OVERLAP`: no cipher suite in common.
- `ERR_SSL_VERSION_OR_CIPHER_MISMATCH`: the Chromium code for version and cipher mismatches alike.
