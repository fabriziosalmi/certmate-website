## The principle: keep certificates out of the image

Never bake certificates or private keys into a Docker image — they rotate far
more often than your code, and a key in a layer is a key in your registry.
Instead, **mount** them at runtime and terminate TLS at the edge.

## Option A — terminate TLS at a reverse proxy

Run a TLS-terminating reverse proxy (Nginx, Caddy, Traefik) in front of your
app container and mount the certificate into the proxy:

```yaml
# docker-compose.yml
services:
  proxy:
    image: nginx:stable
    ports:
      - "443:443"
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - /etc/letsencrypt/live/example.com:/certs:ro   # fullchain.pem + privkey.pem
    restart: unless-stopped
  app:
    image: your/app:latest
    expose:
      - "8080"
```

The proxy config points at `/certs/fullchain.pem` and `/certs/privkey.pem`. The
app container never sees the key.

## Option B — mount certs straight into the app

If the app terminates TLS itself, mount the directory read-only:

```bash
docker run -d \
  -v /etc/letsencrypt/live/example.com:/certs:ro \
  -e TLS_CERT=/certs/fullchain.pem \
  -e TLS_KEY=/certs/privkey.pem \
  -p 443:8443 your/app:latest
```

## Renewal: reload the container, don't rebuild

When the certificate renews on the host, the mounted files update — but a
long-running proxy may still hold the old cert in memory. Reload (not rebuild)
the container:

```bash
certbot renew --deploy-hook "docker exec proxy nginx -s reload"
```

## Verify

```bash
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -dates
```

## Do it the hands-off way

You can run CertMate itself as a container (`docker run` / compose) to issue and
renew certificates across 27 DNS providers, and use its deploy hooks to reload
the proxy container the moment a cert rotates — no keys in images, no manual
restarts, managed from a UI or REST API.
