Backup & Recovery

What a backup holds, when it can restore, and how to bring it back

What a Backup Contains

A CertMate backup (a unified backup) is one archive holding settings and certificate state together:

  • settings.json and backup_metadata.json, the manifest.
  • certificates/: every domain directory under the certificate directory, including certbot's accounts/ and archive/, but not certbot's logs/ and work/.
  • data/: the certs, audit and inventory subtrees of the data directory: the private CA, client certificates, the CRL and the audit chain.

Archives are named backup_<YYYYMMDD_HHMMSS_microseconds>_<reason>.zip, or .zip.enc when encrypted, and are written with mode 0600.

Share-safe and disaster-recovery archives

Every backup is one of two kinds, recorded in the manifest as secrets_masked and key_material_excluded:

  • Share-safe (the default): every credential in the settings is replaced with a mask, and no private key is included: no privkey* files, no ACME account private_key.json, no .key, .pfx or .p12 files, and nothing under a keys/ directory. It cannot restore an instance on its own, because the credentials are not in it. Restored onto an instance with no certificates, it still brings back the domains, deploy hooks, the inventory and the audit chain; the certificates come back without their private keys, and the credentials must be re-entered.
  • Disaster recovery (include_secrets: true): plaintext settings and every key. This is the archive that can rebuild an instance.

The Backup Passphrase

Set CERTMATE_BACKUP_PASSPHRASE in the environment. When it is set, every backup is encrypted before it is written: the key is derived from the passphrase with PBKDF2-SHA256 (600,000 iterations) and the archive is encrypted with Fernet. The file gets the .zip.enc suffix. The passphrase is read only from the environment, never from settings.json, and the same passphrase must be present to inspect or restore the archive.

The passphrase also decides what automatic backups contain:

  • With a passphrase, automatic backups are disaster-recovery archives, encrypted at rest. They can restore the instance.
  • Without a passphrase, automatic backups are share-safe: credentials are masked and private keys are left out, so they cannot restore the instance. CertMate logs a warning to this effect once per process, the first time it takes one.

Automatic and Manual Backups

An automatic backup is taken before each settings save, when a settings file already exists. A failed automatic backup is logged and does not block the save.

A manual backup is taken on request from the web UI or the API. Without include_secrets it is share-safe, whether or not a passphrase is set. With "include_secrets": true it is a disaster-recovery archive; without a passphrase that file is unencrypted and holds every credential and private key. The opt-in is recorded in the audit log.

Storage and Retention

Backups are written to <backup dir>/unified/. The backup directory defaults to backups under the install root, is /app/backups in the container image, and can be moved with CERTMATE_BACKUP_DIR. Mount it as a volume in Docker:

-v certmate_backups:/app/backups

Pruning runs after every backup and applies two rules: at most the 50 most recent archives are kept, and any archive older than 30 days is deleted however few there are. Both limits are constants in the code, not settings. A disaster-recovery archive left only in the backup directory is deleted after 30 days, so keep a copy off the host.

If the settings include a backup_storage block with backend: s3_compatible and a complete endpoint, bucket and key pair, each new backup is also copied to that S3-compatible store. The copy is skipped, with an error in the log, when the backup is not encrypted.

Using the Web UI

Go to Settings, section Backup & Restore:

  • Create Unified Backup takes a manual backup. It does not send include_secrets, so the result is share-safe.
  • Restore From Elsewhere uploads an archive you kept off the host. Uploading only stores it.
  • Existing Backups lists each archive with download, restore and delete buttons. An archive that cannot restore is marked cannot restore with the reason, and its restore button is disabled. For a share-safe archive the reason says what it can still do onto an instance with no certificates; that restore is done through the API.

Using the API

All endpoints take Authorization: Bearer <token>. Listing needs the viewer role; creating, downloading, uploading, restoring and deleting need admin. Boolean fields must be JSON booleans: a string such as "true" is refused with 400.

List backups

curl -H "Authorization: Bearer $API_TOKEN" \
  http://localhost:8000/api/backups

The response is {"unified": [...]}. Each entry has filename, can_restore, restore_blocked_reason, contains_key_material, key_file_count and metadata. An encrypted archive on an instance without the passphrase is reported as can_restore: false. can_restore answers whether the archive can bring this instance back, not whether the restore endpoint accepts the file: a share-safe archive is can_restore: false, and its restore_blocked_reason says what restoring it onto an instance with no certificates still returns.

Create a backup

curl -X POST http://localhost:8000/api/backups/create \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"type": "unified", "reason": "before_upgrade", "include_secrets": true}'

reason defaults to manual and becomes part of the filename. include_secrets defaults to false. The 201 response lists the created file under backups[].filename and states secrets_masked.

Download a backup

curl -H "Authorization: Bearer $API_TOKEN" \
  -o backup.zip.enc \
  http://localhost:8000/api/backups/download/unified/<filename>

Restore a backup

curl -X POST http://localhost:8000/api/backups/restore/unified \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"filename": "<filename>", "create_backup_before_restore": true}'

The filename must be an archive in <backup dir>/unified/ ending in .zip or .zip.enc. create_backup_before_restore defaults to true.

Delete a backup

curl -X DELETE -H "Authorization: Bearer $API_TOKEN" \
  http://localhost:8000/api/backups/delete/unified/<filename>

What a Restore Does

  • Pre-restore backup. When requested, the current state is saved first as a disaster-recovery archive with reason pre_restore. It is encrypted only if a passphrase is set. If it cannot be written, the restore is refused with 500 and nothing is changed.
  • Decryption. A .zip.enc archive is decrypted with CERTMATE_BACKUP_PASSPHRASE. A missing or wrong passphrase fails the restore.
  • Share-safe archive over existing certificates. Refused with 409, because it would leave certificates next to private keys that do not match them.
  • Deploy hooks. The restored deploy_hooks are checked with the same validator used when saving settings. If they fail, the restore is aborted before anything is written.
  • Settings. settings.json is replaced. For a share-safe archive, fields holding the mask are dropped before the settings are written. Where a settings file already exists, the credentials already on disk are kept. On a fresh install the settings come back without those credentials, not with the mask in their place, and the DNS, storage and SMTP credentials must be re-entered before the next renewal.
  • Files. Files under certificates/ and data/ are extracted one by one, each replacing its target only once fully written. Private keys and everything under data/ are written 0600, public certificate files 0644. Only the certs, audit and inventory subtrees of data/ are accepted. Certbot's live/ symlinks are rebuilt for each restored domain.
  • Partial failure. If any file cannot be extracted, the response is 500 and names the failed files in failed. Those files keep their previous content. Roll back with the pre-restore backup.

A restore does not bring back anything outside the archive: logs, certbot logs/ and work/, files in the data directory other than settings.json and the certs, audit and inventory subtrees, and the backup passphrase, which CertMate never stores.

Restoring onto a New Host

Restore only reads archives already in the backup directory. After losing the volume, bring a copy back first:

  1. Start the new instance with the same CERTMATE_BACKUP_PASSPHRASE the archive was encrypted with.
  2. Upload the archive, from Restore From Elsewhere or with the API: 
    curl -X POST http://localhost:8000/api/backups/upload \
  -H "Authorization: Bearer $API_TOKEN" \
  -F "file=@backup.zip.enc"
  3. Read the filename in the response. CertMate stores the upload as backup_<timestamp>_uploaded and discards the name you sent. It decides between .zip and .zip.enc from the file's content. Uploads over 40 MB, and files that are neither an encrypted CertMate backup nor a ZIP containing settings.json, are rejected.
  4. Check that the list reports can_restore: true for it, then restore it by that filename.
