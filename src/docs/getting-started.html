Getting Started

Install CertMate with Docker or as a systemd service, and issue a first certificate

Quick Start with Docker

Prerequisites

  • Docker 20.10+
  • Docker Compose 2.0+
  • Domain with DNS managed by a supported provider

1. Clone and Setup

# Clone the repository
git clone https://github.com/fabriziosalmi/certmate.git
cd certmate

# Copy environment template
cp .env.example .env

2. Configure Environment

Edit .env file with your credentials:

# Recommended for any network-exposed deployment: API Security.
# Auto-generated if unset, but an un-onboarded instance is UNAUTHENTICATED
# until you create the first admin — set this (or bind to localhost) before
# exposing CertMate. When set, the first-run screen asks you to paste this
# same token once to authorize creating the initial admin.
API_BEARER_TOKEN=your_super_secure_api_token_here_change_this

# DNS provider. Cloudflare is the only provider read from the environment:
# this token sets the default Cloudflare account. Route53, Azure and the
# rest are configured in Settings -> DNS Providers or through the API.
CLOUDFLARE_TOKEN=your_cloudflare_api_token_here
Docker Hub: Pre-built multi-platform images are available at fabriziosalmi/certmate

3. Deploy

# Start all services
docker compose up -d

# Check status
docker compose ps

# View logs
docker compose logs -f certmate

4. Access CertMate

Service URL Description
Web Dashboard http://localhost:8000 Main interface
API Docs http://localhost:8000/docs/ Swagger UI
Health Check http://localhost:8000/health Service health

5. Create Your First Certificate

Using the Web Interface:

  1. Navigate to http://localhost:8000
  2. Go to Settings and configure your DNS provider, and the CA if you want one other than Let's Encrypt: since v2.35.0 a request for a CA that is not configured is refused rather than issued by Let's Encrypt
  3. Add your domain (e.g. example.com)
  4. Click "Create Certificate"

Using the API:

curl -X POST "http://localhost:8000/api/certificates/create" \
  -H "Authorization: Bearer your_api_token_here" \
  -H "Content-Type: application/json" \
  -d '{"domain": "example.com"}'

Alternative Installation Methods

Python Virtual Environment

Ideal for development and testing:

# Create and activate virtual environment
python3 -m venv certmate-env
source certmate-env/bin/activate

# Install dependencies
git clone https://github.com/fabriziosalmi/certmate.git
cd certmate
pip install -r requirements.txt

# Run the application
python app.py

Kubernetes

The repository ships a Helm chart in charts/certmate:

helm install certmate ./charts/certmate --namespace certmate --create-namespace
Security Note: Set API_BEARER_TOKEN yourself, or keep the port bound to localhost, before the instance is reachable from a network.

Running as a systemd service (without Docker)

Docker is the way CertMate is tested and released. For a Linux host without Docker, the repository ships a systemd unit, certmate.service, that runs the application under gunicorn from a virtualenv in /opt/certmate as a dedicated certmate user.

Prerequisites

  • Linux with systemd
  • Python 3.12: the version the container image is built on and the only one CI tests. requirements.txt does not install on Python 3.9.
  • root or sudo access

Packages needed to build the Python dependencies:

# Ubuntu / Debian
sudo apt update
sudo apt install python3-dev python3-venv build-essential libssl-dev libffi-dev

# CentOS / RHEL / Rocky
sudo yum install python3-devel gcc openssl-devel libffi-devel

1. Application directory and user

Clone into /opt/certmate, then create a system user whose home is that directory and give it ownership:

sudo git clone https://github.com/fabriziosalmi/certmate.git /opt/certmate

sudo useradd --system --shell /bin/false --home-dir /opt/certmate certmate
sudo chown -R certmate:certmate /opt/certmate

2. Virtualenv and state directories

The unit expects the virtualenv at /opt/certmate/venv. Create it as the certmate user and install from the shipped requirements file:

cd /opt/certmate
sudo -u certmate python3 -m venv venv
sudo -u certmate ./venv/bin/pip install -r requirements.txt

CertMate keeps its state in four directories under the install root: certificates, data, backups and logs. At startup it checks that all four are writable and refuses to start if one is not. The unit makes the rest of the filesystem read-only, so create all four before the first start:

sudo -u certmate mkdir -p certificates data backups logs

3. Environment file

The unit reads its settings from /etc/certmate/certmate.env (EnvironmentFile=-/etc/certmate/certmate.env; the leading - makes the file optional). CertMate does not read a .env file from its install directory, so settings placed in /opt/certmate/.env have no effect on this service.

sudo mkdir -p /etc/certmate
sudo tee /etc/certmate/certmate.env > /dev/null <<'EOF'
API_BEARER_TOKEN=your_super_secure_api_token_here_change_this
# Set when a reverse proxy sits in front of CertMate
BEHIND_PROXY=true
# Encrypts backups at rest; the same passphrase is needed to restore
CERTMATE_BACKUP_PASSPHRASE=choose-a-long-random-passphrase
# Optional: sets the default Cloudflare account
CLOUDFLARE_TOKEN=your_cloudflare_token
EOF
sudo chmod 600 /etc/certmate/certmate.env

The unit itself carries no credential. With no token in the file, the application generates one at startup. API_BEARER_TOKEN_FILE and SECRET_KEY_FILE take a path to a file holding the value and take precedence over API_BEARER_TOKEN and SECRET_KEY. Cloudflare is the only DNS provider read from the environment; the others are configured in Settings → DNS Providers or through the API.

The environment file does not set the listen address: gunicorn is started with --bind 0.0.0.0:8000 in ExecStart, so a PORT entry here changes nothing. To listen elsewhere, override ExecStart (see step 4).

4. The unit file

This is certmate.service as shipped in v2.35.0, with its comments removed:

[Unit]
Description=CertMate SSL Certificate Manager
Documentation=https://github.com/fabriziosalmi/certmate
After=network.target network-online.target
Wants=network-online.target

[Service]
Type=simple
User=certmate
Group=certmate
WorkingDirectory=/opt/certmate
Environment=PATH=/opt/certmate/venv/bin
Environment=GUNICORN_TIMEOUT=300
EnvironmentFile=-/etc/certmate/certmate.env
ExecStart=/opt/certmate/venv/bin/gunicorn --bind 0.0.0.0:8000 --workers 1 --threads 8 --timeout ${GUNICORN_TIMEOUT} app:app
ExecReload=/bin/kill -s HUP $MAINPID
Restart=always
RestartSec=10
KillMode=mixed
TimeoutStopSec=5

# Security settings
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/certmate/certificates /opt/certmate/data /opt/certmate/backups /opt/certmate/logs
PrivateTmp=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true

[Install]
WantedBy=multi-user.target
  • --timeout ${GUNICORN_TIMEOUT} (300 seconds) matches the container image. DNS-01 issuance waits on propagation and can run for minutes; gunicorn's own default of 30 seconds would stop the worker in the middle of an issuance.
  • ProtectSystem=strict leaves only the four ReadWritePaths writable, which is why they must exist before the first start.
  • --workers 1 --threads 8 is the same as the container image. See the single-instance constraint below.

Install it, enable it at boot and start it:

sudo cp /opt/certmate/certmate.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable certmate
sudo systemctl start certmate

To change a directive such as the bind address, use a drop-in rather than editing the copied file. ExecStart has to be cleared before it is set again:

sudo systemctl edit certmate

# in the editor:
[Service]
ExecStart=
ExecStart=/opt/certmate/venv/bin/gunicorn --bind 127.0.0.1:8000 --workers 1 --threads 8 --timeout ${GUNICORN_TIMEOUT} app:app

5. Status and logs

sudo systemctl status certmate
sudo journalctl -u certmate --lines=50     # recent logs
sudo journalctl -u certmate -f             # follow
curl http://localhost:8000/health          # health check

The application logs to stdout, so its log lines are in the journal. Set CERTMATE_LOG_FILE in the environment file to also write a rotated log file.

Other management commands:

sudo systemctl stop certmate
sudo systemctl restart certmate
sudo systemctl reload certmate        # sends SIGHUP to the gunicorn master
sudo systemctl is-enabled certmate
sudo systemctl is-active certmate
sudo systemctl disable certmate

After editing /etc/certmate/certmate.env, use restart: systemd reads the environment file when it starts the service.

6. File permissions

sudo chown -R certmate:certmate /opt/certmate
sudo chmod 755 /opt/certmate
sudo chmod 750 /opt/certmate/certificates /opt/certmate/data /opt/certmate/backups /opt/certmate/logs
sudo chmod 644 /opt/certmate/*.py /opt/certmate/*.md
sudo chmod 755 /opt/certmate/venv/bin/*
sudo chmod 600 /etc/certmate/certmate.env

The environment file holds the API token and any provider credential; keep it readable by root only. Issued certificates and their private keys are written to /opt/certmate/certificates.

Single instance

CertMate runs as a single instance. Its renewal scheduler runs inside the web process, so a second copy is a second scheduler issuing against the same certificates: duplicate ACME orders and the CA's duplicate-certificate rate limit. The unit starts one gunicorn worker for the same reason: sessions, session revocation and the login rate limiter are held in memory per process, and each extra worker would run its own renewal job. Keep --workers 1 in any override, run the unit on one host only, and do not run it alongside a CertMate container managing the same certificates. To handle more certificates, give the host more CPU and memory.

Exposure

The shipped unit binds 0.0.0.0:8000. Before the host is reachable from a network, set API_BEARER_TOKEN in the environment file or bind to 127.0.0.1 with a drop-in, and put a reverse proxy in front with BEHIND_PROXY=true set. Without that setting every request appears to come from the proxy's address, and per-client rate limiting collapses into one bucket.

Troubleshooting

  1. Check the service state: sudo systemctl status certmate
  2. Read the log: sudo journalctl -u certmate --lines=100
  3. "Required directories are not writable by the CertMate process." The log line names each directory that failed. Check that it exists, is owned by certmate, and is listed in ReadWritePaths.
  4. Check permissions: the certmate user must be able to read everything under /opt/certmate.
  5. Run it by hand as the service user, outside systemd: sudo -u certmate /opt/certmate/venv/bin/python /opt/certmate/app.py. This starts the development server on port 8000 and does not read /etc/certmate/certmate.env.
  6. Check the certbot plugins installed in the virtualenv: sudo -u certmate /opt/certmate/venv/bin/certbot plugins --text
  7. A provider's plugin fails to install: install requirements-minimal.txt first, then the provider's own file (requirements-aws.txt, requirements-gcp.txt, requirements-azure.txt) on top, rather than pinning packages by hand.

Authentication options

CertMate ships three authentication paths; they coexist and are configured independently.

  • Local users — the first-run screen creates the initial admin. On an instance where you set API_BEARER_TOKEN, paste that token once on that screen to authorize creating the admin. RBAC roles (admin / operator / viewer) gate every endpoint.
  • API keys — per-key role + allowed_domains scope for fine-grained programmatic access. Rotated independently from local users.
  • OIDC / SSO (v2.7.0+) — Authorization Code + PKCE against any OIDC IdP (Keycloak, Authentik, Okta, Auth0, …). IdP-claim-based role mapping with case-insensitive matching. JIT provisioning or link-by-email with an email_verified gate against self-service-signup IdPs. See Security → OIDC / SSO configuration for the full setup.
