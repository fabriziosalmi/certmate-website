Custom Script DNS Provider

Issue DNS-01 certificates through a DNS service CertMate has no provider for, by giving it a script that creates and removes the TXT record.

How It Works

The custom-script provider runs certbot in its core --manual mode with --preferred-challenges dns, and passes your scripts as --manual-auth-hook and, when set, --manual-cleanup-hook. No certbot plugin is installed or needed. Your auth script creates the _acme-challenge TXT record and waits for it to propagate; the optional cleanup script removes it after validation.

Use it for a DNS service without a certbot plugin: an in-house DNS server with an HTTP API, an appliance, or a cloud DNS that CertMate does not list.

Configuration

In Settings, choose Custom Script and fill in Auth Hook Script Path (required) and Cleanup Hook Script Path (optional). Through the API:

curl -X POST https://certmate.example.com/api/settings \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "dns_provider": "custom-script",
    "dns_providers": {
      "custom-script": {
        "auth_hook": "/opt/certmate-hooks/dns-auth.sh",
        "cleanup_hook": "/opt/certmate-hooks/dns-cleanup.sh"
      }
    }
  }'

The values are paths, not commands: you cannot add arguments. The provider supports multiple accounts like the others, so two accounts can point at two different pairs of scripts.

Path Rules

CertMate checks each path when a certificate is issued or renewed with the provider, and in the provider test (POST /api/web/certificates/test-provider). A path is refused unless it:

  • is absolute;
  • names an existing file that the CertMate process can execute;
  • contains only letters, digits, /, ., _ and - (certbot runs hooks through the shell, so whitespace and shell metacharacters cannot work even quoted);
  • is neither world-writable nor group-writable (chmod 755 or stricter).

The test checks the files only. It does not run the scripts and makes no DNS change, so the first real test of the script is an issuance; use the Let's Encrypt staging CA (letsencrypt_staging) for it.

Where the Script Lives

The script runs inside the CertMate container, as the container user certmate (UID 1000 in the image), with CertMate's privileges. The path you configure is a path inside the container, and the script can use only what the image contains: sh, bash, curl, openssl and grep. There is no jq, no dig and no vendor DNS CLI.

Mount the scripts from the host read-only, and set the mode on the host:

# on the host
mkdir -p dns-hooks
chmod 755 dns-hooks/dns-auth.sh dns-hooks/dns-cleanup.sh

# docker-compose.yml, under the certmate service
    volumes:
      - ./dns-hooks:/opt/certmate-hooks:ro

Keep the path stable. certbot stores the hook paths in the certificate's renewal configuration and replays them at every renewal; if you move the scripts, reissue the certificate.

Only an admin can set the provider's configuration. Treat the scripts as part of your deployment, the same trust model as deploy hooks.

The Contract

certbot calls the auth script once per challenge, then asks the CA to validate. It calls the cleanup script once per challenge after validation. The scripts take no arguments; everything arrives in environment variables:

VariableHookValue
CERTBOT_DOMAINbothThe name being validated. The record goes on _acme-challenge.$CERTBOT_DOMAIN.
CERTBOT_VALIDATIONbothThe TXT value for this challenge.
CERTBOT_ALL_DOMAINSbothComma-separated names of every challenge in this run.
CERTBOT_REMAINING_CHALLENGESbothHow many challenges come after this one; 0 on the last.
CERTBOT_AUTH_OUTPUTcleanupWhat the auth script printed on stdout for the same challenge, trimmed.
CERTMATE_DNS_PROPAGATION_SECONDSbothThe propagation wait CertMate has configured (see below).

The script also inherits the CertMate process environment, so a variable you set on the container (an API token, for example) is visible to it.

The exit code does not stop the issuance. certbot 2.10.0, the version the image installs, logs a non-zero exit and anything on stderr as a warning and carries on to validation. The outcome depends only on whether the CA finds the TXT value. Exit non-zero anyway when something fails (set -eu, curl -f), so the warning and the error text appear in the log next to the failed validation.

There is no timeout per script. CertMate stops the whole certbot run after 30 minutes, for issuance and for renewal. A script that hangs holds the issuance until then, and a killed run does not reach the cleanup script.

Waiting for Propagation

certbot validates as soon as the last auth script returns and does not wait between them, so the wait is the script's job. CertMate exports the wait it would use for a plugin as CERTMATE_DNS_PROPAGATION_SECONDS:

  • the custom-script entry of the dns_propagation_seconds setting, default 120, kept between 1 and 3600;
  • unless the account's configuration has its own propagation_seconds, which takes precedence.

The variable is set at issuance and at renewal. Nothing enforces it: a script can ignore it and poll its DNS API instead.

Because all auth scripts run before validation, a script that sleeps only when CERTBOT_REMAINING_CHALLENGES is 0 waits once per run instead of once per name.

Apex and Wildcard in One Certificate

A certificate for example.com and *.example.com has two challenges, and both put their TXT value on _acme-challenge.example.com. Both auth scripts run before the CA checks either value, so both values must be on the name at the same time.

The auth script must add a record, never replace the record set. If your DNS API offers only "set the TXT records on this name", read the existing values and write them back with the new one. The cleanup script must delete only the record whose value is $CERTBOT_VALIDATION, since the other challenge's cleanup runs separately.

Worked Example

The DNS service here is a made-up HTTP API at dns-api.example.net that creates one TXT record per POST and deletes records matching a name, type and value. Replace the URLs and the request body with your service's. The scripts use only sh and curl. The token comes from a container variable, DNS_API_TOKEN, which you set in the container's environment.

/opt/certmate-hooks/dns-auth.sh:

#!/bin/sh
set -eu

NAME="_acme-challenge.${CERTBOT_DOMAIN}"

# Add one TXT record. The API adds; it does not replace the
# records already on the name, so apex + wildcard both survive.
curl -fsS -X POST "https://dns-api.example.net/v1/records" \
  -H "Authorization: Bearer ${DNS_API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d "{\"type\":\"TXT\",\"name\":\"${NAME}\",\"content\":\"${CERTBOT_VALIDATION}\",\"ttl\":60}" \
  >/dev/null

# Wait once, after the last record of this run.
if [ "${CERTBOT_REMAINING_CHALLENGES:-0}" = "0" ]; then
  sleep "${CERTMATE_DNS_PROPAGATION_SECONDS:-120}"
fi

/opt/certmate-hooks/dns-cleanup.sh:

#!/bin/sh
set -eu

NAME="_acme-challenge.${CERTBOT_DOMAIN}"

# Delete only this challenge's value.
curl -fsS -G -X DELETE "https://dns-api.example.net/v1/records" \
  -H "Authorization: Bearer ${DNS_API_TOKEN}" \
  --data-urlencode "type=TXT" \
  --data-urlencode "name=${NAME}" \
  --data-urlencode "content=${CERTBOT_VALIDATION}" \
  >/dev/null

If your API deletes by record ID instead, have the auth script print the ID on stdout and read it in the cleanup script from CERTBOT_AUTH_OUTPUT. Keep other output off stdout, or send it to stderr.

Before a production certificate:

  1. Mount the scripts, chmod 755 them, and set DNS_API_TOKEN on the container.
  2. Save the provider and use the provider test to confirm the paths pass the checks.
  3. Issue a certificate for example.com and *.example.com against letsencrypt_staging, which exercises the two-values case.
  4. Check that both records are gone from _acme-challenge.example.com afterwards.
