Deploy Hooks

Shell commands CertMate runs after a certificate is issued, renewed or revoked: configuration, environment, maintenance windows, validation and history.

What a Deploy Hook Is

A deploy hook is a shell command CertMate runs after a certificate is created, renewed or revoked, such as telling a load balancer to pick up the new certificate. The command is passed to sh -c with a timeout; exit code 0 is success, anything else a failure.

Hooks fire automatically on three events: created, renewed and, since v2.35.0, revoked. Only client certificates can be revoked through CertMate (POST /api/client-certs/<id>/revoke), so that is when a revoked hook fires, with CERTMATE_DOMAIN set to the client certificate's identifier. There is no revoke operation for a server certificate, so no hook fires for one.

A failed hook does not block the certificate operation. It is recorded in the history and audit log, and CertMate publishes deploy_hook_failed, which the notifier delivers whatever event filter is set (see Webhooks).

Hook Fields

A hook is a JSON object. The validator applies these rules when you save:

  • id (required): a stable identifier; the UI generates a UUID.
  • name (required): a label.
  • command (required): one shell command, at most 1024 characters, subject to Command Validation.
  • enabled: defaults to true if absent or not a boolean.
  • timeout: seconds. Defaults to 30 and is clamped to between 1 and 300.
  • on_events: a list of the events the hook runs on, from created, renewed and revoked. If it is absent or not a list, it is set to ["created", "renewed"]: revoked has to be asked for. A hook written into settings.json by hand is not normalised, so without on_events it runs on no certificate event; it still runs when you run hooks by hand.
  • window: an optional maintenance window, described below.

Hooks live under the deploy_hooks settings key. global_hooks run for every domain; domain_hooks maps an exact domain name to hooks for that domain only, which run after the global ones. The top-level enabled flag is the master switch: when it is false or missing, no hook runs on certificate events.

{
  "enabled": true,
  "global_hooks": [
    {
      "id": "tell-lb",
      "name": "Tell the load balancer",
      "command": "curl -fsS -X POST https://lb.internal/api/reload",
      "enabled": true,
      "timeout": 30,
      "on_events": ["created", "renewed"]
    }
  ],
  "domain_hooks": {
    "api.example.com": [
      {
        "id": "push-lb",
        "name": "Push to load balancer",
        "command": "/opt/scripts/push-cert.sh \"$CERTMATE_DOMAIN\"",
        "timeout": 120,
        "on_events": ["renewed"]
      }
    ]
  }
}

Configuring Hooks

In the web UI

Open Settings, then the Deploy tab. Turn on Enable Deploy Hooks, then use Add Global Hook, or add a domain under Domain-Specific Hooks and add hooks to it. Each hook offers Created, Renewed and Revoked checkboxes. New hooks start enabled, with a 30-second timeout and Created and Renewed ticked. Nothing is stored until you press Save Deploy Settings; a rejected hook fails the save with an error naming the hook and the reason.

Through the API

Both endpoints require the admin role.

# Read the current configuration
curl -H "Authorization: Bearer $TOKEN" https://certmate.example.com/api/deploy/config

# Save a configuration
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d @hooks.json https://certmate.example.com/api/deploy/config

Each top-level key you send replaces the stored value, so sending global_hooks replaces the whole list; keys you leave out, such as targets, are kept. A rejected save returns HTTP 400 with the reason in error. POST /api/settings does not accept deploy_hooks.

Environment Variables

The hook inherits the CertMate process environment, plus these variables:

  • CERTMATE_DOMAIN: the domain name.
  • CERTMATE_CERT_PATH: <cert_dir>/<domain>/cert.pem.
  • CERTMATE_KEY_PATH: <cert_dir>/<domain>/privkey.pem. Not set when that file does not exist, as for a certificate issued from a CSR.
  • CERTMATE_FULLCHAIN_PATH: <cert_dir>/<domain>/fullchain.pem.
  • CERTMATE_CHAIN_PATH: <cert_dir>/<domain>/chain.pem, the intermediates without the leaf.
  • CERTMATE_EVENT: created, renewed, revoked, manual or test.
  • CERTMATE_DRY_RUN: set to 1 only for a test run.

<cert_dir> is the certificate directory, certificates under the install root unless CERTMATE_CERT_DIR moves it. The command runs as the CertMate process user, certmate in the Docker image.

Where a Hook Runs

A hook runs inside the CertMate container, as the process that issued the certificate. It does not run on the Docker host, or on the machine you want to reload. A command such as systemctl reload haproxy runs in the container and exits 127, command not found.

The published image carries sh, bash, curl and openssl for a hook to use. It does not carry ssh, scp, sftp, rsync, jq, nginx, systemctl or haproxy. To act on another machine:

  • Call it over the network. Most things worth reloading have an API, and curl is in the image.
  • Build your own image from CertMate's and install what your hook needs.
  • Mount a script into the container and call it. The script also runs in the container, so anything it invokes has to be there too.

Examples that run in the published image:

curl -fsS -X POST -H "Authorization: Bearer $DEPLOY_TOKEN" --data-binary "@$CERTMATE_FULLCHAIN_PATH" https://lb.internal/api/certs/$CERTMATE_DOMAIN

openssl x509 -in "$CERTMATE_FULLCHAIN_PATH" -noout -subject -dates

With curl, keep -f: without it curl exits 0 on an HTTP error, and the hook reports success for a deploy that did not happen.

Maintenance Windows

A certificate renews when it is due. A window on a hook does not change that. It only holds the deploy until the window is next open.

"window": {
  "start": "02:00",
  "end": "04:00",
  "days": ["sat", "sun"],
  "timezone": "Europe/Rome"
}
  • start and end are required, in 24-hour HH:MM. end is exclusive.
  • start and end may not be equal. For a whole day, use 00:00 to 23:59.
  • days is optional. Use mon to sun. Only the first three letters are read, and case does not matter. If the list is absent or empty, the window is open every day.
  • timezone is optional and defaults to UTC. It must be an IANA name such as Europe/Rome. An unknown name is refused when you save.
  • A window that crosses midnight belongs to the day it starts on. With 22:00 to 04:00 on fri, the window is open at 02:00 on Saturday.

In the UI, tick Only deploy during a maintenance window on a hook. The window starts as 02:00 to 04:00 on every day, in your browser's timezone.

Held deploys

When a hook's window is closed, its deploy goes into a queue stored in pending_deploys.json in the data directory, so it survives a restart. A scheduler job checks the queue every minute and runs each held deploy once its window is open.

  • The queue holds one entry per hook and domain. A second renewal before the window opens does not add a second deploy. The hook reads the certificate from disk when it runs, so it deploys the newest one.
  • A held deploy is dropped if its hook has been deleted or disabled, or if the master switch has been turned off.
  • A held deploy that fails is not queued again.
  • A deploy waiting more than 7 days logs a warning but stays queued.

A held deploy does not appear in the history until it runs. To list the queue:

curl -H "Authorization: Bearer $TOKEN" https://certmate.example.com/api/deploy/pending

Each entry includes the hook id, domain, event, queued_at, a readable window, next_run, and orphaned (the hook no longer exists).

Running Hooks by Hand

Testing one hook

curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"domain": "test.example.com"}' \
  https://certmate.example.com/api/deploy/test/<hook_id>

This runs the saved hook with that id, with CERTMATE_EVENT=test and CERTMATE_DRY_RUN=1. The domain defaults to test.example.com, as sent by the UI's Test button. The command really executes; CERTMATE_DRY_RUN only tells your script it is a test. The test ignores on_events, the window, the hook's enabled flag and the master switch. The hook must already be saved, or the endpoint returns 404 with reason: hook_missing_from_config.

Running every hook for a domain

curl -X POST -H "Authorization: Bearer $TOKEN" \
  https://certmate.example.com/api/certificates/api.example.com/deploy

Admin only. Runs every enabled global and domain hook for the domain, plus applicable typed deploy targets, with CERTMATE_EVENT=manual, ignoring on_events and windows. It returns HTTP 200 with {ok, total, succeeded, failed, results} even when ok is false; if the master switch is off or nothing applies, error says so. The dashboard's Run deploy hooks now action calls it.

Command Validation

The command is checked on save, on restore from backup, and again just before it runs. A command is rejected if it is longer than 1024 characters or contains any of these:

  • backticks, $(, or ${. ${CERTMATE_NAME} is allowed, but only with the closing brace directly after the name.
  • &&, ||, ;, a carriage return or a newline
  • > followed by an absolute path, or <<
  • the words eval or source, or . used as the source shorthand: a dot at the start of the command, or after a space or a pipe, followed by a space and an argument
  • the strings settings.json, api_bearer_token, client_secret or vault_token, or .env not followed by a letter or digit, in any case

$CERTMATE_NAME references are allowed, and so are a simple pipe, such as curl ... | grep -q ok, and a redirect to a relative path, such as > out.txt. A rejected save reads like Global hook rejected: hook 'Tell the load balancer' command contains dangerous shell metacharacters. When you need chaining or conditionals, put the logic in a script inside the container and call the script:

#!/bin/sh
set -eu
[ -n "${CERTMATE_DRY_RUN:-}" ] && exit 0
openssl x509 -in "$CERTMATE_FULLCHAIN_PATH" -noout -checkend 0
curl -fsS -X POST --data-binary "@$CERTMATE_FULLCHAIN_PATH" "https://lb.internal/api/certs/$CERTMATE_DOMAIN"

Only the command field is validated, not the script's contents.

History and Audit

Every run is appended to deploy_history.jsonl in the data directory, which keeps the last 500 records. A run that was in progress when CertMate stopped is reported as interrupted. Captured stdout and stderr have secret patterns redacted and are cut to 4096 characters each.

curl -H "Authorization: Bearer $TOKEN" \
  "https://certmate.example.com/api/deploy/history?limit=50&domain=api.example.com"

limit defaults to 50 and is capped at 200. domain is optional. The Deploy tab shows the same under Recent Executions. Each run also writes an audit entry with operation deploy_hook.

Error messages you may see in the history:

  • exit code N: ...: non-zero exit, followed by up to 200 characters of stderr.
  • timeout after Ns: the command ran past its timeout.
  • Command blocked at runtime: ...: the stored command fails validation.

If the history stays empty, check that the data volume is writable by the CertMate user.
