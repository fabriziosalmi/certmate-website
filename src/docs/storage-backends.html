Storage Backends

Where certificates and keys are kept, locally or in a secrets manager

What Is Stored

For each domain, CertMate stores four PEM files, cert.pem, chain.pem, fullchain.pem and privkey.pem, together with a JSON metadata record for the certificate.

CertMate issues certificates into its local certificate directory. When a backend other than the local filesystem is configured, the bundle is then pushed to that backend on issuance and on renewal, as a copy that survives the loss of the local directory. If that push fails, the certificate is still issued, and its metadata carries a storage_warning that GET /api/certificates/<domain> returns. A later renewal check pushes the bundle again while the warning is set, and clears the warning once the push succeeds.

Settings, metadata, backups and runtime state stay on local disk even when certificates also live in a remote backend.

Default: Local Filesystem

The default backend is local_filesystem. It writes to CertMate's certificate directory: CERTMATE_CERT_DIR when that is set, otherwise certificates under the install root. A certificate_storage.cert_dir in settings.json overrides that, unless its value is certificates: the shipped defaults write that value into every settings file, so it is read as "not chosen".

certificates/
  example.com/
    cert.pem
    chain.pem
    fullchain.pem
    privkey.pem       # mode 0600
    metadata.json     # mode 0600

Private keys and metadata.json are written with mode 0600, the other PEM files with 0644. Each file is written to a temporary file with its final mode already set, then renamed over the destination, so a crash mid-write does not leave a truncated key or certificate, and the key is never readable under a looser mode.

Upgrading: CERTMATE_CERT_DIR moves the storage layer too

Since v2.35.0, the local storage backend follows CERTMATE_CERT_DIR. Before, the variable moved where certificates are issued, while the storage layer kept reading and writing a relative certificates/ directory resolved against the working directory the process was started in. The certificate listing reads through the storage layer first, so such an instance had a second tree under its working directory.

  • If certificate_storage.cert_dir in settings.json names a directory other than certificates, nothing changes: that directory is still used.
  • If you set CERTMATE_CERT_DIR and left certificate_storage.cert_dir at its default, the storage layer now uses CERTMATE_CERT_DIR. Confirm your certificates are listed as expected after the upgrade. A certificates/ directory under the working directory CertMate was started from is no longer read or written.
  • If you did not set CERTMATE_CERT_DIR, the storage layer uses certificates under the install root, an absolute path, rather than one resolved against the working directory. When CertMate is started from its install directory, that is the same place.

Supported Backends

The backend is chosen by the certificate_storage.backend key in settings.json. Each remote backend reads its settings from a sub-object with the same name.

s3_compatibleendpoint_url, bucket, access_key_id, secret_access_keyregion (us-east-1), prefix (certmate/certificates)

Azure Key Vault

storage_mode takes one of three values:

  • secrets (default): each PEM file and the metadata are stored as separate Key Vault Secrets. Names derive from cert-<domain>-<file>, with characters other than letters, digits and hyphens replaced by hyphens and an 8-hex-digit CRC32 suffix appended to prevent collisions.
  • certificate: certificate, chain and private key are imported as one PKCS12 Certificate object, which App Service, Application Gateway, Front Door, API Management and AKS Ingress can bind to directly. It is imported with issuer_name="Unknown" so Key Vault does not try to renew it.
  • both: writes both. Reads prefer the Secrets.

Service Principal permissions: secrets mode needs Secrets Get/Set/List/Delete. certificate and both add Certificates Get/List/Import/Delete and keep Secrets Get/List.

When Key Vault imports a Certificate object, it also creates a Secret with the same name whose value is the full PFX, private key included. Any principal with Secrets/Get on the vault can therefore download the private key, so scope that permission carefully in certificate and both modes.

For a vault that already holds certificates as Secrets, POST /api/storage/azure-keyvault/backfill-certificates (admin, also a button in the Storage settings) imports a Certificate object for every domain that lacks one and skips the rest. It is refused unless the active mode is both. An optional ?limit=N caps how many domains one call processes; call it again until the response reports remaining: 0.

AWS Secrets Manager

Each domain is one secret named certmate/certificates/<domain>, whose value is a JSON object holding the PEM files and the metadata.

HashiCorp Vault

Each domain is written to the path certmate/certificates/<domain> in the KV engine at mount_point, using KV v2 or v1 according to engine_version. CertMate renews its Vault token every 6 hours and re-authenticates if the renewal fails.

Infisical

Each PEM file is one secret named certmate-<domain>-<file>, with the dot in the file name replaced by a hyphen (for example certmate-example.com-cert-pem), plus a certmate-<domain>-metadata secret. All are written to the given project_id and environment.

S3-Compatible Object Storage

One backend covers any S3 API through endpoint_url: Hetzner, Contabo, OVHcloud, Scaleway, Exoscale, Wasabi, self-hosted MinIO or Ceph, and AWS S3. Each domain is one JSON object at <prefix>/<domain>.json holding the PEM files and the metadata.

Python dependencies

boto3 is part of the base requirements.txt, so AWS Secrets Manager and S3-compatible storage need nothing extra. The other backends need their packages installed:

pip install -r requirements-azure-storage.txt      # Azure Key Vault
pip install -r requirements-vault-storage.txt      # HashiCorp Vault
pip install -r requirements-infisical-storage.txt  # Infisical
pip install -r requirements-storage-all.txt        # all of the above

When building the Docker image, pass these files through the EXTRA_REQUIREMENTS build argument, for example --build-arg EXTRA_REQUIREMENTS=requirements-storage-all.txt.

Selecting and Configuring a Backend

In the web interface, open Settings, then the Storage tab. Choose a value under Storage Backend Type, fill in its fields, press Test Connection, then save. A saved change takes effect without restarting CertMate.

The same operations are available over the API:

  • GET /api/storage/info (viewer): the active backend, the list of accepted backend values, and backend and cert_dir from settings.
  • POST /api/storage/test (operator): builds the backend from {"backend": ..., "config": {...}} and lists its certificates. For Azure in certificate or both mode it also checks access to the Certificate API.
  • POST /api/storage/config (admin): saves the backend. The backend's fields go under a key named after the backend, not under config.
curl -X POST https://certmate.example.com/api/storage/config \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "backend": "hashicorp_vault",
    "hashicorp_vault": {
      "vault_url": "https://vault.example.com:8200",
      "vault_token": "hvs.example",
      "mount_point": "secret",
      "engine_version": "v2"
    }
  }'

A masked secret value sent back unchanged (********) does not overwrite the stored credential.

When a backend fails to start

If the configured backend cannot be built (for example, a required field is empty or the backend value is unknown), CertMate logs the error and falls back to the local filesystem, in CertMate's certificate directory. GET /api/health then reports "storage": "fallback_to_local (configured backend: azure_keyvault)" (with the name of your backend) and an overall status of degraded.

Migrating Between Backends

POST /api/storage/migrate (admin), also the Migrate Certificates button in the Storage settings, copies certificates from one backend to another. It lists every domain in the source, reads each one, and stores it in the target. It does not delete anything from the source, and it does not change the saved backend.

  • source_backend and source_config default to the currently saved certificate_storage.
  • target_config is required. The target backend comes from target_backend, or from target_config.backend.
curl -X POST https://certmate.example.com/api/storage/migrate \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "target_backend": "s3_compatible",
    "target_config": {
      "endpoint_url": "https://s3.example.com",
      "bucket": "certmate",
      "access_key_id": "...",
      "secret_access_key": "..."
    }
  }'

The response reports migrated_count, failed_count, total, and a per-domain migration_results map. A domain that fails is recorded as false and the rest continue. If the source cannot be listed at all, the call returns HTTP 500 with success: false and does not report an empty migration as a success. Because the source defaults to the saved backend, migrate before you save the new one; then save the new backend with POST /api/storage/config or the Settings form.

Choosing a Backend

CertMate runs as a single instance. For availability, keep the data directory on storage that can be reattached, and configure a remote backend so certificate material also lives somewhere independent of the node.
