Deploy con Docker

Immagine, Compose, ambiente, volumi, aggiornamenti e health check

Immagine e tag

L'immagine è pubblicata su Docker Hub come fabriziosalmi/certmate. Le build di release sono pubblicate per linux/amd64 e linux/arm64; Docker scarica automaticamente l'architettura corrispondente. linux/arm/v7 non è pubblicata, ma l'immagine si può compilare per quella piattaforma (vedi Compilare l'immagine più sotto).

Tag:

  • latest: si sposta solo con un tag di release v*. I push su main pubblicano :main, non :latest.
  • MAJOR, MAJOR.MINOR e MAJOR.MINOR.PATCH, più vMAJOR.MINOR e vMAJOR.MINOR.PATCH.

In produzione, fissa un tag di versione come fabriziosalmi/certmate:2.19, così un nuovo pull non ti aggiorna senza volerlo.

Il container gira come utente non root certmate (UID 1000) sotto tini e serve l'applicazione con gunicorn, con un worker e otto thread. Usa un solo container per volume di dati: lo scheduler dei rinnovi gira dentro il processo web, quindi una seconda replica sarebbe un secondo scheduler che invia ordini ACME duplicati sullo stesso archivio di certificati.

Avvio con docker run

docker run -d --name certmate \
  --env-file .env \
  -p 127.0.0.1:8000:8000 \
  -v certmate_data:/app/data \
  -v certmate_certificates:/app/certificates \
  -v certmate_logs:/app/logs \
  -v certmate_backups:/app/backups \
  fabriziosalmi/certmate:latest

Tieni il file .env sull'host. .dockerignore esclude ogni file .env dal contesto di build, quindi la configurazione viene fornita a runtime e non finisce mai dentro l'immagine.

L'interfaccia web è poi su http://localhost:8000, e la documentazione delle API su /docs/ e /redoc/.

Avvio con Docker Compose

Il docker-compose.yml del repository compila l'immagine dai sorgenti; per usare invece l'immagine pubblicata, togli il commento alla sua riga image:.

git clone https://github.com/fabriziosalmi/certmate.git
cd certmate
cp .env.example .env
# edit .env

# bind mounts: prepare the host directories once (see Volumes)
mkdir -p ./{certificates,data,logs,backups}
chgrp -R 0 ./{certificates,data,logs,backups}
chmod -R g+rwX ./{certificates,data,logs,backups}

docker compose up -d
docker compose ps
docker compose logs -f certmate

Il servizio compose pubblica 127.0.0.1:8000:8000, rimuove tutte le capability Linux, si riavvia con unless-stopped, limita il container a 512 MB di memoria e una CPU, e ruota il log json-file a 10 MB, conservando tre file.

Per compilare con plugin DNS o backend di storage opzionali, imposta EXTRA_REQUIREMENTS in .env con un elenco di file di requirements separati da spazi, ad esempio EXTRA_REQUIREMENTS=requirements-azure.txt requirements-storage-all.txt. È un argomento di build, quindi ha effetto alla build successiva.

Variabili d'ambiente

Queste sono lette dall'applicazione. .env.example elenca solo variabili che qualcosa legge, e un test fa fallire la build se una non lo è.

  • API_BEARER_TOKEN: token di autenticazione delle API, generato automaticamente se non impostato. Impostalo prima che un'istanza non ancora configurata sia raggiungibile dalla rete: finché non esiste il primo admin, un'istanza senza di esso offre il bypass del setup a chiunque la raggiunga. Quando è impostato, la schermata del primo avvio chiede di incollarlo una volta per creare l'admin. Il valore è vincolante: se differisce dal token memorizzato, quello memorizzato viene sostituito all'avvio.
  • API_BEARER_TOKEN_FILE: percorso di un file che contiene il token; ha la precedenza su API_BEARER_TOKEN.
  • SECRET_KEY: chiave di sessione di Flask. Se non è impostata, o è impostata su un segnaposto come change-me, CertMate ne genera una e la salva come /app/data/.secret_key, così le sessioni sopravvivono ai riavvii.
  • SECRET_KEY_FILE: percorso di un file che contiene la chiave; ha la precedenza su SECRET_KEY. Se il file non si può leggere o è vuoto, CertMate si rifiuta di avviarsi.
  • CERTMATE_BACKUP_PASSPHRASE: vedi Backup più sotto.
  • CLOUDFLARE_TOKEN: inizializza l'account DNS Cloudflare predefinito.
  • LETSENCRYPT_EMAIL: email dell'account ACME. Prevale sull'email salvata nell'interfaccia web.
  • PORT: porta di ascolto dentro il container, predefinita 8000. Se la cambi, cambia anche la mappatura ports:.
  • GUNICORN_TIMEOUT: timeout del worker in secondi, predefinito 300. Le challenge DNS-01 su servizi DNS lenti possono richiedere fino a cinque minuti.
  • BEHIND_PROXY: vedi Reverse proxy più sotto.
  • SESSION_TIMEOUT_HOURS: durata della sessione di login, predefinita 8.
  • CERTMATE_LOG_LEVEL (predefinita INFO), CERTMATE_LOG_JSON (predefinita true), CERTMATE_LOG_FILE: vedi Log più sotto.
  • CERTMATE_CERT_DIR: dove risiedono i certificati emessi, predefinita /app/certificates. Vedi Volumi più sotto.

Variabili che non hanno effetto

  • Le credenziali DNS diverse da quelle di Cloudflare. Route53, Azure, Google Cloud DNS, PowerDNS e gli altri si configurano nell'interfaccia web (Settings, DNS Providers) o tramite l'API. Impostare AWS_ACCESS_KEY_ID o AZURE_CLIENT_ID nel container non ha alcun effetto.
  • CLOUDFLARE_API_TOKEN. La variabile è CLOUDFLARE_TOKEN.
  • LOG_LEVEL. La variabile è CERTMATE_LOG_LEVEL.
  • HOST e FLASK_DEBUG. L'indirizzo di bind non è configurabile: il container ascolta sempre su 0.0.0.0 dentro il proprio namespace di rete.

Una credenziale DNS configurata nell'interfaccia viene salvata in settings.json. Per tenerla fuori da quel file, un campo credenziale può invece indicarne la fonte, con api_token_file (un percorso) o api_token_env (il nome di una variabile). Il valore viene letto quando certbot viene eseguito e non viene riscritto.

Porte e reverse proxy

Poiché l'indirizzo di bind dentro il container è fisso, limita l'esposizione quando pubblichi la porta: -p 127.0.0.1:8000:8000 rende CertMate raggiungibile solo sul loopback dell'host. Per l'accesso dall'esterno, mettigli davanti un reverse proxy con TLS.

Quando c'è un proxy davanti, imposta BEHIND_PROXY=true. CertMate si fida allora degli header X-Forwarded-* di un solo hop di proxy, così il rate limiting e le voci di audit vedono l'indirizzo del client anziché quello del proxy. Lasciala non impostata quando non c'è un proxy: con l'opzione attiva, un client può falsificare il proprio indirizzo, che è la chiave su cui si basa il rate limit del login. Quando il TLS termina sul proxy, valuta anche PREFERRED_URL_SCHEME=https, che marca il cookie di sessione come Secure.

Il file compose include un servizio nginx opzionale nel profilo nginx. Crea la sua configurazione prima di avviarlo; se nginx.conf non esiste sull'host, Docker crea al suo posto una directory vuota e nginx non si avvia.

cp nginx.conf.example nginx.conf
# replace every <your-domain> in ssl_certificate / ssl_certificate_key
docker compose --profile nginx up -d

Volumi

Tutto lo stato persistente risiede in quattro directory:

  • /app/data: settings.json, gli utenti admin, la .secret_key generata, la chiave di firma dell'audit e il database dello scheduler.
  • /app/certificates: certificati emessi e chiavi.
  • /app/logs: log dell'applicazione e di audit.
  • /app/backups: archivi di backup.

L'immagine assegna queste directory al gruppo 0, le rende scrivibili dal gruppo e con setgid, così un processo che gira con qualsiasi UID nel gruppo 0 (podman rootless, OpenShift) può scriverci. I file segreti vengono creati con modalità 0600.

I volumi nominati ereditano questi permessi e non richiedono preparazione. I bind mount mantengono la proprietà della directory dell'host; Docker crea le directory mancanti con proprietario root, e il processo non root non può scriverci. Preparale con i comandi chgrp -R 0 e chmod -R g+rwX mostrati sopra oppure, con podman, aggiungi :U a ogni mount. Se una directory non è scrivibile, CertMate si rifiuta di avviarsi con il messaggio "Required directories are not writable by the CertMate process".

Per tenere i certificati in un percorso diverso da /app/certificates, imposta CERTMATE_CERT_DIR e monta quel percorso. Dalla v2.35.0 lo segue anche il backend di storage locale, a meno che certificate_storage.cert_dir nelle impostazioni non indichi una directory propria, nel qual caso prevale quella.

Backup

Imposta CERTMATE_BACKUP_PASSPHRASE se vuoi backup automatici da cui poter ripristinare. Con la passphrase, i backup sono completi e cifrati a riposo (.zip.enc, PBKDF2-SHA256 e Fernet). Senza, i backup automatici hanno le credenziali mascherate: l'elenco dei backup li marca can_restore: false e l'API di ripristino li rifiuta su un'istanza che contiene già certificati. La passphrase viene letta dall'ambiente e mai salvata in settings.json, e per il ripristino serve la stessa passphrase. Gli archivi sull'host vengono eliminati dopo 30 giorni e la perdita del volume li porta via con sé, quindi tienine una copia fuori dall'host.

Aggiornamento

Lo stato risiede nei volumi, non nell'immagine, quindi aggiornare significa scaricare un'immagine più recente e ricreare il container con gli stessi mount. Fai prima un backup (da Settings, Backup, oppure tramite l'API). Le migrazioni del formato delle impostazioni vengono eseguite automaticamente all'avvio.

# Docker Compose, with the image: line in use
docker compose pull
docker compose up -d

# docker run
docker pull fabriziosalmi/certmate:latest
docker rm -f certmate
# re-run the original docker run command with the same -v mounts

Prima di aggiornare alla v2.35.0

  • Un certificato richiesto a una CA non configurata sull'istanza viene rifiutato con HTTP 400, indicando la CA. Let's Encrypt, e la sua voce di staging, funzionano ancora senza nulla di salvato. Configura la CA che richiedi, oppure richiedine una configurata.
  • Se imposti CERTMATE_CERT_DIR e le impostazioni non indicano un certificate_storage.cert_dir proprio, ora anche il livello di storage scrive in CERTMATE_CERT_DIR.
  • Un URL di directory ACME configurato su un account CA deve usare https. Un URL http semplice viene rifiutato.

Una build si rifiuta di leggere un settings.json o un metadata.json scritto da una versione più recente. CERTMATE_ALLOW_SCHEMA_DOWNGRADE=1 scavalca questo controllo, al prezzo di perdere i campi che la build più vecchia non comprende.

Health check

  • /health è l'endpoint di liveness. Restituisce 200 ogni volta che l'applicazione serve richieste; il suo campo JSON status vale healthy o degraded, con i checks per componente. L'HEALTHCHECK dell'immagine lo chiama con curl ogni 30 secondi, con un periodo di avvio di 40 secondi, come docker-compose.yml.
  • /health/ready restituisce 503 quando lo scheduler dei rinnovi non è in esecuzione o quando la verifica di certbot è stata eseguita ed è fallita. Usalo per le readiness probe e i gate di deploy: in entrambi i casi l'istanza è attiva ma non rinnoverebbe nulla.

Log

Il container scrive i log su stdout, in JSON per impostazione predefinita (CERTMATE_LOG_JSON=false per righe semplici), quindi docker logs certmate o docker compose logs -f certmate li mostrano. Per scrivere anche un file ruotato sul volume, imposta CERTMATE_LOG_FILE=/app/logs/certmate.log; lo stream dei log dell'interfaccia web legge quel file.

Recuperare l'accesso admin

Se hai perso la password dell'admin:

docker exec -it certmate python scripts/reset_admin_password.py

Compilare l'immagine

docker build -t certmate:latest .

# multi-platform, from the repository's build script
./build-multiplatform.sh -r YOUR_DOCKERHUB_USERNAME -p
./build-multiplatform.sh --platforms linux/arm/v7 -r YOUR_DOCKERHUB_USERNAME -p

Prossimi passi

  • Per iniziare: primo avvio e primo certificato
  • Provider DNS: configurare le credenziali DNS
  • Backup e ripristino: creare e ripristinare i backup
  • Sicurezza: autenticazione e hardening
  • Risoluzione dei problemi: diagnosticare i problemi del container
