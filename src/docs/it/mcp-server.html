Server MCP

Come collegare un assistente IA a CertMate tramite il server MCP, quali strumenti espone e come le sue azioni vengono autorizzate e sottoposte ad audit.

Che cos'è

Il repository di CertMate include un server Model Context Protocol (MCP) nella directory mcp/. È un processo Node.js che parla MCP su stdio con un assistente IA e trasforma ogni chiamata a uno strumento in una richiesta alla REST API di CertMate. Non ha uno stato proprio e non ha alcun accesso oltre a quello consentito dal token API che gli fornisci: ogni controllo dei permessi avviene in CertMate, non nel server MCP.

Nulla nel server è specifico di un assistente. Qualsiasi client MCP in grado di avviare un server stdio funziona allo stesso modo.

Strumenti

Il server espone gli strumenti seguenti. Il ruolo minimo è quello che CertMate impone sulla route API chiamata dallo strumento.

StrumentoCosa faChiamata APIRuolo minimo
certmate_list_certificatesElenca tutti i certificati con scadenza, stato e domini.GET /api/certificatesviewer
certmate_get_certificateDettaglio di un dominio: stato, giorni alla scadenza, SAN, provider DNS e CA, flag di rinnovo automatico.GET /api/certificates/<domain>viewer
certmate_get_activityAttività recenti e voci di audit. limit opzionale, da 1 a 500, predefinito 100.GET /api/activityviewer
certmate_get_settingsImpostazioni globali. I valori segreti sono mascherati.GET /api/settingsviewer
certmate_list_dns_providersProvider DNS supportati e configurati sull'istanza.GET /api/settings/dns-providersviewer
certmate_diagnosticsUn'istantanea diagnostica sanificata.GET /api/diagnostics/snapshotadmin
certmate_create_certificateRichiede un certificato. domain è obbligatorio; dns_provider, account_id e ca_provider sono opzionali.POST /api/certificates/createoperator
certmate_renew_certificateForza il rinnovo di un certificato esistente.POST /api/certificates/<domain>/renewoperator
certmate_update_certificateRiemette un certificato con un nuovo insieme di SAN e/o un nuovo alias DNS-01.POST /api/certificates/<domain>/reissueoperator
certmate_get_jobInterroga un job asincrono di creazione, rinnovo o aggiornamento tramite job_id.GET /api/certificates/jobs/<job_id>operator

certmate_get_certificate_fileRestituisce un file del bundle come testo PEM grezzo.GET /api/certificates/<domain>/download?file=<file>viewer per cert.pem, chain.pem, fullchain.pem; operator per privkey.pem, combined.pem, cert.pfx

certmate_list_dns_accountsAccount DNS configurati, con credenziali mascherate. Filtro provider opzionale.GET /api/dns/accounts o GET /api/dns/<provider>/accountsadmin

Due delle voci admin sono facili da non notare. Eseguire i deploy hook ed elencare gli account DNS toccano entrambi credenziali memorizzate, quindi un token operator che può rinnovare i certificati riceve comunque un 403 su queste operazioni. Se un agente con ambito operator ha bisogno di un id account per l'emissione, metti l'account_id nel suo prompt invece di chiedergli di cercarlo.

Installazione

Il server richiede Node.js 20 o successivo (engines.node è >=20.0.0 in mcp/package.json) e npm. Da un checkout del repository di CertMate:

cd mcp
npm install

Il punto di ingresso è mcp/index.js. All'avvio scrive CertMate MCP server running on stdio su stderr.

Configurazione

Il server legge quattro variabili d'ambiente:

  • CERTMATE_URL: l'URL di base della tua istanza CertMate. Predefinito http://localhost:8000. Una barra finale viene rimossa. Quando CertMate gira su un altro host, usa un URL https://, perché il token viene inviato con ogni richiesta.
  • CERTMATE_TOKEN: il bearer token dell'API. Obbligatorio. Senza di esso, ogni chiamata a uno strumento restituisce Error: CERTMATE_TOKEN environment variable is not defined.
  • CERTMATE_AGENT_SESSION: opzionale. L'id di sessione inviato a ogni chiamata nell'header X-CertMate-Agent-Session. Se non è impostato, viene generato un nuovo UUID a ogni avvio del processo. Impostalo per correlare un'esecuzione con l'id di un orchestratore esterno.
  • CERTMATE_AGENT_ID: opzionale. Un'etichetta per questa installazione, inviata come X-CertMate-Agent-Id. Predefinito certmate-mcp-server.

Per Claude Desktop, aggiungi il server a claude_desktop_config.json (su macOS in ~/Library/Application Support/Claude/, su Windows in %APPDATA%\Claude\):

{
  "mcpServers": {
    "certmate": {
      "command": "node",
      "args": ["/absolute/path/to/certmate/mcp/index.js"],
      "env": {
        "CERTMATE_URL": "http://localhost:8000",
        "CERTMATE_TOKEN": "your_secure_bearer_token"
      }
    }
  }
}

Per qualsiasi altro client MCP, configuralo in modo che esegua node /absolute/path/to/certmate/mcp/index.js con le stesse variabili d'ambiente.

Autenticazione e ruoli

Il server invia CERTMATE_TOKEN come Authorization: Bearer <token> a ogni richiesta. CertMate lo autentica e applica il ruolo e l'ambito di domini della chiave, quindi l'agente può fare esattamente ciò che può fare la chiave e nulla di più. Revocare la chiave taglia fuori l'agente.

Crea una chiave dedicata all'agente in Settings, nella scheda API Keys, oppure con POST /api/keys (solo admin), e assegnale il ruolo più basso che copre gli strumenti di cui ha bisogno:

  • viewer per un agente che legge soltanto inventario, attività e impostazioni.
  • operator per un agente che crea, rinnova, riemette o scarica certificati.
  • admin solo se deve eseguire deploy hook, elencare account DNS, leggere la diagnostica o eliminare certificati.

Una chiave viewer o operator può essere limitata a domini specifici con allowed_domains. Una chiave con ambito di domini non può leggere, modificare né interrogare i job di domini al di fuori del suo ambito. Le chiavi admin non possono avere un ambito di domini: CertMate rifiuta la richiesta con Admin keys cannot be domain-scoped; use the operator role for scoped access. Una chiave non può mai essere creata con un ruolo più alto di quello della chiave o dell'utente che la crea.

Cosa un agente può e non può modificare

  • Creazione, rinnovo e aggiornamento sono asincroni. Il server invia sempre async: true e CertMate risponde con HTTP 202, un job_id e status: "queued". Interroga con certmate_get_job; il job passa per queued e running e termina come succeeded o failed. Se la coda di emissione è piena, CertMate restituisce 429 con il codice ISSUANCE_QUEUE_FULL.
  • Dalla v2.35.0, un ca_provider non configurato sull'istanza viene rifiutato, non sostituito: il job di creazione termina come failed con un errore che indica la CA, e nessun certificato viene emesso da un'altra CA. Let's Encrypt e Let's Encrypt staging non richiedono una configurazione salvata. Un job di creazione fallito non emette certificate_failed, quindi il segnale è il resoconto dell'agente stesso.
  • certmate_update_certificate non può cambiare il dominio principale, che è l'identità del certificato. Ometti sans per mantenere l'insieme di SAN attuale, passa un array vuoto per rimuovere tutti i SAN e passa domain_alias: "" per azzerare l'alias.
  • certmate_set_auto_renew richiede un booleano vero e proprio. Se il modello invia la stringa "false", il server rifiuta la chiamata con enabled must be true or false invece di inoltrarla.
  • certmate_deploy_certificate esegue ogni deploy hook abilitato per il dominio con CERTMATE_EVENT=manual; i filtri per evento degli hook vengono ignorati.
  • certmate_delete_certificate è distruttivo e non si può annullare. Non revoca il certificato presso la CA. Si rifiuta di procedere mentre una creazione o un rinnovo detiene il lock del dominio.
  • Nessuno strumento scrive impostazioni, gestisce chiavi API o utenti, né aggiunge, modifica o rimuove account DNS. certmate_get_settings e certmate_list_dns_accounts sono di sola lettura e restituiscono segreti mascherati.
  • certmate_download_certificate e certmate_get_certificate_file con privkey.pem, combined.pem o cert.pfx portano materiale di chiave privata nel contesto dell'assistente. Dai all'agente una chiave operator solo se è ciò che intendi.

Attribuzione nell'audit

Per distinguere le azioni di un agente da quelle di una persona, dai al server MCP una chiave propria, spuntando la casella AI agent key al momento della creazione (oppure con "is_agent": true nel corpo di POST /api/keys), e usa quella chiave come CERTMATE_TOKEN.

CertMate registra chi ha agito in un blocco actor su ogni voce di audit, e determina il tipo di attore solo dalla chiave autenticata:

  • Una chiave contrassegnata come chiave agente viene registrata come actor.kind="agent" con l'id della chiave, e la causa del trigger è agent.
  • Qualsiasi altra chiave API, e il bearer token globale legacy, viene registrata come api_token. Il token legacy inoltre non ha un id di chiave e compare come api_user.

Gli header X-CertMate-Agent-Session e X-CertMate-Agent-Id vengono memorizzati come actor.agent_session e actor.agent_id, troncati a 128 caratteri. Sono dichiarazioni non autenticate: permettono di raggruppare le azioni di un'esecuzione, ma non trasformano mai un chiamante non agente in agent. Lo strumento certmate_get_activity legge lo stesso log. Vedi Conformità per la catena di audit a cui appartengono queste voci.

Eseguire un agente a intervalli pianificati

Un assistente in grado di eseguire un prompt salvato secondo una pianificazione e di chiamare strumenti MCP può mantenere rinnovati i certificati secondo una policy che scrivi nel prompt. Il ciclo:

  1. Chiama certmate_list_certificates, oppure certmate_get_certificate per ogni dominio, e leggi days_left.
  2. Per ogni dominio che soddisfa la tua condizione, ad esempio days_left < 14, chiama certmate_renew_certificate.
  3. Interroga certmate_get_job con il job_id restituito finché lo stato non è succeeded o failed.
  4. Segnala i fallimenti. Un job di rinnovo fallito, tranne uno rifiutato perché il dominio era occupato, emette anche l'evento certificate_failed di CertMate, quindi le notifiche configurate partono indipendentemente da ciò che fa l'agente.

Questo ciclo richiede una chiave operator.
