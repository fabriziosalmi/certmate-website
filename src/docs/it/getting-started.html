Per iniziare

Installa CertMate con Docker o come servizio systemd ed emetti il primo certificato

Avvio rapido con Docker

Prerequisiti

  • Docker 20.10+
  • Docker Compose 2.0+
  • Un dominio con DNS gestito da un provider supportato

1. Clonare e preparare

# Clone the repository
git clone https://github.com/fabriziosalmi/certmate.git
cd certmate

# Copy environment template
cp .env.example .env

2. Configurare l'ambiente

Modifica il file .env con le tue credenziali:

# Recommended for any network-exposed deployment: API Security.
# Auto-generated if unset, but an un-onboarded instance is UNAUTHENTICATED
# until you create the first admin — set this (or bind to localhost) before
# exposing CertMate. When set, the first-run screen asks you to paste this
# same token once to authorize creating the initial admin.
API_BEARER_TOKEN=your_super_secure_api_token_here_change_this

# DNS provider. Cloudflare is the only provider read from the environment:
# this token sets the default Cloudflare account. Route53, Azure and the
# rest are configured in Settings -> DNS Providers or through the API.
CLOUDFLARE_TOKEN=your_cloudflare_api_token_here
Docker Hub: le immagini multipiattaforma precompilate sono disponibili su fabriziosalmi/certmate

3. Deploy

# Start all services
docker compose up -d

# Check status
docker compose ps

# View logs
docker compose logs -f certmate

4. Accedere a CertMate

Servizio URL Descrizione
Dashboard web http://localhost:8000 Interfaccia principale
Documentazione API http://localhost:8000/docs/ Swagger UI
Health check http://localhost:8000/health Stato di salute del servizio

5. Creare il primo certificato

Con l'interfaccia web:

  1. Apri http://localhost:8000
  2. Vai in Settings e configura il tuo provider DNS, e la CA se ne vuoi una diversa da Let's Encrypt: dalla v2.35.0 una richiesta per una CA non configurata viene rifiutata anziché essere emessa da Let's Encrypt
  3. Aggiungi il tuo dominio (ad es. example.com)
  4. Fai clic su "Create Certificate"

Con l'API:

curl -X POST "http://localhost:8000/api/certificates/create" \
  -H "Authorization: Bearer your_api_token_here" \
  -H "Content-Type: application/json" \
  -d '{"domain": "example.com"}'

Metodi di installazione alternativi

Ambiente virtuale Python

Ideale per sviluppo e test:

# Create and activate virtual environment
python3 -m venv certmate-env
source certmate-env/bin/activate

# Install dependencies
git clone https://github.com/fabriziosalmi/certmate.git
cd certmate
pip install -r requirements.txt

# Run the application
python app.py

Kubernetes

Il repository include un chart Helm in charts/certmate:

helm install certmate ./charts/certmate --namespace certmate --create-namespace
Nota di sicurezza: imposta tu stesso API_BEARER_TOKEN, oppure mantieni la porta legata a localhost, prima che l'istanza sia raggiungibile dalla rete.

Esecuzione come servizio systemd (senza Docker)

Docker è il modo in cui CertMate viene testato e rilasciato. Per un host Linux senza Docker, il repository include una unit systemd, certmate.service, che esegue l'applicazione con gunicorn da un virtualenv in /opt/certmate, con un utente dedicato certmate.

Prerequisiti

  • Linux con systemd
  • Python 3.12: la versione su cui è costruita l'immagine del container e l'unica testata dalla CI. requirements.txt non si installa su Python 3.9.
  • Accesso root o sudo

Pacchetti necessari per compilare le dipendenze Python:

# Ubuntu / Debian
sudo apt update
sudo apt install python3-dev python3-venv build-essential libssl-dev libffi-dev

# CentOS / RHEL / Rocky
sudo yum install python3-devel gcc openssl-devel libffi-devel

1. Directory dell'applicazione e utente

Clona in /opt/certmate, poi crea un utente di sistema con quella directory come home e assegnagliene la proprietà:

sudo git clone https://github.com/fabriziosalmi/certmate.git /opt/certmate

sudo useradd --system --shell /bin/false --home-dir /opt/certmate certmate
sudo chown -R certmate:certmate /opt/certmate

2. Virtualenv e directory di stato

La unit si aspetta il virtualenv in /opt/certmate/venv. Crealo come utente certmate e installa dal file di requirements incluso:

cd /opt/certmate
sudo -u certmate python3 -m venv venv
sudo -u certmate ./venv/bin/pip install -r requirements.txt

CertMate conserva il proprio stato in quattro directory sotto la radice di installazione: certificates, data, backups e logs. All'avvio verifica che tutte e quattro siano scrivibili e si rifiuta di partire se una non lo è. La unit rende di sola lettura il resto del filesystem, quindi crea tutte e quattro le directory prima del primo avvio:

sudo -u certmate mkdir -p certificates data backups logs

3. File d'ambiente

La unit legge le impostazioni da /etc/certmate/certmate.env (EnvironmentFile=-/etc/certmate/certmate.env; il - iniziale rende il file opzionale). CertMate non legge un file .env dalla propria directory di installazione, quindi le impostazioni messe in /opt/certmate/.env non hanno effetto su questo servizio.

sudo mkdir -p /etc/certmate
sudo tee /etc/certmate/certmate.env > /dev/null <<'EOF'
API_BEARER_TOKEN=your_super_secure_api_token_here_change_this
# Set when a reverse proxy sits in front of CertMate
BEHIND_PROXY=true
# Encrypts backups at rest; the same passphrase is needed to restore
CERTMATE_BACKUP_PASSPHRASE=choose-a-long-random-passphrase
# Optional: sets the default Cloudflare account
CLOUDFLARE_TOKEN=your_cloudflare_token
EOF
sudo chmod 600 /etc/certmate/certmate.env

La unit in sé non contiene alcuna credenziale. Se nel file non c'è un token, l'applicazione ne genera uno all'avvio. API_BEARER_TOKEN_FILE e SECRET_KEY_FILE accettano il percorso di un file che contiene il valore e hanno la precedenza su API_BEARER_TOKEN e SECRET_KEY. Cloudflare è l'unico provider DNS letto dall'ambiente; gli altri si configurano in Settings → DNS Providers o tramite l'API.

Il file d'ambiente non imposta l'indirizzo di ascolto: gunicorn viene avviato con --bind 0.0.0.0:8000 in ExecStart, quindi una voce PORT qui non cambia nulla. Per ascoltare altrove, sovrascrivi ExecStart (vedi il passo 4).

4. Il file della unit

Questo è certmate.service come distribuito nella v2.35.0, senza i commenti:

[Unit]
Description=CertMate SSL Certificate Manager
Documentation=https://github.com/fabriziosalmi/certmate
After=network.target network-online.target
Wants=network-online.target

[Service]
Type=simple
User=certmate
Group=certmate
WorkingDirectory=/opt/certmate
Environment=PATH=/opt/certmate/venv/bin
Environment=GUNICORN_TIMEOUT=300
EnvironmentFile=-/etc/certmate/certmate.env
ExecStart=/opt/certmate/venv/bin/gunicorn --bind 0.0.0.0:8000 --workers 1 --threads 8 --timeout ${GUNICORN_TIMEOUT} app:app
ExecReload=/bin/kill -s HUP $MAINPID
Restart=always
RestartSec=10
KillMode=mixed
TimeoutStopSec=5

# Security settings
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/certmate/certificates /opt/certmate/data /opt/certmate/backups /opt/certmate/logs
PrivateTmp=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true

[Install]
WantedBy=multi-user.target
  • --timeout ${GUNICORN_TIMEOUT} (300 secondi) coincide con l'immagine del container. L'emissione DNS-01 attende la propagazione e può durare minuti; il valore predefinito di gunicorn, 30 secondi, fermerebbe il worker a metà di un'emissione.
  • ProtectSystem=strict lascia scrivibili solo i quattro ReadWritePaths, ed è per questo che devono esistere prima del primo avvio.
  • --workers 1 --threads 8 è uguale all'immagine del container. Vedi il vincolo di istanza singola più sotto.

Installala, abilitala all'avvio e avviala:

sudo cp /opt/certmate/certmate.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable certmate
sudo systemctl start certmate

Per cambiare una direttiva come l'indirizzo di bind, usa un drop-in anziché modificare il file copiato. ExecStart va svuotata prima di essere impostata di nuovo:

sudo systemctl edit certmate

# in the editor:
[Service]
ExecStart=
ExecStart=/opt/certmate/venv/bin/gunicorn --bind 127.0.0.1:8000 --workers 1 --threads 8 --timeout ${GUNICORN_TIMEOUT} app:app

5. Stato e log

sudo systemctl status certmate
sudo journalctl -u certmate --lines=50     # recent logs
sudo journalctl -u certmate -f             # follow
curl http://localhost:8000/health          # health check

L'applicazione scrive i log su stdout, quindi le sue righe di log sono nel journal. Imposta CERTMATE_LOG_FILE nel file d'ambiente per scrivere anche un file di log ruotato.

Altri comandi di gestione:

sudo systemctl stop certmate
sudo systemctl restart certmate
sudo systemctl reload certmate        # sends SIGHUP to the gunicorn master
sudo systemctl is-enabled certmate
sudo systemctl is-active certmate
sudo systemctl disable certmate

Dopo aver modificato /etc/certmate/certmate.env, usa restart: systemd legge il file d'ambiente quando avvia il servizio.

6. Permessi dei file

sudo chown -R certmate:certmate /opt/certmate
sudo chmod 755 /opt/certmate
sudo chmod 750 /opt/certmate/certificates /opt/certmate/data /opt/certmate/backups /opt/certmate/logs
sudo chmod 644 /opt/certmate/*.py /opt/certmate/*.md
sudo chmod 755 /opt/certmate/venv/bin/*
sudo chmod 600 /etc/certmate/certmate.env

Il file d'ambiente contiene il token API e le eventuali credenziali dei provider; mantienilo leggibile solo da root. I certificati emessi e le relative chiavi private vengono scritti in /opt/certmate/certificates.

Istanza singola

CertMate gira come istanza singola. Il suo scheduler dei rinnovi gira dentro il processo web, quindi una seconda copia è un secondo scheduler che emette sugli stessi certificati: ordini ACME duplicati e il rate limit della CA sui certificati duplicati. La unit avvia un solo worker gunicorn per lo stesso motivo: le sessioni, la revoca delle sessioni e il rate limiter del login sono tenuti in memoria per processo, e ogni worker in più eseguirebbe il proprio job di rinnovo. Mantieni --workers 1 in ogni override, esegui la unit su un solo host e non eseguirla accanto a un container CertMate che gestisce gli stessi certificati. Per gestire più certificati, dai all'host più CPU e memoria.

Esposizione

La unit distribuita si lega a 0.0.0.0:8000. Prima che l'host sia raggiungibile dalla rete, imposta API_BEARER_TOKEN nel file d'ambiente oppure lega il servizio a 127.0.0.1 con un drop-in, e mettigli davanti un reverse proxy impostando BEHIND_PROXY=true. Senza questa impostazione ogni richiesta sembra provenire dall'indirizzo del proxy, e il rate limiting per client si riduce a un unico contatore.

Risoluzione dei problemi

  1. Controlla lo stato del servizio: sudo systemctl status certmate
  2. Leggi il log: sudo journalctl -u certmate --lines=100
  3. "Required directories are not writable by the CertMate process." La riga di log indica ogni directory che ha fallito il controllo. Verifica che esista, che sia di proprietà di certmate e che sia elencata in ReadWritePaths.
  4. Controlla i permessi: l'utente certmate deve poter leggere tutto il contenuto di /opt/certmate.
  5. Avvialo a mano come utente del servizio, fuori da systemd: sudo -u certmate /opt/certmate/venv/bin/python /opt/certmate/app.py. Questo avvia il server di sviluppo sulla porta 8000 e non legge /etc/certmate/certmate.env.
  6. Controlla i plugin di certbot installati nel virtualenv: sudo -u certmate /opt/certmate/venv/bin/certbot plugins --text
  7. Il plugin di un provider non si installa: installa prima requirements-minimal.txt, poi sopra il file specifico del provider (requirements-aws.txt, requirements-gcp.txt, requirements-azure.txt), anziché fissare i pacchetti a mano.

Opzioni di autenticazione

CertMate offre tre modalità di autenticazione; coesistono e si configurano in modo indipendente.

  • Utenti locali — la schermata del primo avvio crea l'admin iniziale. Su un'istanza in cui hai impostato API_BEARER_TOKEN, incolla quel token una volta in quella schermata per autorizzare la creazione dell'admin. I ruoli RBAC (admin / operator / viewer) controllano l'accesso a ogni endpoint.
  • Chiavi API — ruolo per chiave + ambito allowed_domains per un accesso programmatico granulare. Si ruotano indipendentemente dagli utenti locali.
  • OIDC / SSO (v2.7.0+) — Authorization Code + PKCE verso qualsiasi IdP OIDC (Keycloak, Authentik, Okta, Auth0, …). Mappatura dei ruoli basata sui claim dell'IdP, con confronto non sensibile alle maiuscole. Provisioning JIT o collegamento tramite email, con un controllo su email_verified contro gli IdP con registrazione self-service. Vedi Security → OIDC / SSO configuration per la configurazione completa.
