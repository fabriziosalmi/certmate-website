CA Providers

The certificate authorities CertMate can issue from over ACME, how each one is configured, and how to pick one per certificate.

Supported Certificate Authorities

Each certificate authority is an entry with a fixed key: the value of ca_provider in the API and in a certificate's metadata.

KeyNameEABWildcardTypes

letsencrypt_stagingLet's Encrypt (Staging)NoYesDV (untrusted)
zerosslZeroSSLRequiredYesDV

The ACME directory each entry uses:

letsencrypt          https://acme-v02.api.letsencrypt.org/directory
letsencrypt_staging  https://acme-staging-v02.api.letsencrypt.org/directory
zerossl              https://acme.zerossl.com/v2/DV90
google               https://dv.acme-v02.api.pki.goog/directory
actalis              https://acme-api.actalis.com/acme/directory
digicert             https://one.digicert.com/mpki/api/v1/acme/v2/directory  (default; your setting wins)
sslcom               https://acme.ssl.com/sslcom-dv-rsa
sectigo              the URL of your SCM ACME account
private_ca           the URL you configure

The directory passed to certbot with --server depends on the entry:

  • Fixed: Let's Encrypt, its staging entry, ZeroSSL, Google Trust Services, Actalis and SSL.com always use the built-in directory above. Their settings forms do not ask for one.
  • Default, overridable: DigiCert uses the ACME Directory URL saved in its settings, and the built-in one only when that field is empty.
  • Yours only: Sectigo and Private CA have no built-in directory. Issuance fails with <CA name> ACME URL not configured when none is saved.

Directory URLs must use https

Since v2.35.0, a directory URL taken from your settings (DigiCert, Sectigo, Private CA) must use the https scheme, in any letter case. Issuance with an http:// directory is refused with:

<CA name> ACME Directory URL must use https. A directory fetched over plain HTTP cannot be trusted to be the one you meant.

Any other value that does not start with https:// is refused as Invalid <CA name> ACME Directory URL format.

Let's Encrypt

The default. When no CA is chosen on a certificate and default_ca is not set, CertMate uses letsencrypt. It needs no credentials, only an email address.

Let's Encrypt (Staging)

Staging is a separate CA entry, not a per-certificate flag. It issues certificates that browsers do not trust; use it to check DNS, deployment and renewal without spending production rate limits. Select it as the CA for one certificate, or make it the default while you test.

It shares the Let's Encrypt account settings: if the staging entry has no email of its own, CertMate uses the letsencrypt entry. A request that still carries the older staging boolean with letsencrypt is mapped to letsencrypt_staging.

A staging certificate cannot be turned into a trusted one. Reissue it with letsencrypt as the CA (see Switching a certificate to another CA).

ZeroSSL, Google Trust Services, SSL.com

Each needs an EAB Key ID, an EAB HMAC Key and an email. The settings page points to where the credentials come from: the ZeroSSL Developer Dashboard for ZeroSSL, and Google Cloud Console under Certificate Authority Service for Google Trust Services.

Actalis

An Italian CA issuing 90-day DV certificates over ACME. It needs EAB credentials, which you generate in the Actalis customer area under Manage with ACME, then ACME Credentials. Actalis does not offer wildcards over ACME, and its free plan covers single-domain certificates only. A request with SAN entries on the free plan is rejected by Actalis with:

Your account only grants single-domain 90-days DV certificates

Issue one certificate per hostname, or use a paid plan.

DigiCert

Needs EAB credentials from DigiCert and an email. The settings form also has an ACME Directory URL field, prefilled with the DigiCert ONE directory. That directory is regional: an account outside the default region has its own directory URL, shown in CertCentral. Enter it in the field and issuance uses it; leave the default and the default is used. It must be an https URL. DigiCert publishes no public ACME staging directory.

Sectigo

Issues through a Sectigo Certificate Manager (SCM) ACME account. There is no shared Sectigo directory: each SCM ACME account has its own, so the settings form asks for it. Fields:

  • CA account: pick a saved account, or Add account... to create one.
  • Account name: the key the account is saved under.
  • ACME Directory URL (from SCM) (required): copy it from the SCM ACME account details. It must use https.
  • EAB Key ID / KID and EAB HMAC Key (required): from the same account details.
  • Email.

Whether wildcards and OV are available depends on the SCM account and its profile.

Accounts are saved under ca_providers.sectigo.accounts, one entry per account name, each with its own acme_url, eab_kid, eab_hmac and email. To use a particular account for one certificate, send its name as ca_account_id to POST /api/certificates/create. Without it, CertMate uses the account named in default_ca_accounts.sectigo, then an account named default, then the first one saved. Asking for an account that does not exist is refused.

curl -X POST http://localhost:8000/api/certificates/create \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "domain": "example.com",
    "ca_provider": "sectigo",
    "ca_account_id": "production-ov"
  }'

Private CA

Points CertMate at any ACME server you name: an internal CA such as step-ca or Boulder, or a public ACME CA that has no entry of its own. Fields:

  • ACME Directory URL (required): the directory URL of your ACME server. It must use https (see Directory URLs must use https).
  • CA Certificate (PEM format) (optional): the root that signed the ACME server's TLS certificate. Leave it empty when the server has a publicly trusted certificate.
  • EAB Key ID and EAB HMAC Key (optional): sent only when both are set. If only one is set, CertMate logs a warning and registers without EAB.
  • Email (required).

The Known ACME CA (preset) menu fills in the directory URL of a public CA. Its one preset is Actalis (https://acme-api.actalis.com/acme/directory); with it, fill in the EAB fields from the Actalis customer area and leave the CA certificate empty. The dedicated Actalis entry does the same job.

External Account Binding

EAB ties the ACME account to an account you hold with the CA. It is a Key ID and an HMAC Key, passed to certbot as --eab-kid and --eab-hmac-key.

  • For a CA that requires EAB, issuance fails with EAB credentials not configured for CA provider '<key>' when either value is missing.
  • For Let's Encrypt and its staging entry, EAB is never sent, even if stray EAB fields are present in the saved settings.
  • For Private CA, EAB is sent only when both values are set.

Both spellings are accepted in the settings file: eab_kid/eab_hmac (what the settings page saves) and eab_key_id/eab_hmac_key. When both pairs are present, eab_kid/eab_hmac wins; an empty value falls back to the other spelling.

The settings page does not show a saved HMAC key again. When you reopen the form, the HMAC field is empty; saving with it left empty keeps the stored key, and typing a new one replaces it.

Configuring a CA

  1. Open Settings, then the Certificate Authority (CA) Providers section.
  2. Choose the Default Certificate Authority. The form for that CA appears below it.
  3. Fill in the fields.
  4. Click Test CA Connection.
  5. Save the settings.

CA configuration lives in the settings under ca_providers, keyed by the CA key; the default is default_ca.

When the settings page is saved, the email of the default CA's form becomes the global email setting. That global email is what CertMate passes to certbot as --email for every issuance, whichever CA the certificate uses. If it is empty, creating a certificate fails with Email not configured.

What the connection test checks

The button calls POST /api/settings/test-ca-provider, which requires the operator role. The body is ca_provider plus a config object.

  • Let's Encrypt and staging: checks that an email is present. It does not contact the CA.
  • ZeroSSL, Google Trust Services, SSL.com, Actalis: checks that both EAB values and an email are present. It does not contact the CA.
  • Sectigo: checks that the directory URL is present and uses https, and that both EAB values and an email are present. It does not contact Sectigo.
  • DigiCert: checks that the directory URL, both EAB values and an email are present, and that the Key ID is at least 10 characters and the HMAC Key at least 32. It does not contact DigiCert.
  • Private CA: the only test that makes a network request. It fetches the directory URL (10-second timeout, redirects not followed), using the CA certificate you supplied for TLS verification, and passes when the response is JSON containing newAccount or keyChange.
curl -X POST http://localhost:8000/api/settings/test-ca-provider \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "ca_provider": "private_ca",
    "config": {
      "acme_url": "https://step-ca.example.com:9000/acme/directory",
      "email": "admin@example.com",
      "ca_cert": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----"
    }
  }'

Private CA failure messages and what they mean:

  • SSL verification failed. Provide CA cert for verification.: the server's certificate does not chain to a public root; paste the CA certificate.
  • SSL verification failed. Provided CA cert could not verify server. Check PEM format.: the certificate you pasted is not the one that signed the server.
  • CA certificate must be in PEM format: the text must start with -----BEGIN CERTIFICATE----- and end with -----END CERTIFICATE-----.
  • Endpoint does not appear to be a valid ACME directory: the URL answers but is not an ACME directory.

Choosing the CA per Certificate

New certificates use default_ca. To override it for one certificate, pick a CA in the Certificate Authority menu of the create form, or send ca_provider to POST /api/certificates/create. Leaving the menu on Use default from settings, or omitting the field, uses the default.

curl -X POST http://localhost:8000/api/certificates/create \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "domain": "example.com",
    "ca_provider": "letsencrypt_staging"
  }'

The CA used is recorded in the certificate's metadata and returned as ca_provider in the response.

Since v2.35.0, a request for a CA that has no saved configuration, or for a CA account that does not exist, is refused with 400. CertMate does not issue from a different CA in its place. The error names the CA:

CA provider 'digicert' is not configured on this instance, and issuing from a different CA is not a substitute for the one you asked for. Configure it in Settings, or request a CA that is configured.

Let's Encrypt is the exception, because certbot's defaults are its configuration: a request for letsencrypt or letsencrypt_staging works with nothing saved, and a staging request stays on staging.

If you upgrade from an earlier version and have been requesting a CA you never configured, those requests now fail. Configure that CA in Settings, or request one that is configured.

Which CA issued a certificate

The CA column of the certificates table (shown on wide screens, and sortable) and the Issuing CA row of a certificate's detail panel name the CA it was issued with. The same value is ca_provider in the API response and in the certificate's metadata. Certificates issued before CertMate recorded the CA show — there rather than a guess.

CAA records

While you fill in the create form, CertMate checks the domain's CAA records against the chosen CA through POST /api/certificates/check-caa. The result is a warning only; issuance is never blocked on it, because CertMate's DNS resolver is not the one the CA uses. For a Private CA the check reports that it does not apply.

Switching a Certificate to Another CA

Changing default_ca affects new certificates only. Renewal runs certbot renew on the existing certificate, so it goes back to the CA that issued it.

To move a certificate to another CA, reissue it: POST /api/certificates/<domain>/reissue with the new ca_provider. Fields you omit keep the values the certificate was issued with, and the old certificate is served until certbot succeeds.

curl -X POST http://localhost:8000/api/certificates/example.com/reissue \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"ca_provider": "letsencrypt"}'

Trust for Private CAs

The CA certificate you give CertMate is used for one thing: letting certbot verify the TLS certificate of your ACME server. CertMate writes it to a temporary file and sets REQUESTS_CA_BUNDLE for the certbot process, both at issuance and at renewal, and removes the file afterwards. If the account or its certificate is missing at renewal, the renewal runs without the bundle, which fails against a server whose certificate chains to the private root.

It does not make the issued certificates trusted anywhere. Clients that connect to services using them need your private root installed in their own trust stores.
