Monitoring

The health and readiness endpoints, the Prometheus metrics CertMate exports, and the alert rules and Grafana dashboard shipped with it.

Three Endpoints

CertMate answers three different questions over HTTP:

  • GET /health: is the process serving requests, and is anything degraded? Public, always 200.
  • GET /health/ready: can this instance renew certificates? Public, 200 or 503.
  • GET /metrics: Prometheus metrics. Requires the viewer role.

Notifications about certificate events (issued, renewed, failed) are a separate mechanism, pushed rather than scraped; see Webhooks.

/health

/health is the liveness endpoint. It needs no authentication and returns HTTP 200 whenever Flask is serving, whatever the checks find. The published image's HEALTHCHECK and the docker-compose.yml healthcheck both run curl -f against it. Read the status field, not the HTTP code, to find out whether something is wrong.

curl -s http://localhost:8000/health

The response has four top-level fields:

  • status: healthy, or degraded when any check below fails.
  • version: the CertMate release.
  • api_contract_version: changes only when the API interface changes, so a client should check compatibility against this field rather than version. It is 2.14 in v2.35.0.
  • checks: the individual results.

The scheduler is APScheduler, and it runs the automatic renewals. The certbot check runs certbot --version (first .venv/bin/certbot, then certbot on the PATH) with a 30-second timeout. Running the command is what catches a certbot that is installed but fails on import because a dependency changed version. A timeout counts as a failure. skipped means no real shell was available to run it with, as in tests.

The certbot result is cached. It is checked at startup and again when a request finds the cached answer older than CERTMATE_CERTBOT_PROBE_TTL seconds (default 300, clamped to between 30 and 3600). A certbot that breaks after startup therefore shows up within one TTL, and a probe every few seconds still runs certbot at most once per TTL.

/health/ready

/health/ready is the readiness endpoint, for Kubernetes readiness probes, compose healthchecks and deploy gates. It needs no authentication. It returns 200 when the instance can renew and 503 when it cannot.

The reason for a separate endpoint: /health stays 200 while the scheduler is down, but an instance whose scheduler failed to start serves the UI and API and never renews anything. /health/ready makes that case fail loudly.

It is ready when both hold:

  • the scheduler is running and its recorded state is not failed;
  • the certbot check is not failed. unknown (not checked yet) and skipped count as ready, because neither is evidence of a problem.

The body:

{
  "ready": false,
  "scheduler": "running",
  "certbot": "failed",
  "certbot_error": ".venv/bin/certbot: ...; certbot: exited 1: ..."
}

scheduler is running, otherwise the recorded scheduler state (such as failed) or not_running. certbot is the certbot check's state, or unknown. scheduler_error and certbot_error are added only when that side is the reason for the 503 and an error was recorded.

A 503 means this instance will not renew certificates until the cause is fixed. The app keeps running either way; a failed certbot check never stops startup, so the web UI stays available for diagnosis. Check the error field, then the logs, which carry a critical line when certbot cannot run.

/metrics

/metrics returns the Prometheus text format. It requires authentication with at least the viewer role. It is not public because the series name every managed domain. For Prometheus, create a dedicated API key with the viewer role and send it as a Bearer token; see Security for roles and keys.

curl -s -H "Authorization: Bearer $TOKEN" https://certmate.example.com/metrics

If the prometheus_client library is missing, the endpoint returns 503 with a plain-text comment saying so. It is in requirements.txt, which the Docker image installs by default; an image built with REQUIREMENTS_FILE=requirements-minimal.txt does not include it. If collection fails, the endpoint returns 500.

Inventory gauges are recomputed when /metrics is requested, but at most once every 30 seconds; a scrape within 30 seconds of the last collection gets the previous values. Counters and histograms are updated when the event happens.

Scrape Configuration

The repository's monitoring/ directory holds a scrape job, alert rules and a Grafana dashboard. The scrape job, from monitoring/prometheus-scrape.example.yml, goes in the scrape_configs: list of prometheus.yml:

scrape_configs:
  - job_name: certmate
    metrics_path: /metrics
    scheme: http            # set to https when CertMate is behind TLS
    scrape_interval: 60s
    authorization:
      type: Bearer
      # credentials_file: /etc/prometheus/certmate-token   # recommended
      credentials: "REPLACE_WITH_ADMIN_API_TOKEN"
    static_configs:
      - targets: ["certmate:8000"]   # host:port of your CertMate instance
        labels:
          instance: certmate

The placeholder asks for an admin token, but a viewer key is enough for /metrics and exposes less if the scrape configuration leaks. Put the token in a file and use credentials_file rather than writing it in the configuration. Keep job_name: certmate: the CertMateDown rule matches on it.

Alert Rules

Copy monitoring/prometheus-alerts.yml to where Prometheus can read it and load it:

# prometheus.yml
rule_files:
  - /etc/prometheus/certmate-alerts.yml

The file holds eight rules in three groups.

AlertFires whenForSeverity
CertMateDownup{job="certmate"} == 0: Prometheus cannot scrape CertMate.5mcritical
CertMateCertificateExpiringSoonA domain's certmate_certificate_expiry_days is below 14 and above 2.1hwarning
CertMateCertificateExpiringCriticalA domain's certmate_certificate_expiry_days is 2 or less. This includes expired certificates, which read 0.30mcritical
CertMateCertificatesExpiredsum(certmate_certificates_by_status{status="expired"}) > 0.10mcritical
CertMateRenewalsFailingAny renewal failure in the last 6 hours: increase(certmate_certificate_renewals_total{status="failure"}[6h]) summed is above 0.15mcritical
CertMateIssuanceFailingMore than 3 failed issuances in the last hour, from certmate_certificate_requests_total{status="failure"}.15mwarning
CertMateACMERateLimitedAny rate-limit refusal in the last 24 hours, from certmate_acme_rate_limit_hits_total.5mcritical
CertMateACMEErrorsMore than 5 ACME errors of one error_type in the last hour.30mwarning

The counter-based rules use increase() over a window, so they fire on failures happening now, not on any failure since the process started. The expiry thresholds (14 and 2 days) are the rule file's own and are separate from CertMate's renewal threshold, which decides expiring_soon in certmate_certificates_by_status.

None of the rules uses /health/ready. To alert on an instance that is up but cannot renew, probe that endpoint with your orchestrator or a blackbox check, or alert on certmate_renewal_sweep_completed_timestamp_seconds falling behind.

Grafana Dashboard

monitoring/grafana-dashboard.json is a dashboard titled CertMate - Certificates & ACME, uid certmate-overview, tagged certmate, tls and certificates, refreshing every minute over the last 24 hours by default. To import it: in Grafana, go to Dashboards > New > Import, upload the file, and pick your Prometheus datasource when prompted.

Its eleven panels:

  • Stats: Managed domains, Total certificates, Valid, Expiring soon, Expired.
  • Days until expiry (per certificate): a table of certmate_certificate_expiry_days.
  • Certificates by status (pie chart) and Certificates by DNS provider (bar gauge).
  • Stats: Uptime, Cache entries, Version.

The dashboard shows inventory state only. The issuance, renewal, sweep and queue metrics above are not on it; add panels for them if you need them.
