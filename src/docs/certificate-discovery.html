Certificate Discovery

How CertMate records certificates it observes on hosts and in Certificate Transparency logs, what each inventory record holds, and the inventory API.

Issued and Observed Certificates

Without discovery, CertMate knows only the certificates it issued. Discovery also records certificates it observes, served on a host:port or logged in Certificate Transparency. All of them go into one inventory keyed by SHA-256 fingerprint, so one certificate served on many hosts is one record with many endpoints.

Each record carries a source:

  • issued: the certificate was observed on the host of a domain CertMate manages.
  • probed: the certificate was read from a monitored endpoint that is not a managed domain.
  • ct-log: the certificate was found in Certificate Transparency through crt.sh.
  • imported: accepted by the schema, but nothing writes it yet.

An issued certificate enters the inventory when a sweep probes its managed domain, not at issuance. Records are grouped as issued when managed is true and discovered otherwise.

Turning Discovery On

Discovery is opt-in. monitored_endpoints (endpoint probing) and ct_monitoring (CT-log polling) both default to enabled: false. Their daily jobs do nothing until a section is enabled and has something to check.

An admin configures both in the Discovery configuration panel on /inventory, or with POST /api/inventory/config. In the request body the endpoint section is named discovery; the settings file stores it as monitored_endpoints.

curl -X POST https://certmate.example.com/api/inventory/config \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "discovery": {
      "enabled": true,
      "endpoints": ["example.com", "api.example.com:8443", "[2001:db8::1]:443"],
      "include_managed": true,
      "allow_private": false,
      "check_revocation": true
    },
    "ct_monitoring": {
      "enabled": true,
      "domains": ["example.com"],
      "include_managed": true,
      "only_valid": true,
      "max_new_per_run": 100,
      "min_request_interval": 2.0
    }
  }'

Endpoints are parsed on save; a malformed one returns 400. The response is the effective configuration. The same request and panel also hold domain_registration, domain_health and, since v2.35.0, dns_resolver, the nameservers CertMate asks for its own DNS lookups; see Domain Health.

Endpoint Discovery

The sweep runs daily at 04:00. It probes each configured endpoint and records every certificate it reads. The monitored_endpoints keys and their defaults:

  • enabled (false): run the sweep at all.
  • endpoints ([]): hosts to probe.
  • include_managed (true): also probe the host of every managed domain. Wildcard domains are skipped, because *.example.com has no host of its own to probe.
  • allow_private (false): allow private and loopback targets (see the SSRF guard below).
  • check_revocation (true): ask OCSP, then the CRL, whether each served certificate is revoked.

An endpoint can be host, host:port, a bare IPv4 address, a bare IPv6 literal, or a bracketed [v6] or [v6]:port. The port defaults to 443 and must be between 1 and 65535.

Probing managed domains lets you compare what CertMate issued with what the host serves: a renewed certificate that was never deployed shows up as a different served fingerprint.

Each endpoint gets its own status: ok, blocked, unreachable, invalid (the endpoint could not be parsed) or record_failed (the host answered, but the inventory write failed). A failure on one endpoint never stops the sweep.

The Deep TLS Probe

The probe connects to host:port and returns the served certificate's subject and issuer (CN and full DN), serial (decimal and hex), SHA-256 fingerprint, validity dates and days to expiry, SAN DNS names and IPs, public key type (RSA, ECDSA, Ed25519, Ed448 or DSA) with size and curve, signature algorithm, and the served chain (the leaf alone where the runtime cannot expose the chain).

The probe does not validate PKI trust, so it can still describe an expired, self-signed or mismatched certificate. A validation block reports is_expired, not_yet_valid, is_self_signed and hostname_match. The probe requires TLS 1.2 or later. The connect and handshake timeout defaults to 5 seconds. CERTMATE_PROBE_TIMEOUT_SECONDS changes it, and the value is clamped to between 1 and 30 seconds.

A failed probe has status blocked or unreachable, with an error_class such as dns_error, timeout or tls_error.

SSRF Guard

The probe resolves the target and refuses the whole host if any address is not globally routable: loopback, private, link-local, reserved, multicast, CGNAT (100.64.0.0/10), including IPv4-mapped IPv6. It then connects to the validated IP with SNI set to the hostname, so a DNS rebind cannot redirect it. A sweep follows its allow_private setting; POST /api/probe follows the CERTMATE_PROBE_ALLOW_PRIVATE environment variable (1, true, yes or on).

Revocation

With check_revocation on, the probe asks the OCSP responder in the certificate's AIA extension, then falls back to up to two CRL distribution points. The issuer certificate comes from the served chain or the AIA caIssuers URL, and must have signed the certificate.

An answer counts only when verified: an OCSP response signed by the issuer or its delegated OCSP-signing responder and current, or a CRL signed by the issuer and not past its nextUpdate. The statuses are:

  • good: a verified OCSP or CRL answer says the certificate is not revoked.
  • revoked: a verified answer says it is; revoked_at and reason carry what the issuer published.
  • unknown: OCSP does not know the certificate and no CRL settled it.
  • unavailable: no verified answer; error says why.
  • not_applicable: the certificate is self-signed.
  • null: never checked.

A stored revoked is never overwritten. OCSP, CRL and issuer URLs go through the same SSRF guard; only plain http is fetched, redirects are not followed, and bodies are capped.

Certificate Transparency Discovery

Probing finds certificates only on hosts you list. The CT poll queries crt.sh for your domains daily at 05:00 and adds unseen certificates as ct-log, unmanaged, with no endpoints. A certificate in CT that CertMate does not manage is one to investigate. The ct_monitoring keys and defaults:

  • enabled (false).
  • domains ([]).
  • include_managed (true): also poll every managed domain that is not a wildcard.
  • only_valid (true): skip CT entries whose not_after has passed.
  • max_new_per_run (100): the maximum number of new certificates ingested per poll.
  • min_request_interval (2.0): seconds between crt.sh requests.

crt.sh returns a serial but no fingerprint, so the poll matches serials against the inventory and downloads a certificate only when its serial is new. When the per-run cap is reached, the poll logs a warning and stops; remaining domains wait for the next run. Errors are recorded per domain and per entry.

What the Inventory Records

A record holds fingerprint, subject_cn, subject, issuer_cn, issuer, serial, not_before, not_after, key ({type, size, curve}), signature_algorithm, san_dns, source, managed, managed_domain, first_seen, last_seen, revocation ({status, method, reason, revoked_at, error, checked_at} or null) and endpoints, each endpoint with its own host, port, first_seen and last_seen.

Writes are idempotent. Seeing a known certificate again refreshes last_seen and the endpoint; metadata and source keep their first values, and managed never goes from true back to false. Only the revocation answer is rewritten.

The inventory is a SQLite database at <data_dir>/inventory/inventory.db. The inventory directory is one of the data subtrees the unified backup includes. See Backup and Recovery.

The Inventory Page

/inventory lists records as Issued by CertMate and Discovered / unmanaged. The summary counts expired certificates, those expiring within 7, 30 and 90 days, and each revocation status, across every record. Admins also get Scan now, which runs POST /api/inventory/scan.

Adopt appears on unmanaged records. It builds a plan from the observed certificate: the subject CN (or first SAN) as the domain, the other SANs, and the key type where the create flow accepts it. Adoption is refused, with a reason, when no DNS provider with credentials is configured for the domain or no ACME account email is set. After you confirm, CertMate issues the certificate, marks the record managed and publishes certificate_created with adopted: true, which runs the deploy hooks.

Forget (DELETE /api/inventory/<fingerprint>) removes a record and its endpoints. The certificate itself is not touched. If the domain is still in the discovery configuration, the next scan records the certificate again, so remove the domain from the configuration first.

/inventory/crypto-report classifies each certificate's algorithms as weak, acceptable, modern, pqc or unknown. It is informational and does not change issuance.

API

All paths are under /api. A scoped API key sees only records whose subject CN or a SAN falls within its allowed_domains. An out-of-scope record returns 404, the same as a missing one.

Method and pathRolePurpose
GET /api/inventoryviewerRecords and summary. Filters: ?managed=true|false, ?source=.
GET /api/inventory/configviewerEffective discovery and CT configuration.
POST /api/inventory/configadminUpdate configuration; 400 on a bad endpoint.
POST /api/inventory/scanadminRun a sweep and a CT poll now.
GET /api/inventory/crypto-reportviewerReadiness report as JSON, or CSV with ?format=csv.
GET /api/inventory/<fingerprint>/adoptviewerAdoption plan.
POST /api/inventory/<fingerprint>/adoptoperatorAdopt: 201 on success, 400 ADOPTION_UNAVAILABLE, 409 if an operation is in progress for the domain.
DELETE /api/inventory/<fingerprint>operatorForget a record.
POST /api/probeviewerProbe one host now; not stored in the inventory.

POST /api/probe takes host (required), port (default 443), optional server_name for SNI, and check_revocation (default true). A scoped key can probe only names in its scope, server_name included.

curl -X POST https://certmate.example.com/api/probe \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"host": "example.com", "port": 443}'
