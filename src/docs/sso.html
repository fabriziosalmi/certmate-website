Single Sign-On (OIDC)

How to sign in to CertMate through an OpenID Connect identity provider, map its groups to CertMate roles, and control which accounts it creates or links.

How SSO Fits In

CertMate can authenticate users against an OpenID Connect identity provider such as Keycloak, Authentik, Okta, Google Workspace or Microsoft Entra. It uses the Authorization Code flow with PKCE. SSO is an additional way in: local username and password login and API keys keep working alongside it.

A successful SSO login ends in an ordinary CertMate session, the same one a local login creates. Roles and permissions apply to it exactly as they do to a local session. The session remembers that it came from SSO, and that matters in one place: logout.

A fully configured SSO block (enabled, with an issuer URL and a client ID) counts as an operator credential. An instance can therefore run with SSO only, with local authentication never enabled, and it does not stay in first-run setup mode.

Registering CertMate at the IdP

Create a client (application) for CertMate at the identity provider and register this redirect URI:

https://certmate.example.com/api/auth/oidc/callback

The SSO tab in CertMate shows the exact URI for the address you are browsing from. The IdP issues a client ID and a client secret; CertMate needs both.

If you set a post-logout redirect URI in CertMate (see Sessions and Logout), register that exact URI at the IdP as well. In Keycloak it goes in the client's Valid post logout redirect URIs; otherwise the IdP rejects the logout with invalid_redirect_uri.

Issuer URL and discovery

The issuer URL is the part before /.well-known/openid-configuration. CertMate strips a trailing slash and fetches {issuer}/.well-known/openid-configuration to find the IdP's endpoints and signing keys. Examples:

  • Keycloak: https://idp.example.com/realms/main
  • Authentik: https://idp.example.com/application/o/certmate/
  • Google: https://accounts.google.com

The discovery document is fetched on the first login attempt, not at startup, and then cached for the life of the process. Saving a change to the issuer URL, client ID, client secret or scopes drops the cache, so the next login uses the new values without a restart.

Scopes

The default scopes are openid email profile groups. groups is what Keycloak, Authentik and Okta use to put group membership in the token. A provider that does not support it drops it, and role mappings on groups then never match. Claims are read from the ID token and, when the IdP answers, from its userinfo endpoint; where both carry a claim, the ID token's value is used.

Redirect URI behind a proxy

CertMate builds the redirect URI from the incoming request: its scheme and host, followed by /api/auth/oidc/callback. Behind a reverse proxy, set BEHIND_PROXY=true so CertMate honours the proxy's X-Forwarded-Proto, X-Forwarded-Host and X-Forwarded-Prefix headers and builds the public address. Set Redirect URI override only when the IdP must see an absolute URL that differs from the host the request arrives on, for example behind a CDN. When set, it is sent as is.

Keeping the client secret out of settings.json

Instead of storing the secret, the oidc block can name where it lives: client_secret_file with a path, or client_secret_env with an environment variable name.

"oidc": { "client_secret_env": "CERTMATE_OIDC_CLIENT_SECRET" }

The value is read when the OIDC client is built and never written back to settings.json. A reference wins over a literal client_secret in the same block, and trailing whitespace is stripped. If the reference cannot be resolved, CertMate logs an error naming it and SSO logins fail until it resolves; local login is not affected.

Role Mapping

CertMate reads the claim named in role_claim and compares its values with the claim_value of each entry in role_mappings, in order. The first entry that matches sets the role. The claim can be a list (typical for groups) or a single value. Matching ignores case, so certmate-admins also matches CertMate-Admins. If the claim is missing or nothing matches, the user gets default_role.

For a Keycloak realm that puts a groups claim in the token, the block in settings.json looks like this:

"oidc": {
  "enabled": true,
  "provider_name": "Keycloak",
  "issuer_url": "https://idp.example.com/realms/main",
  "client_id": "certmate",
  "client_secret": "********",
  "scopes": ["openid", "email", "profile", "groups"],
  "role_claim": "groups",
  "role_mappings": [
    { "claim_value": "certmate-admins",    "role": "admin" },
    { "claim_value": "certmate-operators", "role": "operator" }
  ],
  "default_role": "viewer",
  "auto_create_users": true,
  "link_by_email": true,
  "sync_role_on_login": true
}

A member of certmate-admins becomes admin, a member of certmate-operators becomes operator, and everyone else who can sign in at the IdP becomes viewer. A member of both groups becomes admin, because that entry comes first. Each mapping's role must be admin, operator or viewer, and its claim_value must not be empty; otherwise the save is refused with a 400.

The default role applies to every account the IdP will authenticate for this client. viewer is the safe choice; restrict who can reach the client at the IdP if even that is too much.

Role sync

With sync_role_on_login at its default of true, the role is recomputed from the current claims at every SSO login. Removing someone from an admin group at the IdP demotes them in CertMate the next time they sign in. Each change is written to the audit log as oidc_user_role_synced with the old and new role.

Set it to false when the IdP should only authenticate and roles are managed in CertMate. The role is then set once, when the user is created, and a role an admin assigns by hand survives later logins.

Provisioning and Linking

After the IdP has authenticated someone, CertMate looks for a matching user in this order:

  1. Subject. A user already linked to this identity, matched on the sub and iss claims. This always takes precedence, so a linked user whose email changes at the IdP is not re-matched by email.
  2. Email link. If link_by_email is on and an existing CertMate user has the same email (compared without regard to case), CertMate writes the IdP identity onto that user. The user keeps their role and their local password for this login; with role sync on, the role is recomputed from the claims at their next one.
  3. Just-in-time creation. If auto_create_users is on, CertMate creates a new user with the mapped role.
  4. Otherwise the login is refused with oidc_provisioning_disabled.

A disabled CertMate user is refused at the subject and email steps, exactly as at local login. Disabling the account in CertMate locks it out however it authenticates.

The email_verified gate

With require_verified_email at its default of true, an email link happens only when the IdP asserts email_verified as true (the boolean or the string "true"). A missing claim counts as not verified. If email_claim names a custom claim, its value must also equal the standard email claim, because email_verified covers only that one. When the gate refuses, the login fails with oidc_email_not_verified and the audit log records oidc_user_link_refused.

The gate applies only when an existing user would be linked, since linking hands over that user's role. A login that matches no existing email goes on to just-in-time creation. Turn the gate off only if your IdP verifies email ownership for every account it issues.

Users created on first login

The username comes from the configured username claim, falling back to preferred_username, then email, then sub. Characters other than letters, digits, ., -, _ and @ become _, and if the name is taken a suffix such as _2 is added. A name containing control characters, or longer than 256 characters, is refused with oidc_invalid_username.

A user created this way has no local password, so the local login form cannot authenticate it, and CertMate refuses to set a password on any user linked to an IdP. In Settings → Users every account linked to an IdP carries an SSO badge, with the issuer in its tooltip, and has no password reset action.

Local Authentication Alongside SSO

With both enabled, the login page shows the username and password form and, below it, the Sign in with <provider> button. How a given account can sign in depends on how it came to exist:

  • A local user who was never linked signs in with a password only.
  • A local user linked by email can sign in either way, because linking keeps the password. This is useful while moving a team to SSO. Turn link_by_email off if you want SSO accounts with no password fallback.
  • A user created on first SSO login signs in through the IdP only.

On an instance where SSO is the only credential configured, CertMate refuses to save SSO as disabled. POST /api/auth/oidc/settings answers 409 with Refusing to disable the last way in. Enable local authentication with an admin user, or set API_BEARER_TOKEN, before turning SSO off.

Sessions and Logout

The callback sets the same certmate_session cookie as local login: HttpOnly, SameSite=Strict, path /, Secure when the request arrived over HTTPS. It lasts SESSION_TIMEOUT_HOURS, which defaults to 8. The user is then sent to the page they asked for before logging in; only a path on the same site is accepted there, anything else sends them to /.

During the flow, state, nonce, the PKCE verifier and the return path are kept in Flask's signed session cookie. That cookie is SameSite=Lax, because the IdP's redirect back is a cross-site navigation, and Secure when PREFERRED_URL_SCHEME=https or CERTMATE_ENABLE_HSTS=true.

Logging out of an SSO session invalidates the CertMate session and, when the IdP's discovery document lists an end_session_endpoint, sends the browser there with id_token_hint, client_id and, if configured, post_logout_redirect_uri. This ends the IdP session too, so the next Sign in with does not log the user straight back in. If the IdP has no end-session endpoint, the browser goes to /login.

Disabling a user, or changing their role, in Settings → Users ends that user's open sessions at once.

Login Errors

A failed SSO login returns to /login?error=oidc_<code>, and the page shows Single sign-on failed: followed by the code.

CodeMeaning
oidc_disabledSSO is off, or the issuer URL or client ID is missing.
oidc_initThe flow could not start; the server log has the cause. An unreachable discovery document fails here.
oidc_deniedThe IdP returned an error, for example because the user cancelled.
oidc_token_exchangeExchanging the code for tokens or validating the ID token failed.
oidc_token_exchange_algorithmThe ID token was signed with an algorithm the cached discovery document does not list. CertMate drops the cached document, so retry; if it persists, check id_token_signing_alg_values_supported at the IdP. The server log names both the algorithm and the advertised list.
oidc_no_claimsThe IdP returned no claims.
oidc_missing_subThe claims have no sub.
oidc_invalid_usernameThe username claim contains control characters or is over 256 characters.
oidc_email_not_verifiedAn email link was refused by the email_verified gate.

Security Notes

  • PKCE with S256 is used on every login, for confidential and public clients alike.
  • The ID token's signature, audience, issuer, expiry and nonce are checked server-side by Authlib against the keys in the IdP's published JWKS.
  • The client secret is returned as ******** in every read of the settings, and a save that sends ******** back keeps the stored secret.
  • The oidc block cannot be changed through the general POST /api/settings; only POST /api/auth/oidc/settings changes it, and it validates and audits the change.
  • /api/auth/oidc/login shares the per-IP rate limit of local login (5 attempts a minute), and failed callbacks count against it.
  • The audit log records oidc_login_success, oidc_login_failure, oidc_user_provisioned, oidc_user_linked, oidc_user_link_refused, oidc_login_refused, oidc_user_role_synced and oidc_config_changed. The config entry lists which keys changed and flags a new client secret, without recording values.

For example, to stop re-deriving roles at login and manage them in CertMate instead:

curl -X POST https://certmate.example.com/api/auth/oidc/settings \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"sync_role_on_login": false}'
