Revocation Checking

How CertMate asks the issuer whether a certificate a host is serving has been revoked, and what the answer means.

What Is Checked

An issuer can revoke a certificate long before it expires. A revoked certificate that is still being served has the right names, valid dates and a sound key, so nothing else the probe reports gives it away. The revocation check asks the issuer directly.

The check runs on the certificate a host serves, as read by the deep TLS probe, in two places:

  • the discovery sweep, for every endpoint it probes, when check_revocation in monitored_endpoints is on (the default is true);
  • POST /api/probe, for one host, when the request's check_revocation is true (the default).

Only the served leaf certificate is checked, not the intermediates in its chain. With check_revocation off, the probe result's revocation is null: not checked, which is different from checked and good.

Where the Issuer Comes From

Verifying an OCSP or CRL answer needs the certificate of the CA that issued the leaf. CertMate looks for it in the chain the host served, which requires Python 3.13 or later. The CertMate image runs Python 3.12, so in practice it takes the second route: it downloads the issuer from the caIssuers URL in the certificate's Authority Information Access extension, trying up to two URLs. The payload may be DER, PEM or a PKCS#7 bundle.

Either way the candidate must actually have signed the leaf: its name must match and the leaf's signature must verify against its key. If no issuer is found, the result is unavailable with an error that starts issuer not available:.

A certificate whose subject equals its issuer and which verifies against its own key is self-signed. No issuer exists that could revoke it, so the result is not_applicable and nothing is fetched.

OCSP First, Then the CRL

  1. OCSP. CertMate sends an OCSP request to the first responder URL in the certificate's Authority Information Access extension. A verified good or revoked ends the check.
  2. CRL. If the certificate names no responder, the responder fails, or it answers that it does not know the certificate, CertMate reads the CRL at the certificate's CRL distribution points, trying up to two of them. The first verified CRL settles the answer: revoked if the serial is on it, good if it is not.

Let's Encrypt turned OCSP off in 2025, so for its certificates the CRL is the only source.

A certificate that names neither an OCSP responder nor a CRL is unavailable with the error certificate names neither an OCSP responder nor a CRL.

What Counts as a Verified Answer

An OCSP response counts only if all of these hold:

  • its response status is successful;
  • it is signed by the issuer, or by a delegated responder certificate included in the response that the issuer signed and that carries the id-kp-OCSPSigning extended key usage, and the signature verifies;
  • it contains an entry for this certificate's serial number under this issuer's key hash;
  • its thisUpdate is not in the future and its nextUpdate, if present, is not in the past.

A CRL counts only if it names this certificate's issuer as its issuer, its signature verifies against the issuer's key, and it is not past its nextUpdate. A serial that is absent from such a CRL is a good answer.

Both date checks allow five minutes of clock difference between CertMate and the responder.

The Five Statuses

statusMeaning
goodA verified OCSP or CRL answer says the certificate is not revoked.
revokedA verified answer says it is revoked. revoked_at and reason carry what the issuer published.
unknownThe OCSP responder said it does not know this certificate, and no CRL settled it. Not a pass.
unavailableNo verified answer could be obtained. error says why. Not a pass.
not_applicableThe certificate is self-signed, so no issuer could revoke it.

In the inventory a sixth state exists: revocation is null when the certificate has never been checked, because checking is off or no sweep has seen it served since.

An Unverified Answer Is Not Good

good means one thing only: a signed, current answer from the issuer said the certificate is not revoked. unavailable and unknown are not passes. They mean CertMate does not know whether the certificate is revoked.

unavailable covers every way of failing to get a verified answer, including:

  • the issuer certificate could not be found, or what the caIssuers URL returned did not sign the leaf;
  • a responder or CRL server could not be reached, answered with an HTTP status other than 200, or returned something that is not an OCSP response or a CRL;
  • the OCSP responder answered with a status other than successful;
  • a signature did not verify, or the OCSP signer was neither the issuer nor an authorised delegate;
  • the OCSP response did not cover this certificate;
  • a response was dated in the future or was past its nextUpdate;
  • a URL was not plain http, its body was over the size cap, or the SSRF guard refused its host.

A failed source never turns into good. If the OCSP responder is down, answers about a different certificate, or signs with a key the issuer did not authorise, CertMate moves on to the CRL; if no CRL gives a verified answer either, the result is unavailable. The error field carries the reason from the last source tried. The attempts list in a POST /api/probe answer shows each source in turn.

unknown is narrower: the responder answered with a verified response saying it has no record of the certificate, and no CRL gave a verified answer either. Its error is the OCSP responder does not know this certificate.

The inventory page follows the same rule. Only good and revoked get a coloured badge ("Not revoked" in green, "Revoked" in red). unknown and unavailable are grey, with the reason on hover.

Revoked Is Final

A CA cannot un-revoke a certificate. Once a verified answer has stored revoked on an inventory record, no later answer replaces it: not unavailable from a responder that is down, and not any other status. Every other status is rewritten on each sweep that checks the certificate.

Where the Answer Appears

POST /api/probe

The probe answer carries the full result under revocation. It is not stored in the inventory.

curl -X POST https://certmate.example.com/api/probe \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"host": "shop.example.com", "port": 443, "check_revocation": true}'

The revocation object has these fields:

  • status: one of the five statuses;
  • method: ocsp or crl, whichever gave the answer;
  • url: the responder or CRL that gave it;
  • revoked_at and reason: set when revoked;
  • error: why the answer is unavailable or unknown;
  • checked_at: when the check ran;
  • attempts: each source tried, as {method, url, outcome, error}.

A certificate whose OCSP responder failed and whose CRL did not list it would come back like this:

"revocation": {
  "status": "good",
  "method": "crl",
  "url": "http://crl.ca.example/r1.crl",
  "revoked_at": null,
  "reason": null,
  "error": null,
  "checked_at": "2026-09-24T08:15:02.123456",
  "attempts": [
    {"method": "ocsp", "url": "http://ocsp.ca.example", "outcome": "error",
     "error": "http://ocsp.ca.example answered HTTP 503"},
    {"method": "crl", "url": "http://crl.ca.example/r1.crl", "outcome": "good", "error": null}
  ]
}

The endpoint needs the viewer role. A scoped key can probe only hosts, and server_name values, within its allowed_domains. It has its own rate-limit bucket of 30 requests a minute, because each call opens a TLS connection to a third party and may fetch that CA's OCSP response or CRL.

Inventory records

Since API contract 2.4, every record from GET /api/inventory carries revocation as {status, method, reason, revoked_at, error, checked_at}, or null if it was never checked. The inventory keeps the last answer only; it does not store url or attempts.

Summary counts

The summary in the same response counts records per status under revocation: revoked, good, unknown, unavailable, not_applicable and unchecked for records never checked. The inventory page shows the revoked count in its summary and has a Revoked filter.

Sweep results

POST /api/inventory/scan (admin) runs a sweep now. In its answer, each entry of discovery.results has a revocation field holding just the status string for that endpoint, or null when it was not checked.

Fetches, Caches and Timeouts

Every OCSP, CRL and issuer URL comes from a certificate CertMate did not necessarily issue, so the fetches go through the probe's SSRF guard. The host is resolved and refused if any address is private, loopback or otherwise not global, unless private targets are allowed. The connection is then pinned to the address that passed. A sweep follows its allow_private setting; POST /api/probe follows CERTMATE_PROBE_ALLOW_PRIVATE. A refused URL makes that source fail, which leads to unavailable if nothing else answers.

  • Only plain http URLs are fetched. OCSP and CRL payloads are signed, so TLS would add nothing to their integrity.
  • Redirects are not followed; any answer other than HTTP 200 is a failure.
  • Bodies are capped: 64 KiB for an OCSP response or an issuer certificate, 20 MiB for a CRL.
  • Each fetch uses the probe timeout: 5 seconds by default, set with CERTMATE_PROBE_TIMEOUT_SECONDS, clamped to between 1 and 30 seconds.
  • Requests carry the user agent CertMate-revocation-check.

The issuer certificate and each CRL are cached in the memory of the CertMate process, keyed by URL. An issuer certificate is kept for 24 hours. A CRL is kept for at most an hour and never past its nextUpdate, so a sweep over many hosts behind one CA downloads the CRL once. The caches are bounded (64 issuer entries, 16 CRLs), and a restart empties them. OCSP responses are not cached.

What It Does Not Do

  • It does not check the intermediate certificates in the chain, only the leaf.
  • It does not read an OCSP response stapled in the TLS handshake. It asks the responder itself.
  • It does not check certificates found only in Certificate Transparency. A ct-log record stays unchecked until a sweep sees the certificate served on an endpoint.
  • It does not act on the answer. A revoked result is recorded and reported; it does not trigger a renewal, a deploy hook or a notification.
  • It does not validate PKI trust. The probe still describes an expired, self-signed or mismatched certificate, and its validation block reports those conditions.
