Compliance Evidence

How the audit trail records, signs and exports certificate actions, how that maps to NIS2, the EU AI Act and ISO/IEC 42001, and where the evidence stops.

Scope: What This Page Does and Does Not Claim

CertMate is a single-instance, self-hosted MIT tool. It is not an AI system, not a high-risk AI system, and not a regulated entity. It does not comply with or certify anything. Compliance obligations fall on the operator running it.

CertMate provides evidence artifacts the operator can use toward their own obligations. Each mapping below states what the operator can evidence and where that stops.

What the Audit Trail Records

Attribution

Certificate lifecycle actions, including create, renew, reissue, deploy, the auto-renew toggle and unattended scheduled renewals, are recorded with two structured fields:

  • actor: who or what acted. kind is one of user (a session or OIDC login), api_token, agent, scheduler or system. For a scoped API key the record also carries the key id and token_prefix.
  • trigger: why. cause is manual, api, agent, scheduled_renewal (with the scheduler job_id) or event.

actor.kind is derived only from the authenticated identity. An action is recorded as agent only when it is made with a scoped API key created with is_agent set. A request with the legacy global bearer token is recorded as api_token, because it has no key id and cannot be shown to be an agent.

To make an agent's actions distinguishable from a human's, give the agent its own key:

curl -X POST https://certmate.example.com/api/keys \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name": "renewal-agent", "role": "operator", "is_agent": true}'

An agent may also send X-CertMate-Agent-Session and X-CertMate-Agent-Id. These are recorded as actor.agent_session and actor.agent_id, truncated to 128 characters, for correlation. They are client-supplied and unauthenticated, so they are a claim and never change actor.kind. The trustworthy identity is the API key.

Tamper-evidence

Each audit entry is also appended to a SHA-256 hash chain, data/audit/certificate_audit.chain.jsonl. Each line holds a gap-free seq, the entry, the previous line's hash and its own hash. A modification, deletion or reorder by someone who cannot recompute the chain is detectable, and the verifier reports the seq where the chain breaks. The human-readable certificate_audit.log carries no integrity property.

The chain is on by default. CERTMATE_AUDIT_CHAIN=0 turns it off.

Signing

The instance holds an Ed25519 key. On first run it is generated and stored as data/.audit_signing_key with mode 0600; AUDIT_SIGNING_KEY_FILE points CertMate at a key kept elsewhere. If that variable is set but the file cannot be read, or the stored key is corrupt, signing is disabled rather than a new key being generated, and the unsigned chain keeps working.

Every 100 chain entries, the chain head is signed and appended to data/audit/certificate_audit.checkpoints.jsonl. Since v2.35.0 the head is also signed on a clean shutdown, as the last step after pending events have been delivered, so the entries written since the last periodic checkpoint, including any written while shutting down, are covered. A crash, a SIGKILL or a power loss stops before that step; see Limits of the Evidence.

Searching the Log

GET /api/activity (viewer and above) returns the most recent entries, newest first. limit defaults to 100 and is bounded to 1–500.

Since v2.35.0 it can be narrowed by any of operation, resource_type, resource_id, user and status. A filter is not applied to the tail an unfiltered call returns: the search walks backwards through the log until it has limit matches or reaches the start, so old entries are found.

# Which users were created while the instance was still in setup mode?
curl -H "Authorization: Bearer $TOKEN" \
  "https://certmate.example.com/api/activity?operation=create&resource_type=user&user=setup_user"

The response carries entries, count, limit, complete, and filters when one was given. complete says how to read the result:

  • complete: true with no entries: the search reached the start of the log and there are none.
  • complete: true with entries: these are all of them.
  • complete: false with entries: the search stopped at limit matches, and there may be older ones.
  • complete: false with no entries: the log could not be read. This does not mean there are none.

An unfiltered call always reports complete: true.

Verifying the Chain

On the instance

GET /api/audit/verify (admin) recomputes the chain. It returns HTTP 200 when intact and 409 when broken. When a signing key is present it also cross-checks the chain against the newest signed checkpoint that verifies under the instance key; the result carries checkpoint_verified, checkpoint_seq and checkpoint_reason. A new instance with no chain file and no checkpoints returns 200 with state set to absent. A missing chain file when checkpoints exist, or an unreadable checkpoint file, returns 409.

Off the instance

The standalone verifier needs the Python standard library for a chain file, plus cryptography for a signed bundle, and does not require running or trusting CertMate:

# Verify a raw chain file
python -m modules.core.audit_verify data/audit/certificate_audit.chain.jsonl

# Verify a signed export bundle, pinning the instance key
python -m modules.core.audit_verify --bundle bundle.json --pubkey instance.pem

--json prints the result as JSON. Exit codes: 0 intact, 1 broken (with the seq and reason), 2 usage or I/O error.

Signed export for an auditor

  1. Fetch the instance's public key with GET /api/audit/public-key (admin). It returns algorithm, public_key_pem and fingerprint, or 404 when the instance has no signing key. Give the PEM to the auditor out of band.
  2. Export the chain with GET /api/audit/export (admin). Optional from_seq and to_seq bound the slice; a slice that starts mid-chain carries its anchor and verifies on its own.
  3. The auditor runs the verifier with --pubkey. Without it, the verifier prints a note that the fingerprint is self-asserted by the bundle.

A passing check shows that the entries were not edited after they were written and which instance produced them, to anyone who does not hold the signing key.

Streaming to a SIEM

Each audit entry can also be pushed to an external collector, configured under the audit_sink settings key (admin, POST /api/settings). It is off by default. Fields and defaults:

{
  "audit_sink": {
    "enabled": false,
    "format": "syslog",
    "protocol": "udp",
    "host": "",
    "port": 514,
    "url": "",
    "timeout": 3.0,
    "facility": 16,
    "app_name": "certmate"
  }
}
  • format: syslog (RFC 5424, the entry as JSON in the message), cef, or json (HTTP POST of the entry to url).
  • protocol: udp or tcp, for syslog and cef, sent to host:port.

Entries pass through the credential sanitizer before they leave the process. A send error is logged as a warning and never breaks audit logging or the certificate operation.

Since v2.35.0 the weekly summary digest is itself an audit entry, so it is in the chain and reaches the sink like any other: operation send, resource_type digest, resource_id weekly, status success or failed (with the error), attributed to actor.kind system. It records how many recipients the digest was for and the counts it reported, not the recipients themselves: they are personal data, and an append-only chain cannot take them back out. A digest skipped because notifications, SMTP or the digest are turned off writes no entry.

Regime Mapping

NIS2 (Directive (EU) 2022/2555)

What it helps with: certificate operations are security-relevant events. CertMate produces a tamper-evident, attributed, time-stamped record of each one, plus an independent check, which the operator can use in their logging (Art. 21) and incident-evidence (Art. 23) practices.

Limit: NIS2 binds essential and important entities, not software tools. CertMate does not assess, monitor or report incidents. Being an in-scope entity, and meeting NIS2 in full, is the operator's responsibility.

EU AI Act, Article 50 (transparency, in spirit only)

What it helps with: when an AI agent operates certificates, the record carries actor.kind set to agent and the claimed agent session, so the operator can show after the fact which changes an AI agent made versus a human, under which key, and what triggered them.

Limit: Art. 50 duties fall on providers and deployers of AI systems and concern disclosure to natural persons interacting with AI. An agent renewing TLS certificates is not a textbook Art. 50 case, and CertMate is a tool, not an AI system. This maps to the transparency and human-oversight spirit only. CertMate does not satisfy Art. 50 on anyone's behalf.

ISO/IEC 42001 (AI management system)

What it helps with: the attributed, tamper-evident records are objective evidence that an AI agent took specific certificate actions, usable for the operational-records and traceability controls of the operator's own AIMS.

Limit: ISO/IEC 42001 certifies an organisation's management system, not a tool. CertMate is not certified to ISO/IEC 42001 and cannot certify the operator.

Limits of the Evidence

  • The key does not bind the operator. Whoever holds the signing key can re-sign a rewritten chain, checkpoint or anchor. Constraining the operator needs signed checkpoints shipped to an external append-only sink; that is planned and not shipped.
  • Authenticity, not completeness. Audit writes are best-effort and never block a certificate operation. A missing interior seq proves a deletion, but a write that failed before it was recorded leaves nothing to verify.
  • Tail truncation is caught only down to the last checkpoint. A clean shutdown signs the tail, so an instance that stops normally leaves nothing unattested. After a crash, a SIGKILL or a power loss, the entries written since the newest signed checkpoint can be dropped undetected until the next checkpoint seals them. Keep successive signed exports if you need to close that gap.
  • The agent-session header is a claim. It is recorded for correlation; the authenticated API key is the identity.
  • Bootstrap actions are attributed to setup_user. Until setup is complete the instance serves every request as admin, so there is no real identity to record. An entry with operation create, resource_type user and user setup_user means that user was created while anyone who could reach the instance was an admin. Since v2.34.0 setup mode creates only the first admin: a further user or an API key is refused with 409 SETUP_BOOTSTRAP_ONLY, and the refusal is audited. Exactly one such entry is therefore expected. More than one means the instance was bootstrapped under an older version, and every user beyond the first is worth confirming or removing. API keys created in that window are flagged on the API Keys page until an operator reviews them; users are not flagged, and the chain is where the answer for them is. Searching the Log shows the query.
  • History boundary. The chain starts when the feature is first enabled. Earlier .log history is not part of it.
  • A pruned chain proves less. After a prune, verification covers entries from the anchor forward, and both the API and the verifier report anchored and the anchor seq instead of a plain "intact".

Retention: Archiving a Prefix of the Chain

There is no automatic pruning and no API endpoint for it. Pruning is one command, run with CertMate stopped, after the prefix has been exported and verified off the box:

# 1. Export the prefix to archive (admin token)
curl -H "Authorization: Bearer $TOKEN" \
     "https://certmate.example.com/api/audit/export?to_seq=1199" > archive-0-1199.json

# 2. Verify it off this box, pinning the instance key
python -m modules.core.audit_verify --bundle archive-0-1199.json --pubkey instance.pem

# 3. Store the archive, then, with CertMate stopped:
python -m modules.core.audit_prune --bundle archive-0-1199.json --data-dir data/audit
python -m modules.core.audit_prune --bundle archive-0-1199.json --data-dir data/audit --yes

Without --yes the command prints the plan and changes nothing. It refuses, and removes nothing, if the bundle does not verify, is unsigned, is empty, does not start where the chain starts, disagrees with the chain at any seq, or would leave the chain empty. --data-dir defaults to data/audit and --key-dir, the directory holding .audit_signing_key, defaults to data, relative to the directory you run the command from. If AUDIT_SIGNING_KEY_FILE is set, that file is used instead, as on the instance.

With --yes, it also refuses if no signing key is found there, or if the key belongs to a different instance from the one that exported the bundle. Both are checked before anything is removed. The tool never creates a key: a new key would be a new instance identity, and an anchor signed with it would fail the instance's own verification.

A prune:

  • appends an archive entry to the chain that survives, recording the archived seq range, the entry count, their head hash and the SHA-256 of the archive file;
  • writes certificate_audit.anchor.json, signed with the instance key, stating where the chain now starts and what it continues from, so a simply truncated chain cannot pass as a pruned one;
  • rewrites the chain without the archived entries.

The anchor describes only the most recent archive. The complete history is the sequence of exported bundles, so keep all of them.
