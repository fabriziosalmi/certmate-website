CSR-Only Certificates

Certificates for devices that keep their own private key: submitting a CSR, renewal, and what CertMate stores

When to Use It

Some appliances generate their private key on the device and cannot export it; all they can hand out is a Certificate Signing Request (CSR). CertMate can issue and renew certificates for them. You submit the CSR, CertMate obtains the certificate from the configured CA and manages the certificate and chain, and the private key is never sent to CertMate or stored by it.

How It Works

  1. Generate the key and the CSR on the device.
  2. Submit the CSR to CertMate through the API or the web UI.
  3. CertMate runs certbot in --csr mode against the same CA, DNS provider and credentials an ordinary request would use, and obtains the certificate.
  4. CertMate stores the certificate, the chain and the CSR. It does not store a private key.
  5. At renewal, CertMate submits the stored CSR to the CA again.

Submitting a CSR

Through the API

Pass the PEM CSR as csr in the body of the ordinary create call, POST /api/certificates/create. The endpoint requires the operator role.

curl -X POST https://certmate.local/api/certificates/create \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d "$(jq -n --arg csr "$(cat device.csr)" \
        '{domain: "api.example.com", dns_provider: "cloudflare", csr: $csr}')"

The other create fields work as they do for any certificate: dns_provider, account_id, ca_provider, challenge_type and domain_alias. Setting async to true returns 202 with a job id to poll at /api/certificates/jobs/<job_id>.

Through the web UI

The create form has a collapsed section labelled "The private key stays on the device". Open it and paste the CSR. While it holds a CSR, the form disables the SAN editor and the key type, key size and curve selectors, and does not send them. The CSR is only sent when creating a certificate, not when editing an existing one.

Fields the CSR decides

  • Names. The certificate covers the names inside the CSR: the Common Name first, if there is one, then the DNS names in the subjectAltName extension, with duplicates removed. san_domains must be omitted.
  • Key. The device generated the key, so key_type, key_size and elliptic_curve must be omitted.
  • domain is still required and must be one of the names in the CSR. It names the certificate directory, and renewal, the health check and deploy hooks all find the certificate by it.

What Is Refused

These are checked before anything is written, and return 400 with code CERTIFICATE_CREATION_FAILED:

  • csr is not a string: "Invalid CSR: expected PEM text".
  • The CSR is larger than 65536 bytes (64 KiB): "CSR too large".
  • san_domains is also given: "san_domains cannot be combined with a CSR".
  • Any of key_type, key_size or elliptic_curve is also given: "key options cannot be combined with a CSR".
  • The text does not parse as a PEM CSR: "Not a valid PEM certificate signing request".
  • The CSR's signature does not verify against its own public key.
  • The CSR names no domains: it has neither a Common Name nor a subjectAltName extension.

Each name in the CSR is checked against the API key's allowed_domains the same way SANs are. A name outside the scope returns 403 with code DOMAIN_OUT_OF_SCOPE.

These are checked when issuance starts. With async they appear as a failed job rather than in the create response:

  • domain already has a certificate: 409 with code CERTIFICATE_ALREADY_EXISTS.
  • The CSR does not cover domain: 422, with a message listing the names the CSR does request.
  • The domain directory already holds a privkey.pem managed by CertMate: 422. Converting it would leave the old key beside a certificate it cannot serve. Delete the certificate first if you are moving its key onto a device.

What CertMate Stores

In the certificate's directory:

  • csr.pem: the CSR as submitted. Renewal reads it from here.
  • cert.pem, chain.pem and fullchain.pem: what certbot writes in CSR mode. They are written to a csr-out staging directory and then copied beside it.

There is no privkey.pem. In CSR mode certbot generates no key and creates no lineage: no live/ tree and no renewal/ configuration.

The certificate's metadata records the CA, DNS provider, account, challenge type and alias as for any certificate, plus:

  • key_management: external. This marks the certificate as CSR-only for the health check and for renewal.
  • csr_fingerprint: a SHA-256 hash of the CSR's DER encoding, so the same CSR re-exported with different line wrapping has the same fingerprint.
  • san_domains: the CSR's names other than domain.

Status Fields

GET /api/certificates/<domain> reports a CSR-only certificate as follows:

  • private_key_state: external. The other values are present, missing, mismatched and unknown.
  • private_key_present: false.
  • usable: null, not false. The certificate can be used on the device that holds the key, and CertMate cannot answer for a key it does not have.
  • needs_renewal: driven by expiry only. missing and mismatched force needs_renewal; external does not, so a CSR-only certificate is not reissued on every renewal sweep.

If a privkey.pem does turn up beside a CSR-only certificate, it is compared with the certificate like any other key rather than reported as external.

Renewal

certbot renew never renews a certificate issued with --csr; certbot says so itself when it issues one. CertMate therefore renews it by running issuance again with the stored csr.pem, using the CA, DNS provider, account, challenge type and alias recorded in the metadata.

  • Scheduled renewal. The renewal sweep handles CSR-only certificates the same way as all others: it renews those whose needs_renewal is true, using the same threshold.
  • Manual renewal. POST /api/certificates/<domain>/renew works as usual. For a CSR-only certificate it always sends the CSR to the CA, with or without force.
  • Same certificate returned. If the CA returns the same certificate, for example on a repeat request within the CA's reuse window, the renewal is not counted: the response has renewed: false and deploy hooks do not run.
  • Missing CSR. If csr.pem is gone, renewal fails with "Cannot renew <domain>: it was issued from a CSR this instance no longer has". Submit the CSR again from the device that holds the key.

Key Rotation

If the device generates a new key, it needs a new CSR. The create call refuses a domain that already has a certificate (409), and the edit/reissue path does not accept a CSR. To switch to the new CSR, delete the certificate with DELETE /api/certificates/<domain> (admin role), then submit the new CSR with the create call. Deleting removes the files from disk; it does not revoke the certificate at the CA.

Deploy Hooks

A CSR-only certificate has no key to deploy.

  • Shell hooks run normally. CERTMATE_CERT_PATH, CERTMATE_CHAIN_PATH and CERTMATE_FULLCHAIN_PATH are set as usual. CERTMATE_KEY_PATH is not set, so a hook can test [ -n "$CERTMATE_KEY_PATH" ].
  • Typed deploy targets publish the key with the certificate, so they cannot serve a CSR-only certificate. They are skipped and recorded as a failure with a message saying the key stays on the device and that a shell hook should be used instead.

To deliver the certificate to the appliance, use a shell hook that copies only the certificate and chain.
