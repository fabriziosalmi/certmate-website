Client Certificates

The private CA CertMate uses to sign client certificates for mTLS and VPN access, and how to issue, download, renew and revoke them.

What the Private CA Is For

Server certificates come from an ACME certificate authority. Client certificates do not. CertMate signs them with its own private CA, which it generates on first start. A server that requires client certificates, for mTLS on an API or for VPN access, trusts that CA and accepts the certificates it signed.

The CA is self-signed and trusted by nothing until you install it. It is for identities inside your own systems, not for anything a browser or a public client has to accept.

The CA

The CA has a 4096-bit RSA key, is valid for 10 years and signs with SHA-256. It lives in the data directory (data by default, or CERTMATE_DATA_DIR), under certs/ca/:

  • ca.crt: the CA certificate.
  • ca.key: the CA private key.
  • ca_metadata.json: common name, dates, serial, key size and issuer fields.
  • crl.pem: the current certificate revocation list.

All four files are written atomically with mode 0600. CertMate has no endpoint that serves ca.crt by itself. Copy it from the data directory, or take it from a .pfx download, which carries it as the chain.

On start, CertMate refuses to load a CA whose key does not match its certificate, and refuses to regenerate one when only ca.crt or only ca.key is present; it logs which file is missing so you can restore it. An expired CA signs nothing.

Choosing the CA Subject

Unless configured, the CA subject is C=CH, ST=Switzerland, O=CertMate, OU=Certificate Authority, CN=CertMate CA. Since v2.33.0 the client_ca_subject key in settings.json sets it:

{
  "client_ca_subject": {
    "country": "IT",
    "state": "Liguria",
    "organization": "Acme SpA",
    "organizational_unit": "IT Security",
    "common_name": "Acme Client CA"
  }
}

country must be a two-letter ISO 3166-1 code; anything else is refused before a key is written. An empty field is left out of the subject. An empty common_name falls back to CertMate CA.

The setting is read once, when the CA is created. Changing it afterwards does nothing, because regenerating the CA would stop every certificate it signed from verifying. To set a subject on an instance that already has a CA, use the reset below.

POST /api/settings does not accept client_ca_subject. Set it in settings.json before the first start, or pass the subject to the reset.

Resetting the CA

POST /api/client-certs/ca/reset (admin) replaces the CA. The body must carry the confirmation phrase as a string. subject is optional and takes the same fields as client_ca_subject; without it, the new CA keeps the current subject.

curl -X POST https://certmate.example.com/api/client-certs/ca/reset \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "confirm": "reset-client-ca",
    "subject": {"country": "IT", "organization": "Acme SpA", "common_name": "Acme Client CA"}
  }'

A missing or different confirm returns 400, and so does an invalid subject; either way nothing changes. On success the reset:

  1. copies the old ca.key, ca.crt and ca_metadata.json to certs/ca/backups/ with a timestamp in each name;
  2. generates a new CA;
  3. deletes every client certificate the old CA signed;
  4. republishes the CRL, signed by the new key;
  5. writes a ca_reset audit record with the number of certificates removed.

The response gives certificates_removed and a warning. Server certificates, settings and DNS accounts are not touched. Afterwards, install the new ca.crt on every server that trusted the old one and issue the client certificates you still need. CRLs and OCSP answers published for the old CA can no longer be verified. Keep the backup: the old key is the only thing that can sign a CRL for the certificates the old CA issued.

Issuing Client Certificates

In the web UI

Client certificates have their own view on the dashboard (/client-certificates redirects to it). The create form takes a common name (required), email, organization, a usage type (API mTLS, VPN Access, User Authentication or Other), a validity in days and notes. Bulk Upload (CSV) creates up to 100 at once.

Through the API

curl -X POST https://certmate.example.com/api/client-certs/create \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "common_name": "billing-service",
    "email": "ops@example.com",
    "organization": "Acme SpA",
    "organizational_unit": "Payments",
    "cert_usage": "api-mtls",
    "days_valid": 365,
    "notes": "calls the ledger API"
  }'

Only common_name is required, 1 to 64 characters. The defaults and limits:

  • email: empty; at most 254 characters.
  • organization: CertMate; at most 64 characters.
  • organizational_unit: Users; at most 64 characters.
  • cert_usage: api-mtls.
  • days_valid: 365; between 1 and 3650.
  • notes: empty.

The request needs the operator role and returns 201 with the new identifier, the on-disk paths and the full metadata. The identifier is the common name reduced to lowercase letters, digits, ., _ and -, followed by a hyphen and eight hex characters: billing-service-3f9a1c2e. Every other call uses it.

CertMate generates the key pair. The create endpoint takes no CSR, so the private key is created on the CertMate host.

What Is Issued

  • A 2048-bit RSA key.
  • Subject: the common name, organization, organizational unit and email you gave, with C=CH and ST=Switzerland. The client certificate subject does not follow client_ca_subject.
  • Issuer: the CA subject.
  • Extensions: basicConstraints CA:FALSE, keyUsage digitalSignature, keyEncipherment and extendedKeyUsage clientAuth, all critical; subject and authority key identifiers.
  • No CRL distribution point and no OCSP URL. A server that checks revocation has to be given the CRL itself (see below).

Each certificate gets a directory under certs/client/ in the data directory, named by its identifier. The parent is vpn/ when the usage contains vpn, api/ when it contains api or mtls, and other/ for anything else. The directory holds <identifier>.crt, <identifier>.key (mode 0600), <identifier>.csr and metadata.json.

Batch Creation

POST /api/client-certs/batch (operator) takes CSV data already split into headers and rows. headers must include common_name; email, organization, cert_usage, days_valid and notes are also read. A batch of more than 100 rows is refused.

curl -X POST https://certmate.example.com/api/client-certs/batch \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "headers": ["common_name", "email", "cert_usage", "days_valid"],
    "rows": [
      ["alice", "alice@example.com", "vpn", "365"],
      ["bob", "bob@example.com", "vpn", "180"]
    ]
  }'

In a batch, a days_valid that is not a number becomes 365, and one outside 1 to 3650 is clamped. One failed row does not stop the others. The 201 response gives total, successful, failed, the created certificates and an errors list whose row is the CSV line number, counting the header as line 1.

Listing and Inspecting

  • GET /api/client-certs returns certificates (metadata, newest first) and total. ?revoked=true or false filters by revocation; ?search= matches the common name or email; ?usage= selects the storage group the usage falls into (vpn, api or other), not the exact usage string.
  • GET /api/client-certs/<identifier> returns one certificate's metadata: subject fields, serial_number (decimal), created_at, expires_at, days_valid, revoked, revoked_at, reason_revoked, renewal_enabled, renewal_threshold_days and, once renewed, superseded_by.
  • GET /api/client-certs/stats returns total, active (not revoked), revoked, counts by_usage and by_organization, and ca_status (active or not_loaded).

All three need the viewer role.

Downloading

GET /api/client-certs/<identifier>/download/<type>, where type is one of:

TypeContentRole
crtThe certificate, PEM.viewer
csrThe CSR CertMate generated, PEM.viewer
keyThe private key, PEM.operator
pfxPKCS#12 bundle: certificate, private key and the CA certificate as chain, encrypted with the PFX password.operator

A viewer asking for key or pfx gets 403. The .pfx is built on request and encrypted with the PFX password set in Settings, the same password as the server certificate export. Without one, the download returns 400 Set a PFX password in Settings to enable PKCS#12 export; CertMate never produces an unencrypted bundle. In the web UI the detail view of a certificate has a download button for each type.

curl -fsS -H "Authorization: Bearer $TOKEN" \
  -o billing-service.pfx \
  https://certmate.example.com/api/client-certs/billing-service-3f9a1c2e/download/pfx

Renewal

POST /api/client-certs/<identifier>/renew (operator), or Renew in the list, issues a new certificate with a new key, a new serial and a new identifier. It keeps the subject, usage and validity of the original. The response is 201 with the new certificate, like a create.

The original is marked superseded_by the new identifier and its automatic renewal is turned off. It is not revoked: it stays valid until it expires or you revoke it. A revoked certificate cannot be renewed.

Every certificate is created with renewal_enabled true and renewal_threshold_days 30. A scheduled job runs daily around 03:00 (up to an hour either side) and renews each certificate that is not revoked, not superseded, not yet expired and within 30 days of expiry. An expired certificate is not renewed automatically. Scheduled renewals are written to the audit log. Renewal gives the holder a new key and certificate; the new files still have to reach the client.

Revocation

POST /api/client-certs/<identifier>/revoke needs the admin role. Revoke in the web UI asks for confirmation first and sends User requested as the reason.

curl -X POST https://certmate.example.com/api/client-certs/billing-service-3f9a1c2e/revoke \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason": "keyCompromise"}'

reason is free text and defaults to unspecified. The metadata records revoked_at and the reason, and the CRL is regenerated from every revoked certificate. When the reason names an RFC 5280 reason code (keyCompromise, caCompromise, affiliationChanged, superseded, cessationOfOperation, certificateHold, privilegeWithdrawn, aACompromise or removeFromCRL, in any case, with or without _ or -), the CRL entry carries it. Any other reason, unspecified included, leaves the entry without a reason code.

A revocation takes effect only on servers that check the CRL. CertMate does not reach out to the servers that trust the CA.

Deploy Hooks on Revocation

A successful revocation fires the revoked deploy hook event. Client certificates are the only certificates CertMate can revoke, so this is the only time the event fires. CERTMATE_DOMAIN holds the client certificate's identifier and CERTMATE_EVENT is revoked. The path variables point into the server certificate directory and do not name the client certificate's files.

A hook runs on revoked only if its on_events includes it; new hooks get created and renewed. A global hook with revoked runs for every client certificate revocation. For example, to tell another system which identity was withdrawn:

{
  "id": "mtls-revoked",
  "name": "Report revoked client certificate",
  "command": "curl -fsS -X POST https://idp.internal/api/mtls/revoked/$CERTMATE_DOMAIN",
  "enabled": true,
  "timeout": 30,
  "on_events": ["revoked"]
}

The hook runs inside the CertMate container, which has curl. See Deploy Hooks for configuration and the command rules.

CRL and Status Lookup

Relying parties need these two endpoints without a CertMate account, so they take no authentication. Each has its own rate-limit bucket: 200 requests a minute for status lookups and 60 for CRL downloads by default.

CRL

GET /api/crl/download/<format>, where format is:

  • pem: the CRL in PEM, as the attachment ca.crl.
  • der: the same CRL in DER.
  • info: JSON with status, issuer, last_update, next_update, revoked_count and revoked_serials.

The CRL is signed by the CA and valid for 7 days. CertMate regenerates it on every revocation and on a CA reset, and again when it is requested after its next_update has passed, so a server that fetches it on a schedule never gets an expired one. Each entry keeps the revocation date it was recorded with.

curl -fsS -o ca.crl https://certmate.example.com/api/crl/download/pem

Status by serial

GET /api/ocsp/status/<serial> takes the decimal serial number (the serial_number in the metadata) and returns JSON with certificate_status set to good, revoked or unknown. A revoked certificate also has revocation_time and revocation_reason. It answers from the certificate metadata at the moment of the request.

curl -fsS https://certmate.example.com/api/ocsp/status/258328937016381437591925094542366227683

This is a JSON lookup for scripts and monitoring. It is not an RFC 6960 OCSP responder, and the certificates carry no OCSP URL, so a TLS server does not query it on its own.

Trusting the CA on a Server

A server that accepts CertMate client certificates needs two things from CertMate:

  • ca.crt, as the CA it verifies client certificates against;
  • the CRL from /api/crl/download/pem (or der), fetched again before its next_update, if the server checks revocation.

How to configure each is up to the server's own documentation; CertMate's documentation does not cover it.

Backups

The CA and the client certificates are in the certs subtree of the data directory, which the unified backup includes. A share-safe backup leaves out ca.key and the client keys; only a disaster-recovery backup carries them. Without ca.key, a restored instance can neither issue client certificates nor sign a CRL for the ones already out. See Backup and Recovery.
