Troubleshooting

From the symptom you see to the cause and the fix

Where to Look First

The container logs to stdout, as JSON unless CERTMATE_LOG_JSON=false. No application log file is written unless you set CERTMATE_LOG_FILE (for example /app/logs/certmate.log). The audit log is always at logs/audit/certificate_audit.log.

docker logs certmate
docker exec certmate tail -n 50 /app/logs/audit/certificate_audit.log

/health always answers 200 while the process serves requests. Its status field is healthy or degraded, and checks covers the scheduler, certbot, the certificate directory and free disk space. /health/ready answers 503 when the renewal scheduler is not running or certbot failed its probe.

curl -s http://localhost:8000/health
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8000/health/ready

When you report a problem, include the version you are running. It is in the footer of every page of the web UI, and in the version field of /health.

Debug Logging

In the container, set CERTMATE_LOG_LEVEL=DEBUG and restart. LOG_LEVEL is not read. When you run python app.py directly, use the flag instead: --log-level defaults to INFO and overrides the variable.

python app.py --log-level DEBUG

--debug exits with ERROR: Debug mode cannot be enabled in production when FLASK_ENV=production, which the image sets. FLASK_DEBUG has no effect.

The Container Exits at Startup

"Required directories are not writable by the CertMate process"

CertMate refuses to start unless certificates, data, backups and logs are writable, and the message lists each failing directory. The usual cause is a bind mount, which keeps the host directory's ownership. The image runs as UID/GID 1000, or under rootless podman and OpenShift as an arbitrary UID in group 0. Make the host directories writable by group 0 once:

mkdir -p ./{certificates,data,logs,backups}
chgrp -R 0 ./{certificates,data,logs,backups}
chmod -R g+rwX ./{certificates,data,logs,backups}

Named volumes need no preparation. With podman you can instead add the :U option to each bind mount.

"Failed to initialize CertMate app: ..."

CertMate logs this and exits with status 1 rather than start without a secret it was told to use. The text after the colon names the cause:

  • SECRET_KEY_FILE is set to ... but cannot be used: the file is unreadable or empty. Fix the mount or its permissions, or unset SECRET_KEY_FILE.
  • API_BEARER_TOKEN is set but not usable, or the same for API_BEARER_TOKEN_FILE: the token must be 32 to 512 characters, and the message names the rule it broke.
  • settings.json exists but cannot be read, and no backup can replace it.

Certificate Creation Fails

A failed certbot run returns HTTP 422 with code CERTIFICATE_CREATION_FAILED, an error that reads Certificate creation failed: followed by certbot's output with credentials removed, and a hint. The same redacted output is logged on a line starting Certbot failed for '<domain>':. If a CAA record forbids the CA, the error says so.

A request refused before certbot runs returns HTTP 400, also with code CERTIFICATE_CREATION_FAILED; the error says what is missing.

CA not configured

Since v2.35.0, a certificate requested from a CA whose configuration or account cannot be loaded is refused, not issued by a different CA. The request returns HTTP 400 with an error that starts:

CA provider '<ca>' is not configured on this instance, and issuing from a different CA is not a substitute for the one you asked for.

and the hint Configure that CA under Settings > Certificate Authority providers, or request a CA that is already configured. Let's Encrypt and "Let's Encrypt (Staging)" need no saved configuration and are not refused. A reissue whose CA, named in the request or kept from the certificate, is not configured returns 400 with code CERTIFICATE_REISSUE_REJECTED and the same error.

ACME directory URL must use https

Since v2.35.0, an ACME directory URL configured on a CA account must use https. Issuing from an account whose URL is http:// returns HTTP 400 with an error of the form:

<CA name> ACME Directory URL must use https. A directory fetched over plain HTTP cannot be trusted to be the one you meant.

A URL without a scheme gets Invalid <CA name> ACME Directory URL format instead. Change the URL on the CA account in Settings to its https:// form.

Provider account not configured

DNS provider '<provider>' account '<id>' not configured returns HTTP 400 before certbot runs. Add the account, or fix its credentials, in Settings, then try again.

The TXT record is not visible in time

For DNS-01, certbot waits a fixed time after creating the record, then asks the CA to validate. Each provider has a default wait, which the dns_propagation_seconds setting overrides per provider (1 to 3600 seconds). Check what a public resolver sees during an issuance:

dig TXT _acme-challenge.example.com @8.8.8.8 +short

With a domain alias, first check that _acme-challenge resolves as a CNAME to the validation domain.

With the custom-script provider, certbot validates as soon as the auth hook returns, so the script must do the waiting; the configured time is passed to it as CERTMATE_DNS_PROPAGATION_SECONDS. For example.com plus *.example.com both challenges share one name, so the hook must add to the TXT record set, not replace it.

Rate Limits and HTTP 429

Check which limit answered before you retry.

  • The certificate authority's limit. A renewal the CA refused returns HTTP 422 with code ACME_RATE_LIMITED. A new certificate the CA refused returns HTTP 422 with code CERTIFICATE_CREATION_FAILED and the hint You've hit the certificate authority's rate limit. Wait before trying again. Retrying makes it worse: wait, or use a different ACME account. The CA's own text in the log names the limit and when it resets. Hits are counted in certmate_acme_rate_limit_hits_total. Test against the "Let's Encrypt (Staging)" CA entry.
  • ISSUANCE_QUEUE_FULL (429): more jobs are queued or running than CERTMATE_ISSUANCE_QUEUE_LIMIT (default 20).
  • Rate limit exceeded (429, retry_after: 60) is CertMate's own per-client API limit.
  • Too many attempts. Please try again later. (429, with a Retry-After header) is the login limit.

A 409 DOMAIN_OPERATION_IN_PROGRESS means another operation holds that domain's lock.

API Requests Return 401

The code field says why: AUTH_HEADER_MISSING, INVALID_AUTH_SCHEME (the scheme is not Bearer), INVALID_AUTH_FORMAT, or INVALID_TOKEN. A token set in API_BEARER_TOKEN or API_BEARER_TOKEN_FILE replaces the stored one at startup, and the old token stops working.

Locked Out of the Web UI

A login answered with 403 Local auth disabled, or a lost admin password, can be fixed from a shell in the container:

docker exec -it certmate python scripts/reset_admin_password.py

It prompts for a password, creates the admin user if missing, and turns local authentication on.

Certificates Are Not Renewing

The renewal sweep runs daily around 02:00, with up to an hour of random offset, and renews certificates within renewal_threshold_days of expiry (default 30). Each sweep ends with a Renewal check complete in ... log line with its counts. If that line is missing, check /health/ready. Other lines that explain a missing renewal:

  • Automatic renewal is globally disabled; skipping renewal check: auto_renew is off.
  • Skipping renewal for <domain>: auto_renew disabled for this certificate: turn it back on with PUT /api/certificates/<domain>/auto-renew.
  • Renewal check skipped N malformed domain entries: fix those entries in settings.json.
  • A critical line CertMate is running with N gunicorn workers: each worker runs its own scheduler and renews every certificate again. Run --workers 1 and raise --threads.

A manual renewal (POST /api/certificates/<domain>/renew) failing with RENEWAL_CONFIG_BROKEN means certbot's renewal configuration points at paths that no longer exist, usually after the data directory moved: use Edit & Reissue. DNS_ACCOUNT_NOT_CONFIGURED means the certificate's DNS account was removed: add it again in Settings.

If the certificate has already expired, browsers show NET::ERR_CERT_DATE_INVALID.

A Deploy Hook Failed

A failing hook never blocks the certificate operation; it raises deploy_hook_failed. GET /api/deploy/history?limit=50 (admin) and the Activity tab show each run's exit code, duration and output. The error reads:

  • exit code N: ...: 127 means the command was not found in the container; use absolute paths.
  • timeout after Ns: raise the hook's timeout (default 30, maximum 300).
  • Command blocked at runtime: ...: move the logic into a script file.
  • Deploy hooks are disabled. Enable them in Settings → Deploy.

A hook held for a deploy window leaves no history until it runs; GET /api/deploy/pending lists held deploys.

The Browser Does Not Trust a New Certificate

If it came from "Let's Encrypt (Staging)", it is an untrusted test certificate, and browsers report errors such as NET::ERR_CERT_AUTHORITY_INVALID. Select the production "Let's Encrypt" entry and reissue.
