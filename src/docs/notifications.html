Notifications

Where CertMate sends certificate events, what each channel needs, which events can be filtered, and the weekly digest.

Where Notifications Are Configured

Notifications are set up in Settings → Notifications. Nothing is sent until Enable Notifications is on; after that, each channel has its own enable switch. The page holds one email channel, the weekly digest, and a list of webhook channels. Click Save Notification Settings to store the changes. Reading or saving this configuration requires the admin role.

Channels

Email uses SMTP. Every other channel is a webhook entry with a type: Generic, Slack, Discord, Telegram, ntfy or Gotify. The type decides the fields the entry shows and the shape of the request CertMate sends.

ChannelWhat you enterWhat CertMate sends
Email (SMTP)SMTP host, port (default 587), username, password, from address, to addresses (comma-separated)One message to all recipients, subject [CertMate] <title>, plain-text and HTML parts
SlackIncoming webhook URLJSON with text and blocks: a header with the title, a section with the message, and one field per event detail
DiscordWebhook URLJSON with one embed: the title, the message as description, and one inline field per event detail
TelegramBot token, chat IDJSON to https://api.telegram.org/bot<token>/sendMessage with chat_id and text, as plain text
ntfyTopic URL, such as https://ntfy.sh/your-topic; priority; optional access tokenThe message and details as a plain-text body, with Title and Priority headers
GotifyServer URL, app token, priority (0–10)JSON with title, message and priority to <server>/message
GenericURL, optional HMAC secret, method, authentication, custom headers, payload template, timeout, attemptsA JSON body, CertMate's own or rendered from your template

Email

The from address defaults to the username when left empty. CertMate logs in only when both username and password are set. The connection is upgraded with STARTTLS; this is the use_tls field, which is on by default and has no switch in the UI. Implicit TLS on connect is not offered. A message is tried up to 3 times, 1 and then 2 seconds apart; a channel without a host or without recipients fails at once and is not retried.

The plain-text part is the message followed by a Details: list of the event's fields; the HTML part shows the same fields as a table.

Microsoft Teams has no channel type of its own. Add a Teams channel's email address as a recipient of the email channel, and Teams posts the message into the channel.

Telegram, ntfy and Gotify

  • Telegram has no URL field: the address is built from the bot token. Both the token and the chat ID are required. The text is the title, the message and one line per event detail, sent without Markdown parsing, so characters such as * and _ in domain names and error messages arrive unchanged.
  • ntfy priority defaults to default; the field suggests default, high or urgent. The access token, if set, is sent as Authorization: Bearer <token>.
  • Gotify needs both the server URL and the app token. The token is sent in the X-Gotify-Key header. Priority defaults to 5.

Slack, Discord, Telegram, ntfy and Gotify always use POST. Their timeout is 10 seconds and they are tried up to 3 times, unless timeout or max_retries is set on the entry through the API.

Generic webhooks

The generic type is for any receiver that is not in the list. Its request body, payload templates, method and authentication options, HMAC signature, retry rules and the restrictions on internal targets are described in Webhooks. The restrictions on internal targets and the retry rules apply to every webhook type, not only generic.

Events

These events reach notification channels. The title is what appears in the email subject, the Slack header and the other channels' title fields.

EventTitleSent when

certificate_renewedCertificate RenewedA certificate is renewed
certificate_failedCertificate FailedIssuance or renewal fails
certificate_revokedCertificate RevokedA client certificate is revoked
certificate_deployedCertificate DeployedAt least one deploy hook succeeded for a certificate
certificate_expiringCertificate ExpiringA certificate crosses an expiry threshold (below)
domain_expiringDomain Registration ExpiringA tracked domain registration crosses an expiry threshold (below)
deploy_hook_failedDeploy Hook FailedA deploy hook or deploy target fails
certificate_deploy_incompleteCertificate Not DeployedA certificate was obtained but not every deploy target received it

The message is <title>: <domain>, extended with the hook name, the days left or "expired" for the two expiry events, and the error when there is one. Other internal events, such as the start and completion of each deploy hook, are not sent to notification channels.

Filters

There are two event filters, and an event must pass both.

  • Notify on Events, at the top of the page, applies to every channel, email included.
  • Events (leave empty for all), on each webhook entry, applies to that webhook only. The email channel has no filter of its own.

An empty filter lets every event through. Both offer the same seven events: certificate_created, certificate_renewed, certificate_deployed, certificate_expiring, certificate_revoked, certificate_failed and domain_expiring.

Always delivered

deploy_hook_failed and certificate_deploy_incomplete have no checkbox. They are sent to every enabled channel whatever either filter says, because they report a certificate that may not have reached the systems serving it. Only the Enable Notifications switch and each channel's own switch stop them.

Expiry Warnings

A job runs every day at 07:00, after the 02:00 renewal sweep, and publishes an expiry event when a certificate or a domain registration crosses a threshold of days left.

EventThresholds (days left)
certificate_expiring, auto-renew on14, 7, 3, 1, 0
certificate_expiring, auto-renew offThe renewal threshold (default 30) or 14, whichever is larger, then 14, 7, 3, 1, 0
domain_expiring60, 30, 14, 7, 1, 0

With auto-renew on, renewal starts at the renewal threshold, so a certificate still unrenewed at 14 days means renewals have been failing. With auto-renew off, the first warning comes when someone has to act. A threshold of 0 means the day it expires, or expired.

Each threshold is announced once per expiry date. A repeated run says nothing new, and a renewed certificate has a new expiry date and starts again from the first threshold. If the job missed days, it announces the nearest threshold that has been crossed, once, rather than every threshold it skipped.

domain_expiring covers only domains whose registration expiry CertMate tracks and could look up; see Domain Health.

Weekly Digest

The digest is a summary email sent every Sunday at 00:00 to the email channel's recipients. It goes out only when notifications are enabled, the email channel is enabled, and Weekly Digest is on; the digest switch is on by default and can be changed only while the email channel is enabled. It is not affected by the event filters and is not sent to webhooks.

The subject is [CertMate] Weekly Certificate Digest. It contains:

  • Server Certificates: total, valid, expiring soon (within the renewal threshold) and expired, followed by each expiring domain with its days left.
  • Client Certificates: total, active and revoked.
  • Activity (last 7 days): certificates created, renewed, and failed operations, counted from the audit log.

Send now sends the digest immediately (POST /api/digest/send, admin). Each send, successful or failed, is recorded in the audit log with the number of recipients; the addresses themselves are not recorded.

Testing a Channel

Send test email and each webhook's Test send one message titled "Test Notification" with the text "This is a test notification from CertMate.", using the values currently in the form, saved or not. A test makes a single attempt, bypasses the event filters and is not written to the delivery log. On failure the toast shows the error returned by the SMTP server or the receiver, or the reason CertMate refused to send.

Delivery Log

Every delivery to the email channel or a webhook, after its retries, is appended to webhook_deliveries.jsonl in CertMate's data directory, which keeps the latest 1,000 entries. The weekly digest and tests are not logged there. Each entry records the time, channel name and type, event, HTTP status, success, number of attempts, error and duration.

Of the destination URL, only the origin is kept: scheme, host and port. The path and query are dropped, because for Slack, Discord, ntfy and Gotify the path is the credential. Recent Deliveries, below the webhook list, shows the latest 50 entries; GET /api/webhooks/deliveries (admin) returns up to 500. Details are in Webhooks.
