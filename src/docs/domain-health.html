Domain Health

How CertMate checks when each domain's registration expires, and whether its mail records, blocklist standing, response headers and TLS versions still hold.

What v2.34.0 Adds

These checks arrived in CertMate v2.34.0. They look at the domain rather than the certificate, which cannot show a lapsed registration or a blocklisted address.

  • domain_registration: when each domain's registration expires.
  • domain_health: seven checks run daily, plus an eighth, weak_tls, that is off until you turn it on.

Both are opt-in: each section defaults to enabled: false.

Unknown Means Nobody Answered

A check that reports unknown could not be completed. It is not a pass. For the blocklist check, unknown means no blocklist gave CertMate a usable answer. It does not mean the domain is clean. The inventory page labels this status "Not verifiable".

It exists because blocklists (DNSBLs) often refuse without saying so clearly:

  • A DNSBL that will not serve a query answers with a 127.255.255.x code instead of an error; .254 means the query came through a public resolver. Spamhaus says these codes must not be taken to mean the address is listed.
  • Through a forwarder, such as a corporate resolver, a caching proxy or Tailscale's MagicDNS, the refusal can arrive as a plain NXDOMAIN, which at the DNS level is identical to "not listed".
  • So CertMate first asks each list about its own test points: every DNSBL keeps 127.0.0.2 permanently listed and 127.0.0.1 permanently unlisted. A list that does not report 127.0.0.2 as listed is not asked about your domains and is named in unanswered. A list that reports 127.0.0.1 is answering everything (a hijacked or wildcarding resolver) and is dropped too.

What to do: point CertMate at a resolver of your own rather than a public one. From v2.35.0 that is a setting, dns_resolver, described under Choosing the resolver; the unknown detail names it. In v2.34.0 the only lever is the DNS of the host or container CertMate runs in.

The rule holds for every check: a timed-out TXT lookup is unknown, not "no SPF record"; an unreachable host is unknown, not "no HSTS". And weak_tls is unknown when the CertMate runtime cannot offer TLS 1.0 or 1.1 at all, so the host was never asked; it is never reported as "refuses old TLS". Same trap, different cause.

Domain Registration Expiry

CertMate follows each registrable domain once, however many hosts sit under it: www.shop.example.co.uk and api.example.co.uk are both example.co.uk. The set is every managed domain and its SANs, what discovery found (unless include_inventory is off), and any extra_domains.

  1. RDAP, at the server the IANA bootstrap (https://data.iana.org/rdap/dns.json) lists for the TLD.
  2. WHOIS on port 43, only for a TLD with no RDAP service. .it, .eu, .de, .es, .ch, .at, .io and .co had none when this was written.
statusMeaning
okRegistered, and the registry published the expiry date.
not_publishedRegistered, but the registry does not publish an expiry (DENIC for .de, EURid for .eu). This is an answer, never replaced by an estimate.
not_registeredThe registry says the name does not exist.
unavailableNo answer this time; error says why. A known expiry is kept. A WHOIS date in a format CertMate does not recognise also lands here, rather than being guessed.

The check runs daily at 06:00. Registries rate-limit, so one sweep asks at most 100 domains, one second apart. A domain is asked again daily within 60 days of expiry, weekly otherwise, and 6 hours after a failed lookup. WHOIS is a raw TCP connection and cannot go through an HTTP proxy, so behind a proxy the TLDs without RDAP come back unavailable.

Domain Health Checks

Seven checks run daily against every name CertMate tracks. An eighth, weak_tls, is opt-in because it is the only check that opens a connection the host did not invite.

CheckWhat it asksRuns on
spfExactly one v=spf1 TXT record, ending in an all mechanism?Registrable domain
dmarcA v=DMARC1 TXT record at _dmarc, with a p= policy?Registrable domain
mxDoes the domain accept mail at all?Registrable domain
blocklistsAre the domain's addresses listed on a DNSBL?Registrable domain
hstsWhat Strict-Transport-Security does the host serve?Each host
security_headersIs the browser told to refuse framing, MIME sniffing and unsanctioned script?Each host
disclosureDoes the response name the software and version answering it?Each host
weak_tls (opt-in)Does the host still accept TLS 1.0 or 1.1?Each host

Mail and blocklist checks use the registrable domain, since DMARC falls back to it. Header checks belong to each host, so www.example.com and example.com each get a row.

statusMeaning
failingA finding: no SPF or DMARC, two SPF records, +all, a DMARC record with no p=, a blocklist listing, no HSTS header.
warningWorth knowing, not broken: no MX, an SPF with no all, an HSTS max-age under six months.
unknownThe check could not be completed. Not a pass.
okThe check ran and found nothing wrong.

A name's overall status is its worst check, in that order. DMARC p=none is ok: the policy is reported, not graded.

Blocklists

The lists are zen.spamhaus.org, bl.spamcop.net, b.barracudacentral.org and dnsbl-1.uceprotect.net. At most four addresses per domain are checked against each.

  • failing: listed on at least one list.
  • ok: not listed, and every lookup was answered.
  • warning: not listed where it could be checked, but some lookups went unanswered; unanswered names them.
  • unknown: no list answered usefully, nothing the domain resolves to could be asked about, or the domain's addresses could not be resolved.

Some addresses are not asked about, and the result says so. They go in a separate not_covered field, one line per address with the reason. Two kinds land there:

  • IPv6 addresses. The test points that prove a list is answering, 127.0.0.2 and 127.0.0.1, only prove it answers about IPv4. Many lists do not serve IPv6, or serve it from a separate zone, so an empty answer about an IPv6 address cannot be told apart from a list that never looked.
  • Since v2.35.0, any address that is not public: private (RFC 1918), loopback, link-local, carrier-grade NAT (100.64.0.0/10) and any other address that is not globally routable. A blocklist lists hosts that send mail on the internet and has nothing to say about 10.0.0.0/8. Not asking also keeps internal addresses from being sent to the four list operators.

That is a limit of what the lists cover, not a lookup that failed, so it does not change the verdict:

  • a domain that no list names is ok, whether or not some of its addresses were not covered; the detail adds how many were not asked about;
  • a domain that resolves only to addresses the lists do not cover, all IPv6 or all internal, is unknown, because nothing was asked. On split-horizon DNS, a name that resolves to 10.x from where CertMate runs is reported unknown, not clean;
  • a list that refused, or a lookup that failed, still goes in unanswered and still turns what would be ok into warning (or unknown if no lookup was answered at all), whatever else the domain resolves to.

Response Headers

hsts, security_headers and disclosure share one HEAD request per host. It verifies the certificate, because a browser ignores these policies on a connection it does not trust.

hsts: no header, no max-age, or max-age=0 is failing; under 15552000 seconds (six months) is a warning. It is read from the first response, including a redirect, as a browser records it.

security_headers keeps two states apart:

  • Missing is a warning: no X-Frame-Options and no CSP frame-ancestors (either is enough), no Content-Security-Policy, or no X-Content-Type-Options: nosniff.
  • Broken is failing, and worse than missing, because it looks like protection and is not: X-Frame-Options other than DENY or SAMEORIGIN (such as ALLOW-FROM, which modern browsers ignore), a Content-Security-Policy-Report-Only with no enforcing policy (it reports and blocks nothing), or X-Content-Type-Options other than nosniff.

disclosure is at most a warning. Server counts only when it carries a version (nginx/1.24.0, not cloudflare); any X-Powered-By, X-AspNet-Version, X-AspNetMvc-Version or X-Generator counts.

The protective headers live on the page, not on the redirect, so CertMate follows up to three hops, only to https and only within the same registrable domain. If a hop cannot be followed, security_headers is unknown and says the host only redirects.

Old TLS Versions

RFC 8996 deprecated TLS 1.0 and 1.1, and CertMate's other probes require TLS 1.2, so they cannot see this. With check_weak_tls on, CertMate makes two handshakes per host, offering TLS 1.0 and then 1.1, sending no data. An acceptance, counted only when the handshake completed at the version offered, is failing.

An unknown here does not mean the host is fine. Modern OpenSSL builds often refuse to offer these versions, so a handshake would fail on the CertMate machine before a byte leaves it. Before contacting any host, CertMate asks its own runtime, in memory, whether it can produce a ClientHello for each version. If it cannot, the result is unknown and unasked says the host was never asked. A host that could not be reached is also unknown. "Refuses" is reported only when CertMate made the offer and the host declined it.

Configuration and Schedule

An admin sets both sections in the Discovery configuration panel on /inventory, or with POST /api/inventory/config. Except enabled and extra_domains, the values shown are defaults.

curl -X POST https://certmate.example.com/api/inventory/config \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "domain_registration": {"enabled": true, "include_inventory": true, "extra_domains": ["brand.it"]},
    "domain_health": {
      "enabled": true,
      "include_inventory": true,
      "check_mail": true,
      "check_blocklists": true,
      "check_headers": true,
      "check_weak_tls": false,
      "extra_domains": ["brand.it"]
    }
  }'

check_mail covers SPF, DMARC and MX; check_headers covers the three header checks. An extra name that is not a domain, or for registration not under a public suffix, returns 400.

Domain health runs daily at 06:30, between the 06:00 registration check and the 07:00 expiry warnings. A name is checked again only after 20 hours, and one run checks at most 200 names. POST /api/inventory/scan (Scan now) also runs both checks, after discovery and the CT poll, when they are enabled.

Choosing the resolver

Since v2.35.0, CertMate can be told which nameservers to ask for the DNS lookups it makes itself: the SPF, DMARC, MX and blocklist lookups, the addresses the blocklist check asks about, and the CAA check (the warning on the create form before an issuance, and the explanation after a failed one). The header and TLS checks still reach hosts through the system's resolver. Without the setting, CertMate uses the system's resolver: /etc/resolv.conf, Docker's --dns, or the pod's dnsConfig, exactly as in v2.34.0.

An admin sets it in the DNS resolvers field of the Discovery configuration panel on /inventory, one address per line, or with POST /api/inventory/config:

curl -X POST https://certmate.example.com/api/inventory/config \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"dns_resolver": {"nameservers": ["10.0.0.53", "10.0.0.54:5353"]}}'

Or in the environment: CERTMATE_DNS_RESOLVERS=10.0.0.53,10.0.0.54. When both are set, the stored setting wins, so what the interface shows is what CertMate uses.

  • Addresses only, not hostnames: resolving a nameserver's name would need the resolver being replaced.
  • A port may follow the address: 10.0.0.53:5353, or [2001:db8::1]:5353 for IPv6.
  • An entry that is not an address, or a port outside 1-65535, returns 400. An invalid value in CERTMATE_DNS_RESOLVERS is ignored and the system resolver is used.
  • Leaving it empty keeps the system resolver.
  • A change applies from the next domain health run; no restart is needed.

GET /api/inventory/config returns the nameservers in use under dns_resolver, including ones that come from the environment.
