DNS-01 Delegation

How CertMate issues for a domain whose DNS it cannot write, by answering the DNS-01 challenge in a zone it can.

The Problem

A DNS-01 challenge is answered by publishing a TXT record at _acme-challenge.<domain>. CertMate does that through the API of a configured DNS provider, so it needs write access to the zone that holds the name. Sometimes it cannot have it: the zone is served by several providers at once (multi-master DNS), the provider has no API CertMate supports, or the zone belongs to someone else who will not hand out credentials.

How Delegation Works

The owner of the domain adds one CNAME, once, from the challenge name into a zone CertMate can write. CertMate calls that zone the domain alias (the domain_alias field). At issuance and at every renewal CertMate writes the TXT value at _acme-challenge.<domain_alias>; the CA's lookup of _acme-challenge.<domain> follows the CNAME and finds it there. The certificate is still ordered for the real domain: only the place where the challenge is answered moves.

The DNS credentials CertMate holds are those of the alias zone, so they never need to reach the zone that serves the domain. It does not matter which provider answers a given query for the domain, as long as each one serves the CNAME.

Create the CNAME

Pick a name in a zone CertMate can write, for example validation.example.org. In every DNS provider that serves example.com, add:

_acme-challenge.example.com. 300 IN CNAME _acme-challenge.validation.example.org.

The target always carries the _acme-challenge. prefix in front of the alias. Every name on the certificate needs its own CNAME, all pointing at the same target:

_acme-challenge.example.com.     300 IN CNAME _acme-challenge.validation.example.org.
_acme-challenge.www.example.com. 300 IN CNAME _acme-challenge.validation.example.org.

Put the CNAMEs in place before requesting the certificate.

Configure the Alias in CertMate

In the dashboard

  1. Choose the DNS Provider (and Account, if the provider has several) that controls the alias zone, not the domain's own zone.
  2. Open Advanced Options and fill in DNS-01 Alias Domain with the alias, without the _acme-challenge. prefix: validation.example.org. The form strips the prefix, and a trailing dot, if you paste them.
  3. Once the domain and the alias are filled in, the help text under the field lists the CNAMEs to create, one per requested name. Check DNS-01 Alias looks them up before you submit.

A certificate issued this way shows a Check DNS-01 Alias button in its detail panel, which repeats the check against the names the certificate carries.

Through the API

POST /api/certificates/create (operator) takes domain_alias beside the usual fields. dns_provider and account_id name the provider account that writes the alias zone:

curl -X POST https://certmate.example.com/api/certificates/create \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "domain": "example.com",
    "san_domains": ["www.example.com"],
    "dns_provider": "cloudflare",
    "domain_alias": "validation.example.org"
  }'

The alias is validated as a domain name, so a value that still carries _acme-challenge. is rejected with Invalid domain_alias.

CertMate stores the alias in the certificate's metadata as domain_alias, and the provider that writes it as alias_dns_provider, which at creation is the dns_provider of the request. Both appear in GET /api/certificates/<domain>, and renewals read them from there, so a renewal needs nothing new from you.

Changing or removing the alias

  • POST /api/certificates/<domain>/reissue (operator) takes domain_alias (omit to keep it, "" to clear it) and alias_dns_provider (omit to keep it). Clearing the alias also clears alias_dns_provider, and the certificate goes back to the provider's normal DNS-01 flow. In the dashboard, editing a certificate and emptying the alias field does the same.
  • PATCH /api/certificates/<domain> (operator) takes alias_dns_provider without reissuing, for when the alias zone moves to another provider. The provider must already be configured, or the request fails with 400; the new value applies from the next renewal.

An alias provider different from dns_provider is looked up under the certificate's account_id.

Which Providers Can Write the Alias Zone

Alias mode does not use the provider's certbot plugin. CertMate runs certbot with a manual DNS hook of its own that creates the TXT record through the provider's API, waits the provider's propagation time (the dns_propagation_seconds value for that provider, otherwise its default), and deletes the record once validation is over. A failed deletion is logged and does not fail the issuance.

The hook supports these providers: cloudflare, route53, azure, google, powerdns, digitalocean, linode, edgedns, gandi, ovh, namecheap, arvancloud, infomaniak, acme-dns, duckdns and rfc2136. With any other provider a request that sets domain_alias fails with DNS alias mode does not support this DNS provider yet. The domain being certified can sit at any provider, including one CertMate does not support; only the alias zone has to be on this list.

For rfc2136 (BIND, Technitium and other servers that accept dynamic updates), the TXT is written with a TSIG-signed update using the account's nameserver, tsig_key and tsig_secret. CertMate finds the zone that owns the alias from the server's SOA, so one TSIG key can serve several zones.

Alias mode applies to DNS-01 only; with challenge_type set to http-01 the alias is not used.

ACME-DNS

ACME-DNS is itself built on this kind of delegation: the _acme-challenge CNAME points at the subdomain the ACME-DNS server assigned to your account, and CertMate publishes the TXT value with an authenticated update to that server. CertMate sends every acme-dns issuance and renewal through its alias hook, using the account's Subdomain as the alias, whether or not domain_alias is set. If you do set domain_alias with ACME-DNS, it must match the configured subdomain exactly, or the request fails with ACME-DNS domain_alias must match configured subdomain. CertMate does not delete the record afterwards, since ACME-DNS keeps only the latest validation value.

Wildcards

The challenge for *.example.com is answered at _acme-challenge.example.com, the same name as for example.com, so one CNAME serves both. Request the wildcard as the domain, or tick Generate wildcard certificate in the dashboard, which covers *.example.com and example.com:

curl -X POST https://certmate.example.com/api/certificates/create \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "domain": "*.example.com",
    "dns_provider": "cloudflare",
    "domain_alias": "validation.example.org"
  }'

The CNAME is the same as for the apex:

_acme-challenge.example.com. 300 IN CNAME _acme-challenge.validation.example.org.

Verify the Delegation

With dig

# The CNAME, as a public resolver sees it
dig @8.8.8.8 _acme-challenge.example.com CNAME +short
# Expected: _acme-challenge.validation.example.org.

# While an issuance is running, the TXT value on the alias
dig _acme-challenge.validation.example.org TXT +short

The TXT record exists only between the hook's create and delete steps, so an empty answer outside an issuance is expected.

With CertMate's check

Two viewer endpoints check the CNAMEs:

  • POST /api/certificates/check-dns-alias, before a certificate exists. domain and domain_alias are required; san_domains adds names; wildcard: true adds *.<domain>.
  • GET /api/certificates/<domain>/dns-alias-check, for a certificate that exists. It reads the alias and the SANs from the certificate and answers 400 when the certificate does not use alias mode.
curl -X POST https://certmate.example.com/api/certificates/check-dns-alias \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"domain": "example.com", "domain_alias": "validation.example.org", "san_domains": ["www.example.com"]}'
{
  "domain": "example.com",
  "domain_alias": "validation.example.org",
  "ok": false,
  "checks": [
    {
      "source": "_acme-challenge.example.com",
      "expected_target": "_acme-challenge.validation.example.org",
      "found_targets": [],
      "status": "missing",
      "ok": false,
      "error": null
    }
  ]
}

Each check has a status: ok, missing (no CNAME), mismatch (a CNAME to another target, listed in found_targets) or error (the lookup failed, and error says why). The top-level ok is true only when there is at least one check and every check is ok. Every name is checked against the caller's scope, so a scoped API key gets 403 for a name outside it.

The check resolves the CNAMEs over DNS-over-HTTPS at cloudflare-dns.com. If CertMate's outbound traffic goes through an allowlist, that host has to be on it.

Troubleshooting

  • The check reports missing. The CNAME is absent, or not yet visible. Check each provider that serves the domain: with multi-master DNS, every one of them must serve the CNAME.
  • The check reports mismatch. The CNAME points elsewhere. A common cause is a target without the _acme-challenge. prefix: the target must be _acme-challenge.<alias>, while the alias field takes the name without it.
  • DNS alias mode does not support this DNS provider yet. The provider chosen for the request is not one the hook supports. Choose the account that controls the alias zone, which must be on the list above.
  • <provider> DNS alias mode requires: .... The provider account is missing credential fields the hook needs. Complete it in Settings.
  • Alias DNS provider '...' is not configured. alias_dns_provider names a provider with no configured account. Configure it, or change the value with PATCH.
  • A renewal fails with Cannot renew ...: DNS alias provider account for ... is not configured. The provider account that writes the alias zone was removed or renamed after issuance. Restore it, or point the certificate at another one with PATCH.
  • The CA does not find the TXT record. The record may not have reached the alias zone's servers before the CA looked. Raise the propagation time for the alias zone's provider.
